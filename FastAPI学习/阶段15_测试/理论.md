## 知识点 15.1：测试基础

### ① 为什么要测试？

你写了一个函数，跑了一下，输出看起来没问题——于是你觉得"应该是对的"。

但"看起来没问题"和"真的没问题"之间，可能差了一百种你没想到的情况。

**靠肉眼检查代码，就像靠肉眼检查工厂生产的零件——你永远不知道哪个零件内部有裂纹。** 工厂的做法是：每个零件都上质检台，用仪器检测，合格的放行，不合格的打回。

测试就是代码的"质检台"。

你写了一个处理用户消息的函数，你不能只试一句"你好"就说它没问题。万一用户发的是空字符串呢？发了一万字呢？发了特殊字符呢？这些情况你都要主动去测。

> **一句话通俗定义：测试 = 用代码去检验你的代码，看它在各种情况下是不是都能正确工作。**

### ② 三种测试类型：从零件到整机

想象你在开一家手机工厂，质检分三个层次：

#### 🔹 单元测试 = 检查单个零件

> 类比：拿到一颗螺丝钉，用仪器测它的直径、强度、材质是否达标。

在代码里，就是**测试一个单独的函数**，看它给正确的输入能不能得到正确的输出。

比如你写了一个 `format_prompt(user_input)` 函数，单元测试就是：
- 输入 `"你好"`，看返回的是不是你期望的格式
- 输入 `""`（空字符串），看它怎么处理

**只测这一个函数，不关心别的。**

#### 🔹 集成测试 = 检查零件组装

> 类比：把屏幕、电池、主板组装在一起，看它们能不能正常配合工作——屏幕能不能亮、充电能不能充进去。

在代码里，就是**测试多个模块配合在一起是否正确**。

比如你的 Agent 服务有一个 `/api/v1/chat` 接口，它内部会调用"格式化提示词"函数、"调用大模型"函数、"解析返回结果"函数。集成测试就是：发一个请求过去，看这一整条链路能不能跑通。

#### 🔹 端到端测试 = 检查整台机器

> 类比：手机组装好了，开机、打电话、拍照、上网——完整走一遍用户实际使用的流程。

在代码里，就是**模拟真实用户的完整操作流程**。

比如：用户先登录 → 发送一条消息 → 收到 AI 回复 → 查看历史记录——这一整个流程是否都正常。

#### 三种类型的对比

| 类型 | 类比 | 测什么 | 范围 |
|------|------|--------|------|
| **单元测试** | 检查一颗螺丝钉 | 单个函数对不对 | 最小 |
| **集成测试** | 检查零件组装 | 多个模块配合对不对 | 中等 |
| **端到端测试** | 检查整台机器 | 完整流程对不对 | 最大 |

### ③ 为什么不能只靠"手动试试"？

你可能会想："我手动在浏览器里试一下不就行了？"

问题是：
- **你改了一行代码，怎么知道没把别的地方搞坏？** 手动试一遍太慢了，但自动化测试几秒钟就能跑完。
- **人会犯懒，但测试不会。** 你不想每次都手动输入那些边界情况，但测试可以。
- **代码越来越多，手动测试越来越不现实。** 100 个接口你每个都手动试一遍？测试可以一键全跑。

> **测试的本质：让机器帮你反复检查代码，确保它现在是对的，将来改完代码之后还是对的。**

## 知识点 15.2：FastAPI 测试

### ① TestClient 是什么？

测试 API 接口，正常来说你需要：
1. 启动服务器（`uvicorn main:app`）
2. 打开浏览器或 Postman
3. 手动输入 URL，发送请求
4. 查看返回结果

这太麻烦了。FastAPI 提供了一个 **TestClient**——一个"模拟浏览器"。

> **类比：汽车碰撞测试。你不可能每次都拿真车、让真人坐上去撞。你用假人、用模拟器，在实验室里就能模拟碰撞场景。**

TestClient 就是这个"假人"。它**不需要你真的启动服务器**，就能模拟发送请求、接收响应。你在代码里写测试，一键运行，几秒钟就知道结果。

### ② 安装依赖

```bash
pip install pytest httpx
```

- `pytest`：Python 的测试框架，帮你组织和运行测试
- `httpx`：TestClient 底层依赖的 HTTP 客户端库

### ③ 基本用法：模拟发送请求

先看一个完整的例子，然后逐行拆解：

```python
from fastapi import FastAPI
from fastapi.testclient import TestClient

# ---- 这是你的 FastAPI 应用 ----
app = FastAPI()

@app.get("/api/v1/chat")
async def chat(message: str):
    """一个简单的 AI 对话接口"""
    return {"response": f"AI收到: {message}"}

# ---- 这是测试代码 ----
client = TestClient(app)  # 创建一个"模拟浏览器"

def test_chat():
    """测试对话接口是否正常工作"""
    # 第一步：模拟发送一个 GET 请求
    response = client.get("/api/v1/chat", params={"message": "你好"})

    # 第二步：检查返回的状态码是不是 200（成功）
    assert response.status_code == 200

    # 第三步：检查返回的内容是不是我们期望的
    assert response.json() == {"response": "AI收到: 你好"}
```

#### 逐行解释关键概念：

**`client = TestClient(app)`**
- 把你的 FastAPI 应用"喂"给 TestClient，它就知道了你有哪些接口
- 相当于给"假人"输入了汽车的图纸，它就知道该在哪里放传感器

**`client.get("/api/v1/chat", params={"message": "你好"})`**
- `client.get()` = 模拟发送一个 **GET 请求**（就像在浏览器地址栏输入 URL 然后回车）
- `params={"message": "你好"}` = URL 上的**查询参数**，最终会变成 `/api/v1/chat?message=你好`
- 就像你在百度搜索时，搜索词是拼在 URL 后面的

**`client.post("/api/v1/chat", json={"message": "你好"})`**
- `client.post()` = 模拟发送一个 **POST 请求**（提交数据）
- `json={"message": "你好"}` = 数据放在**请求体**里，以 JSON 格式发送
- 就像你填写表单提交，数据是"藏"在请求里面的，不在 URL 上

#### `params` 和 `json` 的区别：

| 参数 | 对应什么 | 用在哪 | 类比 |
|------|----------|--------|------|
| `params=` | 查询参数（URL 上） | GET 请求 | 百度搜索框——关键词写在地址栏里 |
| `json=` | 请求体（Body） | POST 请求 | 填写表单——数据藏在表单里面 |

### ④ `assert` 是什么？

`assert` 中文叫**"断言"**，意思就是：**"我断言这里应该是这样的，如果不是，就报错！"**

```python
assert response.status_code == 200
```

翻译成人话就是：
> "我断言（我坚信）返回的状态码应该是 200。如果不是 200，这个测试就失败！"

```python
assert response.json() == {"response": "AI收到: 你好"}
```

> "我断言返回的 JSON 数据应该是这个内容。如果不是，测试失败！"

**断言就是测试的"判断标准"。** 你告诉程序"什么是对的"，程序帮你检查"实际结果和预期是否一致"。

### ⑤ 异步测试

如果你的接口是 `async def` 定义的（异步函数），你也可以用异步的方式测试：

```python
import pytest
from httpx import AsyncClient
from fastapi import FastAPI

app = FastAPI()

@app.get("/api/v1/chat")
async def chat(message: str):
    return {"response": f"AI收到: {message}"}

@pytest.mark.asyncio
async def test_async_chat():
    """用异步方式测试对话接口"""
    async with AsyncClient(app=app, base_url="http://test") as ac:
        response = await ac.get("/api/v1/chat", params={"message": "你好"})
    assert response.status_code == 200
```

- `@pytest.mark.asyncio`：告诉 pytest"这是一个异步测试"
- `AsyncClient`：异步版本的 TestClient
- `await ac.get(...)`：异步发送请求，需要加 `await`

> 对于初学者，先用同步的 `TestClient` 就够了。异步测试在接口涉及数据库、外部调用等场景时才真正有用。

## 知识点 15.3：测试用例设计

写好了测试代码，下一个问题：**该测什么？**

> **类比：考试复习。你不能只练简单题，还要练难题、练陷阱题。测试也一样——正常情况要测，极端情况要测，错误情况也要测。**

### ① 正常路径测试（正常题）

> **正常路径 = 用户按照你预期的方式正常使用，看结果对不对。**

就像考试里的基础题——输入合法数据，验证返回正确结果。

```python
def test_chat_normal():
    """测试正常对话：用户发一句普通的话"""
    response = client.post("/api/v1/chat", json={"message": "你好"})
    assert response.status_code == 200
    assert "response" in response.json()
```

这里我们检查了两件事：
1. 状态码是 200（请求成功了）
2. 返回的 JSON 里有 `response` 字段（AI 确实回复了）

还可以加更多"正常情况"：
```python
def test_chat_english():
    """测试英文对话"""
    response = client.post("/api/v1/chat", json={"message": "Hello"})
    assert response.status_code == 200

def test_chat_long_message():
    """测试较长的正常消息"""
    response = client.post("/api/v1/chat", json={"message": "请帮我写一首关于春天的诗，要求五言绝句"})
    assert response.status_code == 200
```

### ② 边界情况测试（难题）

> **边界情况 = 输入极端的数据，看程序能不能扛住。**

就像考试里的难题——不是不会做，而是容易忽略。

常见的边界情况：
- **空字符串**：用户什么都没输入
- **超长文本**：用户输入了一万字
- **特殊字符**：用户输入了 emoji、HTML 标签、SQL 语句

```python
def test_chat_empty_message():
    """测试空消息：用户发了个空的"""
    response = client.post("/api/v1/chat", json={"message": ""})
    # 如果你的接口对空字符串做了校验，应该返回 422
    assert response.status_code == 422

def test_chat_very_long_message():
    """测试超长消息：用户输入了 10000 个字符"""
    long_text = "a" * 10000
    response = client.post("/api/v1/chat", json={"message": long_text})
    # 看你的接口怎么处理——是正常返回，还是提示太长了
    assert response.status_code in [200, 422]
```

> **为什么要测边界？** 因为真实用户永远不会"按套路出牌"。你的 Agent 服务上线后，一定会有人发空消息、发超长文本、发奇怪的字符。提前测好，总比上线后崩了强。

### ③ 错误情况测试（陷阱题）

> **错误情况 = 输入非法的数据，看程序能不能正确地报错（而不是直接崩溃）。**

就像考试里的陷阱题——看你能不能识别出"这个条件是错的"。

```python
def test_chat_missing_field():
    """测试缺少必填字段：根本没传 message"""
    response = client.post("/api/v1/chat", json={})
    assert response.status_code == 422  # FastAPI 自动返回 422（参数校验失败）

def test_chat_wrong_type():
    """测试类型错误：message 应该是字符串，但传了个数字"""
    response = client.post("/api/v1/chat", json={"message": 12345})
    assert response.status_code == 422

def test_chat_invalid_format():
    """测试格式错误：发的不是 JSON，而是纯文本"""
    response = client.post("/api/v1/chat", data="not json")
    assert response.status_code == 422
```

> **关键点：好的程序不是"永远不出错"，而是"出错了也能优雅处理"。** 你的 Agent 服务收到非法请求时，应该返回一个清晰的错误信息（422 状态码），而不是直接崩溃（500 状态码）。

### ④ 三种测试的总结

| 类型 | 类比 | 测什么 | 期望结果 |
|------|------|--------|----------|
| 正常路径 | 基础题 | 合法输入 | 返回正确结果（200） |
| 边界情况 | 难题 | 极端输入 | 正常处理或合理拒绝 |
| 错误情况 | 陷阱题 | 非法输入 | 正确报错（422），不崩溃 |

## 知识点 15.4：测试覆盖

### ① 运行测试

当你写了多个测试文件，放在 `tests/` 文件夹下，一条命令就能全跑：

```bash
pytest tests/ -v
```

- `tests/`：测试文件所在的文件夹
- `-v`：显示详细信息（每个测试函数的名字和结果）

### ② 覆盖率报告

**覆盖率** = 你的测试"覆盖"了多少代码。

> 类比：你复习了课本 80% 的内容，那覆盖率就是 80%。剩下 20% 没复习到的，考试可能会考到。

```bash
pip install pytest-cov
pytest tests/ --cov=app --cov-report=html
```

这会生成一个 HTML 报告，告诉你哪些代码行被测试跑到了，哪些没有。没覆盖到的代码行，就是"可能藏有 Bug 的地方"。

## 知识点 15.5：Harness 架构视角分析

### ① 测试在 Harness 中的作用

Harness 架构强调系统的可控性和可观测性，测试在其中扮演四个关键角色：

- **边界控制**：测试验证系统的边界条件——Agent 收到超长上下文会不会崩溃？工具调用参数缺失会不会报错？这些都要通过测试来守住边界。

- **错误恢复**：测试确保错误处理正确——当大模型 API 超时、当数据库连接断开，Agent 是否能优雅降级而不是直接崩溃？

- **上下文管理**：测试验证上下文传递正确——多轮对话中，历史消息是否正确传递？上下文窗口满了之后，裁剪逻辑是否正确？

- **反馈回路**：测试提供持续的质量反馈——每次改完代码，跑一遍测试，几秒钟就知道有没有引入新 Bug。这就是 Harness 强调的"快速反馈循环"。

### ② Agent 项目中的测试重点

在 Agent/LLM 项目中，以下场景需要重点测试：

| 场景 | 测什么 | 为什么重要 |
|------|--------|------------|
| 工具调用 | 参数解析是否正确 | Agent 调错工具 = 灾难 |
| 上下文裁剪 | 超长对话是否正确截断 | 截断错误 = 丢失关键信息 |
| 错误重试 | API 失败后是否正确重试 | 大模型 API 经常不稳定 |
| 流式输出 | 逐字输出是否完整 | 丢字 = 用户体验差 |
| 权限控制 | 不同用户能否访问对应资源 | 安全底线 |

## 🤔 启发式思考题

1. **在 Agent 服务中，哪些场景需要重点测试？**
   > 提示：想想 Agent 可能出错的地方——工具调用失败、上下文丢失、大模型返回异常格式……

2. **如何测试流式输出接口？**
   > 提示：流式输出不是一次性返回结果，而是一块一块返回的。TestClient 能模拟这种场景吗？（提示：看看 `with client.stream()` 的用法）

3. **测试用例应该覆盖哪些边界条件？**
   > 提示：想想真实用户会做什么"奇怪"的事——发空消息、发超长文本、同时发多个请求、发特殊字符……

4. **如果你的 Agent 调用了外部 API（比如大模型接口），测试的时候怎么办？真的去调用吗？**
   > 提示：真调用又慢又花钱。了解"Mock（模拟）"的概念——用假数据代替真实 API 的返回。

## 📌 章节总结

### 知识点在 Agent 项目中的落地位置

| 测试类型 | Agent 项目中的应用 |
|----------|-------------------|
| **单元测试** | 测试独立功能：提示词格式化、工具参数解析、返回结果处理 |
| **集成测试** | 测试 API 接口：对话接口、工具调用接口、历史记录接口 |
| **端到端测试** | 测试完整流程：用户发消息 → Agent 思考 → 调用工具 → 返回结果 |

### 学习重心

| 内容 | 深度 | 理由 |
|------|------|------|
| TestClient 基本用法 | ⚠️ 必须掌握 | 所有 API 测试的基础 |
| `params` vs `json` | ⚠️ 必须掌握 | 搞混了就测不对接口 |
| `assert` 断言 | ⚠️ 必须掌握 | 测试的核心判断逻辑 |
| 测试用例设计（正常/边界/错误） | ⚠️ 适度了解 | 写出好测试的关键思维 |
| 异步测试 | 👀 了解即可 | 初学阶段用同步就够了 |
| Mock / Fixture 高级技术 | 👀 了解即可 | 后续深入测试时再学 |

### 哪些内容浅尝，哪些必须深挖

- **浅尝**：异步测试、Mock、Fixture、覆盖率配置——了解概念，需要时再查
- **深挖**：核心业务流程的测试用例设计——这决定了你的 Agent 上线后会不会"翻车"

> **记住：测试不是"写完了再说"，而是"边写边测"。养成写代码就写测试的习惯，你的代码质量会提升一个档次。**
