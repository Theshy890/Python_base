## 知识点 10.1：什么是中间件

### ① 先搞懂一个问题：为什么需要中间件？

想象你开了一家餐厅，客人（请求）从进门到坐下吃饭（路由处理），要经过好几道关卡：

1. **门口保安**：你是本店客人吗？（身份验证）
2. **安检门**：有没有带危险物品？（安全检查）
3. **前台登记**：记录一下谁来了、几点来的（日志记录）
4. **引导员**：带你到对应的座位（路由分发）

这些"关卡"有一个共同特点：**不管客人去哪个座位、点什么菜，每一道关卡都要走一遍**。

如果不用中间件，你就得在每个座位旁边都安排一个保安、一个安检、一个前台——这显然太蠢了。

**中间件就是这些"公共关卡"的集合**：写一次，所有请求都会自动经过。

### ② 正式定义

**中间件（Middleware）= 在请求到达路由处理函数之前、以及响应返回客户端之前，自动执行的一段代码。**

简单说：它是一个"检查站"，夹在客户端和你的路由之间。

### ③ 生活化类比：公司门禁系统

把 FastAPI 应用想象成一栋写字楼：

| 概念 | 类比 |
|------|------|
| **客户端发的请求** | 来上班的员工 |
| **中间件** | 大楼的门禁 + 安检 + 前台登记 |
| **路由处理函数** | 员工到了工位开始干活 |
| **返回的响应** | 员工干完活，带着成果离开大楼 |

不管员工去 3 楼财务部还是 5 楼技术部，他都必须：
1. 过门禁 → 过安检 → 前台登记 → 上楼干活
2. 干完活 → 下楼 → 前台签退 → 过安检 → 过门禁 → 离开

**中间件就是这些"每人都得经过"的公共流程。**

### ④ 中间件的执行顺序：洋葱模型

中间件不止一个，那它们按什么顺序执行呢？答案是：**像洋葱一样，一层一层包进去，再一层一层剥出来**。

假设有两个中间件：中间件A（日志记录）和中间件B（身份验证），执行顺序如下：

```
                    ┌─────────────────────────────────────┐
                    │           请求从外面进来              │
                    └──────────────┬──────────────────────┘
                                   ▼
                    ┌─────────────────────────────────────┐
                    │     中间件A：记录"有请求进来了"        │
                    │     (请求阶段：从外到内)               │
                    └──────────────┬──────────────────────┘
                                   ▼
                    ┌─────────────────────────────────────┐
                    │     中间件B：检查"这个请求合法吗？"     │
                    │     (请求阶段：从外到内)               │
                    └──────────────┬──────────────────────┘
                                   ▼
                    ┌─────────────────────────────────────┐
                    │          路由处理函数                  │
                    │       (真正干活的逻辑)                │
                    └──────────────┬──────────────────────┘
                                   ▼
                    ┌─────────────────────────────────────┐
                    │     中间件B：给响应盖上"已验证"的章     │
                    │     (响应阶段：从内到外)               │
                    └──────────────┬──────────────────────┘
                                   ▼
                    ┌─────────────────────────────────────┐
                    │     中间件A：记录"响应已发出"          │
                    │     (响应阶段：从内到外)               │
                    └──────────────┬──────────────────────┘
                                   ▼
                    ┌─────────────────────────────────────┐
                    │           响应返回给客户端             │
                    └─────────────────────────────────────┘
```

**关键规律**：
- **请求进来时**：从最外层中间件 → 逐层向内 → 到达路由
- **响应出去时**：从路由 → 逐层向外 → 到达最外层中间件 → 返回客户端

就像俄罗斯套娃：拆开（请求）是从外到内，合上（响应）是从内到外。

### ⑤ 一句话总结

> 中间件 = 每个请求和响应都要经过的"公共关卡"，在请求到达路由之前和响应返回客户端之前自动执行。

## 知识点 10.2：自定义中间件

### ① 先看完整代码，再逐行拆解

```python
from fastapi import FastAPI, Request
from fastapi.responses import JSONResponse

app = FastAPI()

@app.middleware("http")
async def custom_middleware(request: Request, call_next):
    """自定义中间件：给每个请求记录日志，并给响应添加自定义标记"""
    
    # === 请求进来时执行（路由处理之前）===
    print(f"有请求进来了：{request.method} {request.url.path}")
    
    # === 放行，让请求继续往下走 ===
    response = await call_next(request)
    
    # === 响应出去时执行（路由处理之后）===
    response.headers["X-Custom-Header"] = "agent-service"
    
    return response
```

### ② 逐行拆解：每个部分是什么意思？

**`@app.middleware("http")`** —— 注册中间件的"声明"

这行代码的意思是："我要注册一个 HTTP 中间件"。告诉 FastAPI："每次有 HTTP 请求进来，都要先经过这个函数。"

类比：你在公司门口贴了一张告示——"所有进大楼的人，都要先到保安室登记"。

**`request: Request`** —— 当前请求的所有信息

`request` 对象包含了客户端发来的**一切信息**：请求路径、请求方法（GET/POST）、请求头、请求体、客户端 IP……就像保安室的登记表，上面记录了来人的所有信息。

**`call_next`** —— "继续往下走"的指令

这是最关键的参数。调用 `await call_next(request)` 的意思是：
- "我这边检查完了，放行！让请求继续往下走。"
- 往下走到哪？走到下一个中间件，或者最终到达路由处理函数。
- 它会返回路由处理完毕后产生的 `response`（响应）。

类比：保安检查完身份证，对来访者说"请进"——这个"请进"就是 `call_next`。

**`response.headers["X-Custom-Header"] = "agent-service"`** —— 给响应"贴标签"

响应对象有一个 `headers` 属性（响应头），你可以在里面添加自定义信息。客户端收到响应时，能看到这些信息。

类比：员工离开大楼时，保安在他的出门条上盖了一个章："此请求已由 agent-service 处理"。

### ③ 执行流程再梳理

```
请求进来
  → custom_middleware 前半段（打印日志）
    → call_next 放行
      → 路由处理函数执行，生成 response
    ← call_next 拿到 response
  → custom_middleware 后半段（添加自定义响应头）
  → 返回 response 给客户端
```

### ④ 常用中间件场景

在 Agent/LLM 服务中，中间件特别适合做这些事情：

| 场景 | 说明 | 举例 |
|------|------|------|
| **日志记录** | 记录每个请求和响应 | "Agent收到了一次对话请求" |
| **请求追踪** | 给每个请求分配唯一ID | 方便追踪某个请求的完整链路 |
| **认证校验** | 全局检查API Key | 没带Key的请求直接拒绝 |
| **限流** | 限制请求频率 | 防止某个用户疯狂调用LLM接口 |
| **错误处理** | 统一捕获异常 | LLM调用失败时返回友好错误 |

## 知识点 10.3：请求追踪中间件

### ① 为什么需要请求追踪？

想象一下：你的 Agent 服务同时服务 100 个用户，突然有人投诉"我的对话回复出错了"。

你打开服务器日志，看到密密麻麻的日志记录：

```
收到请求 /api/v1/chat
收到请求 /api/v1/chat
收到请求 /api/v1/chat
处理完成，耗时 2.3s
处理出错：LLM超时
处理完成，耗时 1.1s
...（还有几千条）
```

问题来了：**你根本分不清哪条日志是哪个用户的请求产生的！**

这就好比医院里所有病人都叫"张三"，医生根本分不清谁是谁。你需要给每个请求一个"身份证号"——这就是请求追踪。

### ② uuid 是什么？

`uuid` 是 Python 标准库，用来生成一个**全球唯一的随机字符串**。

```python
import uuid
print(uuid.uuid4())  # 例如：a3b4c5d6-e7f8-9012-3456-789012345678
```

你可以把 uuid 想象成**身份证号**：
- 每个人的身份证号都不一样
- 每次调用 `uuid.uuid4()` 都会生成一个全新的、几乎不可能重复的字符串
- 用它来标识每个请求，就像给每个请求发了一张"身份证"

### ③ request.state 是什么？

`request.state` 是 FastAPI 提供的一个"贴标签"功能。你可以在请求对象上贴任何自定义标签，后续代码都能读到。

类比：你在快递包裹上贴了一张便签条，写着"加急件"。不管这个包裹经过多少个中转站，每个人都能看到这张便签。

### ④ 完整代码

```python
import uuid
from fastapi import FastAPI, Request

app = FastAPI()

@app.middleware("http")
async def request_id_middleware(request: Request, call_next):
    # 1. 生成一个唯一的请求ID（像给这个请求发一张身份证）
    request_id = str(uuid.uuid4())
    
    # 2. 把请求ID"贴"在请求对象上（后续的路由函数可以读到）
    request.state.request_id = request_id
    
    # 3. 放行，让请求继续往下走
    response = await call_next(request)
    
    # 4. 同时也在响应头里带上这个ID（客户端也能看到）
    response.headers["X-Request-ID"] = request_id
    
    return response

@app.get("/api/v1/chat")
async def chat(request: Request):
    # 通过 request.state 读取中间件"贴"上去的请求ID
    return {
        "message": "你好，我是AI助手",
        "request_id": request.state.request_id  # 返回请求ID给客户端
    }
```

### ⑤ 运行效果

```
GET /api/v1/chat
响应：
{
    "message": "你好，我是AI助手",
    "request_id": "a3b4c5d6-e7f8-9012-3456-789012345678"
}
响应头里也有：X-Request-ID: a3b4c5d6-e7f8-9012-3456-789012345678
```

现在日志里就能清楚地看到：`request_id=a3b4c5d6... 的请求处理出错`——精确定位问题！

## 知识点 10.4：限流中间件

### ① 为什么需要限流？

假设你的 Agent 服务背后调用的是 GPT-4，每次调用成本 0.1 元。如果有人写个脚本每秒发 100 个请求，你的账单会瞬间爆炸。

限流 = 给每个用户设置一个"额度"，比如每分钟最多 10 次请求，超了就先拒绝。

### ② 完整代码

```python
from fastapi import FastAPI, Request, HTTPException
from collections import defaultdict
import time

app = FastAPI()

# 记录每个IP的请求时间（用字典存储）
rate_limit = defaultdict(list)
MAX_REQUESTS = 10    # 最多允许 10 次请求
TIME_WINDOW = 60     # 在 60 秒的时间窗口内

@app.middleware("http")
async def rate_limit_middleware(request: Request, call_next):
    client_ip = request.client.host  # 获取客户端IP
    now = time.time()
    
    # 1. 清理过期的记录（只保留最近60秒内的请求时间）
    rate_limit[client_ip] = [t for t in rate_limit[client_ip] if now - t < TIME_WINDOW]
    
    # 2. 检查是否超限
    if len(rate_limit[client_ip]) >= MAX_REQUESTS:
        raise HTTPException(status_code=429, detail="请求过于频繁，请稍后再试")
    
    # 3. 记录本次请求时间
    rate_limit[client_ip].append(now)
    
    # 4. 放行
    response = await call_next(request)
    return response
```

## 知识点 10.5：CORS跨域

### ① 先搞懂"跨域"是什么

假设你做了两个网站：
- **网站A**：`http://my-frontend.com`（前端页面）
- **网站B**：`http://my-api.com`（后端API）

网站A的网页里有一段 JavaScript 代码，想调用网站B的接口获取数据。

**浏览器会直接拒绝这个请求！** 为什么？

### ② 生活化类比

想象你有一张工商银行的卡。你去建设银行的ATM机上插卡，想查余额——建设银行的ATM会告诉你："对不起，我们这里不受理工商银行的业务。"

**浏览器就是那个ATM机**。出于安全考虑，浏览器默认不允许一个网页去访问"不同来源"的服务器。这就是"同源策略"。

"同源"指的是三个东西完全一样：
- 协议（http vs https）
- 域名（example.com vs other.com）
- 端口（80 vs 8080）

只要有一个不一样，就是"跨域"，浏览器就会拦截。

### ③ CORS 是什么？

**CORS（Cross-Origin Resource Sharing，跨域资源共享）**= 一种机制，让服务器主动告诉浏览器："我允许这些网站来访问我。"

回到ATM的类比：如果建设银行和工商银行签了合作协议，建设银行的ATM就能受理工商银行的卡了。CORS 就是这个"合作协议"。

**注意**：跨域限制只存在于浏览器中。如果你用 Postman、curl、或者 Python 脚本直接发请求，完全不受限制。

### ④ FastAPI 中配置 CORS

```python
from fastapi import FastAPI
from fastapi.middleware.cors import CORSMiddleware

app = FastAPI()

# 定义"白名单"：这些地址允许访问我的服务器
origins = [
    "http://localhost:8080",       # 本地前端开发服务器
    "http://localhost:3000",       # 另一个本地前端
    "https://yourdomain.com"       # 线上域名
]

app.add_middleware(
    CORSMiddleware,                # 使用CORS中间件
    allow_origins=origins,         # 允许哪些"来源"访问？（白名单列表）
    allow_credentials=True,        # 允许携带Cookie等认证信息吗？
    allow_methods=["*"],           # 允许哪些HTTP方法？（*表示全部：GET/POST/PUT/DELETE等）
    allow_headers=["*"],           # 允许哪些请求头？（*表示全部）
)
```

### ⑤ 三个关键参数详解

| 参数 | 含义 | 类比 |
|------|------|------|
| **allow_origins** | 允许哪些网站访问我？ | "我允许工商银行和农业银行的卡在我这里用" |
| **allow_methods** | 允许哪些操作方式？ | "只允许查余额和转账，不允许修改密码" |
| **allow_headers** | 允许携带哪些自定义信息？ | "允许带身份证和手机号，不允许带其他东西" |

### ⑥ 生产环境配置（重要！）

```python
# 生产环境：只允许自己的域名，绝不能用 "*"
origins = [
    "https://yourdomain.com",
    "https://app.yourdomain.com"
]

app.add_middleware(
    CORSMiddleware,
    allow_origins=origins,                          # 精确指定允许的域名
    allow_credentials=True,
    allow_methods=["GET", "POST", "PUT", "DELETE"], # 只允许需要的HTTP方法
    allow_headers=["Content-Type", "Authorization"], # 只允许需要的请求头
)
```

**为什么生产环境不能用 `*`？** 因为 `*` 意味着全世界任何网站都能调用你的 API，恶意网站也能访问！

## 知识点 10.6：Harness架构视角分析

### ① 中间件在Harness中的作用

在 Harness 架构中，中间件扮演着"边界守卫"的角色：

- **边界控制**：全局限流、认证、安全检查——所有请求都必须先过"安检门"
- **错误恢复**：统一异常捕获和处理——即使内部出了问题，也能给客户端返回友好的错误信息，而不是直接崩溃
- **上下文管理**：请求级别的状态传递——通过 `request.state` 在整个请求生命周期中传递信息（如请求ID、用户身份等）
- **反馈回路**：日志记录、监控指标收集——让系统具备"自我观察"的能力，这是 Harness 闭环反馈的基础

### ② 补偿性代码 vs 系统性工程

| 方式 | 判断 | 说明 |
|------|------|------|
| 使用中间件统一处理 | ✅ 系统性工程 | 写一次，所有路由自动生效；逻辑集中，易于维护 |
| 在每个路由里单独处理 | ❌ 补偿性代码 | 每个路由都要复制粘贴相同的代码，改一处就要改几十处 |

**Harness 视角**：中间件是典型的"系统性工程"思维——把通用逻辑抽象到统一的层，而不是在每个业务节点上打补丁。这正是 Harness 架构强调的"用系统设计替代补偿性代码"。

## 📌 章节总结

### 知识点在Agent项目中的落地位置

- **全局日志**：记录所有请求和响应，方便排查问题
- **请求追踪**：给每个请求分配唯一ID，精确定位问题链路
- **限流控制**：防止API被滥用（尤其是调用LLM这种高成本操作）
- **CORS配置**：让前端能跨域访问后端API

### 学习重心

| 内容 | 深度 | 理由 |
|------|------|------|
| 自定义中间件 | ✅ 必须掌握 | 全局处理的核心机制，理解洋葱模型是关键 |
| 请求追踪 | ✅ 必须掌握 | 调试和监控的基础，生产环境必备 |
| 限流 | ✅ 必须掌握 | 防止API滥用，保护系统稳定性 |
| CORS配置 | ✅ 必须掌握 | 前端对接的必备，不理解CORS就无法联调 |

### 哪些内容浅尝，哪些必须深挖

- **浅尝**：中间件的高级特性（如 WebSocket 中间件、ASGI 中间件底层原理），了解即可
- **深挖**：全局异常处理和限流策略，这是保障系统稳定性的关键。在 Agent 项目中，LLM 调用可能很慢、可能失败，中间件的异常捕获和降级处理尤为重要
