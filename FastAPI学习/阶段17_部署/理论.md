## 知识点 17.1：部署基础

### 🏪 先讲个故事：从"自家厨房"到"正式开店"

想象一下，你学了一手好厨艺，在家做饭给家人吃，大家都说好吃。于是你决定开一家餐厅。

这时候你会发现，**"在家做饭"和"开餐厅"完全是两回事**：

| 在家做饭（开发环境） | 开餐厅（生产环境） |
|---|---|
| 只有自己人吃 | 所有顾客都能来 |
| 想改菜谱随时改 | 改菜谱要谨慎，顾客正吃着呢 |
| 厨房乱一点没关系 | 必须整洁、安全、规范 |
| 停电了重新做就行 | 停电了顾客会投诉、给差评 |
| 不用考虑卫生许可 | 必须通过各项检查 |

**部署**，就是把你在"自家厨房"里开发好的程序，搬到"正式餐厅"里，让所有人都能使用。

> **一句话总结：开发 = 装修准备，部署 = 正式开业。**

### ① 什么是开发环境 vs 生产环境

| | 开发环境 | 生产环境 |
|---|---|---|
| **用途** | 你自己写代码、调试、测试 | 真实用户在使用 |
| **用户** | 只有你一个人 | 全世界的人 |
| **出错代价** | 无所谓，重启就好 | 用户数据丢失、服务宕机、亏钱 |
| **性能要求** | 能跑就行 | 要快、要稳、要能扛住大量请求 |
| **安全性** | 随便搞 | 必须严格保护 |

### ② 部署方式对比

| 方式 | 说明 | 类比 | 适用场景 |
|------|------|------|----------|
| **直接运行** | `python main.py` | 在家做饭自己吃 | 开发测试 |
| **Uvicorn** | `uvicorn main:app` | 开了一个小窗口接客 | 生产环境（基础） |
| **Gunicorn + Uvicorn** | 多进程部署 | 开了多个窗口同时接客 | 高并发 |
| **Docker** | 容器化部署 | 把整个厨房打包搬走 | 标准化环境 |
| **云服务** | 托管服务 | 租一个现成的商铺 | 快速上线 |

### ③ 面向Agent/LLM场景的例子

假设你开发了一个AI助手服务，在本地跑得好好的：

```python
# main.py - 你的AI助手
from fastapi import FastAPI

app = FastAPI()

@app.post("/chat")
async def chat(message: str):
    # 调用LLM处理用户消息
    response = await call_llm(message)
    return {"reply": response}
```

现在你想让朋友们也能用这个AI助手——这就需要**部署**到服务器上，让大家都可以通过网络访问它。

## 知识点 17.2：Uvicorn部署

### 🍜 先理解：Uvicorn是什么？

还记得**阶段1**学过的ASGI吗？

> **ASGI = 异步网关接口**，它是"Python异步Web框架"和"网络"之间的桥梁。

FastAPI就是一个ASGI框架，但FastAPI本身**不能直接运行**——它需要一个"老板"来启动它、管理它。

**Uvicorn就是这个"老板"**——它是一个ASGI服务器，负责：
- 启动你的FastAPI应用
- 监听网络请求
- 把请求转交给FastAPI处理
- 把处理结果返回给用户

> **类比：FastAPI是厨师，Uvicorn是餐厅经理。厨师负责做菜（处理请求），经理负责开门营业、接待客人（监听端口、管理连接）。**

### ① 开发时用的命令

```bash
uvicorn main:app --host 127.0.0.1 --port 8000 --reload
```

逐部分解释：

| 部分 | 含义 |
|---|---|
| `main:app` | `main.py`文件里的`app`对象（就是你的FastAPI实例） |
| `--host 127.0.0.1` | 只允许本机访问（自己用） |
| `--port 8000` | 在8000端口上监听 |
| `--reload` | 代码一改就自动重启（开发方便） |

### ② 生产环境用的命令

```bash
uvicorn main:app \
    --host 0.0.0.0 \
    --port 8000 \
    --workers 4
```

这里有两个关键变化，我们一个一个讲：

#### 🔓 `--host 0.0.0.0` 是什么意思？

- `127.0.0.1` = 只允许"自己"访问（就像只允许你自己进房间）
- `0.0.0.0` = 允许**任何IP**访问（就像把门打开，谁来都接待）

> **生产环境必须用 `0.0.0.0`**，否则外部用户根本访问不到你的服务。

#### 👷 `--workers 4` 是什么意思？

想象一个奶茶店：
- 1个worker = 1个店员，同时只能做1杯奶茶
- 4个workers = 4个店员，可以同时做4杯奶茶

`--workers 4` 就是启动4个进程，**同时处理4个用户的请求**，大大提升并发能力。

> **类比：workers就像银行窗口。1个窗口排长队，4个窗口同时办理，速度快4倍。**

#### 🚫 为什么生产环境不用 `--reload`？

`--reload` 会不断监控文件变化，一旦代码修改就自动重启。这在开发时很方便，但在生产环境有两个大问题：

1. **消耗性能**：要持续监控文件，浪费CPU资源
2. **不安全**：如果有人在服务器上改了代码，服务会自动重启加载恶意代码

> **类比：开发时的 `--reload` 就像"边营业边装修"，随时改随时生效。生产环境不能这样——你不能在餐厅营业的时候突然拆墙。**

### ③ Gunicorn + Uvicorn（更强大的部署方式）

当你的AI助手用户量很大时，可以用Gunicorn来管理多个Uvicorn进程：

```python
# gunicorn.conf.py - 配置文件
workers = 4                    # 4个worker进程
worker_class = "uvicorn.workers.UvicornWorker"  # 每个worker用uvicorn
bind = "0.0.0.0:8000"         # 监听地址
timeout = 120                  # 超时时间（LLM调用可能比较慢）
```

运行：
```bash
gunicorn main:app -c gunicorn.conf.py
```

> **Gunicorn就像一个"总经理"，管理着多个Uvicorn"分店经理"，每个经理手下有自己的worker。**

## 知识点 17.3：Docker部署

### 📦 先讲个故事：搬家的烦恼

假设你要搬家，你有一台电脑，电脑上装了你需要的：
- 操作系统（Windows）
- Python 3.11
- 各种依赖包
- 你的代码
- 配置文件

如果直接搬到新电脑上，你会发现：
- 新电脑可能没有Python
- 依赖包版本不对
- 配置文件路径不一样
- 各种"在我电脑上能跑"的问题

**Docker就是来解决这个问题的。**

> **Docker = 一个"集装箱"，把你的程序 + 它需要的所有环境（Python、依赖、配置）全部打包在一起，搬到任何电脑上都能直接运行。**

类比：
- **没有Docker** = 搬家时只搬家具，到了新家发现插座不对、水管不接
- **有Docker** = 把整个房间（包括插座、水管、家具）打包成一个箱子，到哪打开就能用

### ① Dockerfile —— 打包的"说明书"

Dockerfile就是告诉Docker"怎么打包"的说明书。我们逐行来看：

```dockerfile
# 第1行：选择"基础集装箱"
# 就像一个空的房间，已经装好了Python 3.11
FROM python:3.11-slim

# 第2行：设置"工作目录"
# 就像在房间里划定一个区域作为你的工作区
WORKDIR /app

# 第3行：先把"购物清单"（依赖列表）复制进去
# 为什么不直接复制所有文件？因为依赖不常变，这样可以用缓存加速
COPY requirements.txt .

# 第4行：按照购物清单安装依赖
# --no-cache-dir 表示不保留安装包时的缓存，减小体积
RUN pip install --no-cache-dir -r requirements.txt

# 第5行：把剩下的所有文件（你的代码）都复制进去
COPY . .

# 第6行：告诉Docker，启动时要运行什么命令
# 就像在门上贴个纸条："开门后请执行这个操作"
CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]
```

> **Dockerfile就像一份菜谱：先准备锅（FROM），再准备食材（COPY），然后按步骤烹饪（RUN），最后告诉厨师怎么上菜（CMD）。**

### ② docker-compose.yml —— 管理"一整套设备"

一个AI助手服务通常不只有一个程序，而是有多个组件：
- Web服务（你的FastAPI应用）
- 数据库（存储对话历史）
- Redis（缓存）
- 消息队列

**docker-compose就是用来同时管理这些组件的。**

> **类比：Docker是管理单个集装箱，docker-compose是管理一整个港口——所有集装箱的调度、连接、配置都归它管。**

```yaml
version: "3.8"

services:
  # Web服务（你的AI助手）
  web:
    build: .                    # 用当前目录的Dockerfile构建
    ports:
      - "8000:8000"             # 把容器的8000端口映射到宿主机的8000端口
    environment:
      - API_KEY=your-secret-key # 传入环境变量（后面会讲）
    volumes:
      - .:/app                  # 把当前目录挂载到容器的/app目录

  # 数据库服务（存储对话历史）
  db:
    image: postgres:15          # 使用PostgreSQL镜像
    environment:
      - POSTGRES_PASSWORD=secret
    volumes:
      - db_data:/var/lib/postgresql/data

volumes:
  db_data:                      # 定义数据卷，数据持久化
```

### ③ 构建和运行

```bash
# 构建并启动所有服务
docker-compose up --build

# 后台运行
docker-compose up -d

# 查看运行状态
docker-compose ps

# 停止所有服务
docker-compose down
```

### ④ 面向Agent/LLM场景的完整示例

```dockerfile
# Dockerfile - 部署一个AI Agent服务
FROM python:3.11-slim

WORKDIR /app

# 先安装依赖（利用Docker缓存）
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

# 复制代码
COPY . .

# 暴露端口
EXPOSE 8000

# 启动命令
CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000", "--workers", "2"]
```

## 知识点 17.4：环境变量

### 🏪 先讲个故事：连锁店的配置问题

假设你开了一家奶茶连锁店，有3家分店：

| 配置项 | 北京分店 | 上海分店 | 广州分店 |
|---|---|---|---|
| 营业时间 | 8:00-22:00 | 9:00-23:00 | 10:00-24:00 |
| 配送范围 | 5公里 | 3公里 | 8公里 |
| 店长电话 | 138xxxx | 139xxxx | 137xxxx |

你会怎么做？
- ❌ **错误做法**：把配置写死在代码里（硬编码），每家店改一次代码
- ✅ **正确做法**：配置和代码分离，每家店用自己的配置文件

**环境变量就是这个"配置文件"。**

> **环境变量 = 程序的"外部配置"，程序运行时从环境中读取配置，而不是写死在代码里。**

### ① 为什么生产环境要用环境变量？

| 原因 | 说明 |
|---|---|
| **不同环境配置不同** | 开发、测试、生产环境的数据库地址、密钥都不一样 |
| **安全性** | 密钥不能写在代码里提交到Git |
| **灵活性** | 不改代码就能修改配置 |
| **标准化** | 12-Factor App的最佳实践 |

### ② 生产环境配置文件

```bash
# .env.prod - 生产环境配置
API_KEY=sk-prod-xxxxx          # LLM的API密钥
MAX_TOKENS=4096                 # 最大token数
DATABASE_URL=postgresql://user:pass@db:5432/app  # 数据库连接
LLM_BASE_URL=https://api.openai.com/v1  # LLM接口地址
```

### ③ 在代码中使用环境变量

```python
from pydantic_settings import BaseSettings

class Settings(BaseSettings):
    api_key: str                          # 必须提供，否则报错
    max_tokens: int = 1024                # 有默认值，可以不配
    database_url: str
    llm_base_url: str = "https://api.openai.com/v1"
    
    class Config:
        env_file = ".env.prod"            # 从配置文件读取

settings = Settings()

# 使用配置
@app.post("/chat")
async def chat(message: str):
    # 从环境变量获取API密钥，而不是写死
    response = await call_llm(
        message=message,
        api_key=settings.api_key,
        max_tokens=settings.max_tokens,
        base_url=settings.llm_base_url
    )
    return {"reply": response}
```

> **注意：`.env` 文件绝对不能提交到Git！要加到 `.gitignore` 里。**

## 知识点 17.5：安全配置

### 📮 先讲个故事：明信片和信封

想象你要给朋友寄一封信：

| 方式 | 类比 | 安全性 |
|---|---|---|
| **HTTP** | 寄明信片 | 邮递员、路人谁都能看内容 |
| **HTTPS** | 寄密封信封 | 只有收件人能打开看 |

> **HTTPS = HTTP + 加密**。它会在数据传输前进行加密，即使被截获，别人也看不懂内容。

对于AI助手来说，用户发送的消息可能包含敏感信息（密码、个人隐私），必须用HTTPS加密。

### ① HTTPS配置

```bash
# 使用Let's Encrypt免费获取SSL证书
certbot --nginx -d example.com
```

### ② TrustedHostMiddleware —— 防止"假域名"攻击

**什么是Host头攻击？**

HTTP请求里有一个`Host`头，告诉服务器"我是从哪个域名来的"。

攻击者可以伪造这个头：
```
GET /chat HTTP/1.1
Host: evil.com    # 伪造的域名
```

如果你的服务没有校验，攻击者就可以：
- 用假域名访问你的服务
- 进行钓鱼攻击
- 绕过某些安全限制

**TrustedHostMiddleware就是"门卫"，只允许白名单里的域名访问：**

```python
from fastapi.middleware.trustedhost import TrustedHostMiddleware

# 只允许这些域名访问
app.add_middleware(
    TrustedHostMiddleware, 
    allowed_hosts=["example.com", "www.example.com"]
)
```

> **类比：TrustedHostMiddleware就像小区门禁，只有登记的业主（白名单域名）才能进入，陌生人（伪造域名）一律拦下。**

### ③ 防火墙配置

```bash
# 只允许HTTP(80)和HTTPS(443)端口
ufw allow 80/tcp     # HTTP
ufw allow 443/tcp    # HTTPS
ufw enable           # 启用防火墙
```

> **防火墙就像城堡的护城河，只留几个吊桥（端口）让合法的人通过，其他全部封死。**

### ④ 面向Agent/LLM场景的安全配置

```python
from fastapi import FastAPI
from fastapi.middleware.trustedhost import TrustedHostMiddleware
from fastapi.middleware.cors import CORSMiddleware

app = FastAPI()

# 1. 只允许信任的域名访问
app.add_middleware(
    TrustedHostMiddleware,
    allowed_hosts=["my-ai-app.com"]
)

# 2. 配置CORS（跨域资源共享）
app.add_middleware(
    CORSMiddleware,
    allow_origins=["https://my-ai-app.com"],  # 只允许自己的前端
    allow_methods=["POST"],                    # 只允许POST（AI助手只需要POST）
    allow_headers=["Authorization"],           # 只允许认证头
)

# 3. 限流（防止被恶意刷接口，LLM调用很贵！）
from slowapi import Limiter
from slowapi.util import get_remote_address

limiter = Limiter(key_func=get_remote_address)
app.state.limiter = limiter

@app.post("/chat")
@limiter.limit("10/minute")  # 每分钟最多10次请求
async def chat(request: Request, message: str):
    response = await call_llm(message)
    return {"reply": response}
```

## 知识点 17.6：监控和日志

### 📹 先讲个故事：店铺的摄像头和报警器

你开了一家24小时无人便利店，你怎么知道：
- 店铺是否正常营业？（有没有停电、断网）
- 有没有人进来买东西？（有多少用户）
- 有没有人偷东西？（有没有异常请求）
- 货架是不是空了？（资源是否充足）

你需要：**摄像头 + 报警器 + 仪表盘**

**监控和日志就是程序的"摄像头+报警器"。**

> **监控 = 实时观察程序运行状态**
> **日志 = 记录程序做过的事情（像日记本）**

### ① 健康检查 —— "我还活着"的信号

健康检查就是一个简单的接口，让监控系统知道"服务是否正常"：

```python
@app.get("/health")
async def health_check():
    # 可以检查数据库连接、LLM服务是否可用
    db_ok = await check_database()
    llm_ok = await check_llm_service()
    
    if db_ok and llm_ok:
        return {"status": "healthy", "components": {"db": "ok", "llm": "ok"}}
    else:
        return {"status": "unhealthy", "components": {"db": db_ok, "llm": llm_ok}}
```

> **健康检查就像每天早上开店前，店长检查：灯亮了吗？收银机能用吗？库存够吗？全部OK才能开门营业。**

在生产环境中，Docker、Kubernetes等工具会定期调用这个接口，如果返回异常，就会自动重启服务或报警。

### ② 日志配置 —— 程序的"日记本"

```python
import logging

# 配置日志
logging.basicConfig(
    level=logging.INFO,                    # 记录INFO级别以上的日志
    format="%(asctime)s - %(name)s - %(levelname)s - %(message)s",
    handlers=[
        logging.FileHandler("app.log"),    # 写入文件（持久保存）
        logging.StreamHandler()            # 输出到控制台（实时查看）
    ]
)

logger = logging.getLogger(__name__)

# 在代码中使用
@app.post("/chat")
async def chat(message: str):
    logger.info(f"收到用户消息: {message[:50]}...")  # 记录请求
    
    try:
        response = await call_llm(message)
        logger.info(f"LLM响应成功，长度: {len(response)}")
        return {"reply": response}
    except Exception as e:
        logger.error(f"LLM调用失败: {e}")  # 记录错误
        raise
```

### ③ 监控工具

| 工具 | 作用 | 类比 |
|------|------|------|
| **Prometheus** | 收集指标（请求数、错误率、响应时间） | 摄像头，记录所有数据 |
| **Grafana** | 可视化仪表盘（图表展示） | 监控大屏，一目了然 |
| **Sentry** | 错误追踪（自动捕获异常） | 报警器，出错立刻通知 |

### ④ 面向Agent/LLM场景的监控

```python
import time
from prometheus_client import Counter, Histogram

# 定义指标
REQUEST_COUNT = Counter('llm_request_total', 'Total LLM requests', ['status'])
REQUEST_DURATION = Histogram('llm_request_duration_seconds', 'LLM request duration')
TOKEN_USAGE = Counter('llm_token_usage_total', 'Total tokens used', ['type'])

@app.post("/chat")
async def chat(message: str):
    start_time = time.time()
    
    try:
        response = await call_llm(message)
        
        # 记录成功请求
        REQUEST_COUNT.labels(status='success').inc()
        # 记录token使用量
        TOKEN_USAGE.labels(type='input').inc(len(message))
        TOKEN_USAGE.labels(type='output').inc(len(response))
        
        return {"reply": response}
    except Exception as e:
        # 记录失败请求
        REQUEST_COUNT.labels(status='error').inc()
        raise
    finally:
        # 记录请求耗时
        duration = time.time() - start_time
        REQUEST_DURATION.observe(duration)
```

> **对于LLM应用来说，监控特别重要，因为：**
> - LLM调用很贵，需要监控token消耗
> - LLM响应慢，需要监控延迟
> - LLM可能出错，需要监控错误率

## 知识点 17.7：Harness架构视角分析

### ① 部署在Harness中的作用

Harness架构强调**边界控制、错误恢复、上下文管理、反馈回路**，部署阶段完美体现了这些原则：

| Harness原则 | 在部署中的体现 | 具体做法 |
|---|---|---|
| **边界控制** | 环境隔离和安全配置 | 环境变量、防火墙、TrustedHostMiddleware |
| **错误恢复** | 监控和日志便于问题排查 | 健康检查、日志系统、Sentry错误追踪 |
| **上下文管理** | 配置管理和状态持久化 | Docker数据卷、环境变量、数据库 |
| **反馈回路** | 监控指标提供运行状态反馈 | Prometheus指标、Grafana仪表盘 |

### ② 从Harness角度看AI Agent部署


## 📌 章节总结

### 知识点在Agent项目中的落地位置

| 知识点 | 在AI Agent项目中的作用 |
|---|---|
| **环境配置** | 管理API密钥、数据库地址、LLM参数等敏感配置 |
| **容器化** | 保证"开发-测试-生产"环境一致，方便部署和扩展 |
| **安全防护** | 保护API密钥不泄露，防止恶意刷接口（LLM调用很贵！） |
| **监控运维** | 监控token消耗、响应延迟、错误率，及时发现问题 |

### 学习重心

| 内容 | 深度 | 理由 |
|------|------|------|
| Uvicorn部署 | ⚠️ 适度了解 | 生产环境基础，知道怎么启动服务、配置worker |
| Docker部署 | ⚠️ 适度了解 | 标准化部署，会写Dockerfile、用docker-compose |
| 环境变量 | 🔴 必须掌握 | 安全管理API密钥，每个项目都要用 |
| 安全配置 | 🔴 必须掌握 | LLM应用成本高，必须做好防护 |
| 监控日志 | ⚠️ 适度了解 | 排查问题的关键，知道怎么配置日志、健康检查 |

### 哪些内容浅尝，哪些必须深挖

- **浅尝**：复杂的DevOps流程（如CI/CD、Kubernetes编排），了解基本概念即可
- **深挖**：环境配置（环境变量）和安全防护（HTTPS、限流），这是保障生产环境稳定的关键
- **特别关注**：对于LLM应用，要特别关注**成本控制**（token监控）和**安全防护**（API密钥保护、调用限流）
