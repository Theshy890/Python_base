## 知识点 8.1：数据库选择

### 🏠 先搞清楚：什么是数据库？

想象一下你用手机拍了一张照片——这张照片存在手机里，关机重启后还在。为什么？因为照片被**持久化保存**了。

程序里的变量也是一样。你在 Python 里定义了一个列表 `users = ["Alice", "Bob"]`，程序一关，这些数据就全没了。就像你在白板上写的字，一擦就没了。

**数据库 = 一个长期存储数据的"仓库"**，程序关闭后数据不会丢失。

你可以把数据库想象成一个超级强大的 Excel：
- 可以存很多很多数据（百万、千万条）
- 可以快速查找、排序、筛选
- 多个程序可以同时访问它
- 数据存进去就不会丢

---

### 📊 关系型 vs 非关系型：两种不同的"仓库"

#### 关系型数据库 = Excel 表格

关系型数据库（如 SQLite、PostgreSQL、MySQL）就像 Excel 表格：

```
┌────┬────────┬──────────────┐
│ id │  名字  │    邮箱       │
├────┼────────┼──────────────┤
│  1 │ Alice  │ alice@qq.com │
│  2 │ Bob    │ bob@qq.com   │
│  3 │ Carol  │ carol@qq.com │
└────┴────────┴──────────────┘
```

- 数据一行一行整齐排列，每行有固定的列
- 表与表之间可以建立"关系"（比如"用户表"和"订单表"通过用户ID关联）
- 用 **SQL 语言** 来操作（比如 `SELECT * FROM users WHERE name='Alice'`）
- **适合**：数据结构明确、需要严格管理的场景

#### 非关系型数据库 = 文件夹

非关系型数据库（如 MongoDB、Redis）就像往文件夹里塞文件：

```
📁 用户资料/
   ├── 📄 alice.json  → {"name": "Alice", "age": 25, "hobbies": ["读书", "游泳"]}
   ├── 📄 bob.json    → {"name": "Bob", "age": 30, "hobbies": ["编程"]}
   └── 📄 carol.json  → {"name": "Carol", "age": 28}
```

- 每条数据可以长得不一样（Alice 有 hobbies，Carol 没有，也没关系）
- 不需要提前定义"表格结构"
- **适合**：数据结构灵活多变的场景

#### 对比总结

| | 关系型（Excel表格） | 非关系型（文件夹） |
|---|---|---|
| 数据结构 | 严格，每行格式相同 | 灵活，每条可以不同 |
| 查询方式 | SQL 语句 | 各自的查询方式 |
| 代表 | SQLite、PostgreSQL、MySQL | MongoDB、Redis |
| 类比 | 银行柜台（每笔业务都有固定表格） | 记事本（想记什么记什么） |

---

### 🧠 为什么 AI 项目常用向量数据库？

假设你有一个 AI 助手，用户问："怎么学 Python？"

你不想让它死板地回答，而是想让它参考之前整理好的学习资料。但问题来了——怎么找到**语义相关**的资料？用关键词搜索？那"如何入门Python"和"怎么学Python"关键词不同，但意思一样啊。

**向量数据库**就是解决这个问题的。它的工作方式：

1. 把每段文字转化成一串数字（比如 `[0.12, 0.85, 0.33, ...]`），这叫"向量"
2. 意思相近的文字，转化出来的数字也相近
3. 搜索时，把问题也转化成数字，找最接近的那些

可以理解为：向量数据库存储的是文本的**"语义指纹"**。就像每个人有独特的指纹，每段话也有独特的"意思指纹"。通过比较指纹的相似度，就能找到意思相近的内容。

这在 AI 领域叫做 **RAG（检索增强生成）**——先从知识库里搜出相关内容，再让 AI 基于这些内容回答。

---

### 📋 AI 项目常用数据库一览

| 数据库 | 类型 | 适用场景 | 生活类比 |
|--------|------|----------|----------|
| **SQLite** | 关系型 | 开发测试、轻量级应用 | 随身小笔记本 |
| **PostgreSQL** | 关系型 | 生产环境、复杂查询 | 大型档案柜 |
| **MySQL** | 关系型 | 高并发、读写分离 | 银行数据库 |
| **MongoDB** | 文档型 | 非结构化数据、灵活schema | 活页文件夹 |
| **Redis** | 缓存 | 会话管理、热点数据 | 便签纸（快速查看） |
| **Chroma** | 向量数据库 | 向量检索、RAG | 语义搜索引擎 |

> 💡 **新手建议**：学习阶段用 SQLite 就够了，它不需要安装任何服务器软件，一个文件就是一个数据库。

## 知识点 8.2：SQLAlchemy 基础

### 🌐 先搞清楚：什么是 ORM？

上一节说了，关系型数据库用 **SQL 语言**来操作。比如要查一个叫 Alice 的用户：

```sql
SELECT * FROM users WHERE name = 'Alice';
```

这意味着你得学一套新的语法（SQL），而且在 Python 代码里混着 SQL 字符串，写起来很别扭。

**ORM = 翻译官**

ORM（Object-Relational Mapping，对象关系映射）就像一个翻译官：
- 你用 **Python 代码** 告诉它你想干什么
- 它帮你**翻译**成数据库能听懂的 SQL 语句
- 然后把数据库的返回结果**翻译**回 Python 对象

```
你（Python代码）  →  ORM翻译官  →  数据库（SQL）
                    ↓
你（Python对象）  ←  ORM翻译官  ←  数据库（查询结果）
```

有了 ORM，你不需要写 SQL 语句，全程用 Python 代码就能操作数据库：

```python
# 不用ORM：你要写SQL字符串
db.execute("SELECT * FROM users WHERE name = 'Alice'")

# 用了ORM：你写Python代码，ORM帮你翻译
db.query(User).filter(User.name == 'Alice').first()
```

---

### 🔌 Engine：数据库的"连接器"

要操作数据库，首先得**连上**它。就像你要打电话给朋友，得先拨号、等对方接听。

**Engine（引擎）= 数据库的连接器**

它负责：
- 知道数据库在哪里（地址）
- 管理连接池（可以同时开多个"通话"）
- 把你要做的操作发送给数据库

```python
from sqlalchemy import create_engine

# 创建连接器——告诉程序数据库在哪里
# 这里的 "sqlite:///./test.db" 意思是：在当前文件夹下创建一个叫 test.db 的SQLite数据库文件
engine = create_engine("sqlite:///./test.db", connect_args={"check_same_thread": False})
```

> 💡 `check_same_thread=False` 是 SQLite 的特殊要求，因为 SQLite 比较"小气"，默认只允许一个线程访问。FastAPI 是多线程的，所以需要关掉这个限制。

---

### 💬 Session：和数据库的一次"对话"

连上数据库后，你需要开始一次"对话"来执行具体操作。

**Session（会话）= 和数据库的一次对话**

类比：
- Engine 像是你拨通了朋友的电话
- Session 像是你们正在聊的这一通电话
- 电话接通后，你可以问问题（查询）、告诉对方事情（插入/更新）、让对方删掉什么（删除）
- 聊完了要挂电话（关闭 Session）

```python
from sqlalchemy.orm import sessionmaker

# 创建一个"拨号器"，每次调用就能开始一次新对话
SessionLocal = sessionmaker(autocommit=False, autoflush=False, bind=engine)

# 开始一次对话
db = SessionLocal()

# ... 在这期间执行各种操作 ...

# 挂电话
db.close()
```

> 💡 `autocommit=False` 意思是：操作不会自动"确认"，需要你手动确认（后面会讲为什么）。
> 💡 `autoflush=False` 意思是：不会自动把暂存的操作发给数据库。

---

### 📐 Base 和 declarative_base：定义表格的"模板"

数据库里存数据需要表格（表）。但我们是 Python 程序员，不想手写 SQL 的 `CREATE TABLE` 语句。

**Base = 定义表格的模板**

通过继承 Base，你可以用 Python 类来定义数据库表格：

```python
from sqlalchemy import Column, Integer, String
from sqlalchemy.ext.declarative import declarative_base

# 创建模板
Base = declarative_base()

# 用模板定义一个"用户表"
class User(Base):
    __tablename__ = "users"          # 表格名叫 users
    
    id = Column(Integer, primary_key=True)    # id列，整数类型，主键（唯一标识）
    name = Column(String)                     # name列，字符串类型
    email = Column(String, unique=True)       # email列，字符串类型，不能重复
```

这段 Python 代码"翻译"成 SQL 就是：
```sql
CREATE TABLE users (
    id INTEGER PRIMARY KEY,
    name VARCHAR,
    email VARCHAR UNIQUE
);
```

ORM 帮你完成了这个翻译！你只需要写 Python 类，ORM 自动帮你建表。

```python
# 一行代码，让ORM根据你定义的所有类自动创建表格
Base.metadata.create_all(bind=engine)
```

### 🔄 同步 vs 异步连接

想象你去餐厅点餐：

- **同步** = 你点完餐，站在柜台等着，服务员做好菜端给你，你才能离开。整个过程你一直在等。
- **异步** = 你点完餐拿到一个号码牌，可以去找座位、看手机、做别的事。菜做好了会叫你的号。

```python
# ===== 同步连接（站在柜台等） =====
from sqlalchemy import create_engine

engine = create_engine("sqlite:///./test.db")
# 每次操作数据库时，程序会"卡住"等结果返回

# ===== 异步连接（拿号码牌，不阻塞） =====
from sqlalchemy.ext.asyncio import create_async_engine

engine = create_async_engine("sqlite+aiosqlite:///./test.db")
# 操作数据库时，程序可以去干别的事，结果好了再继续处理
```

| | 同步 | 异步 |
|---|---|---|
| 类比 | 排队等餐 | 拿号等餐 |
| 代码复杂度 | 简单 | 需要 `async/await` |
| 性能 | 一个请求占一个线程 | 一个线程可以处理多个请求 |
| 适用场景 | 学习、简单项目 | 高并发的生产环境 |

> 💡 FastAPI 天然支持异步，所以生产环境推荐用异步连接。学习阶段用同步更简单。

---

### 📝 完整示例：同步连接 + 定义表格

```python
from sqlalchemy import create_engine, Column, Integer, String
from sqlalchemy.ext.declarative import declarative_base
from sqlalchemy.orm import sessionmaker

# 第1步：创建连接器（拨通电话）
SQLALCHEMY_DATABASE_URL = "sqlite:///./test.db"
engine = create_engine(SQLALCHEMY_DATABASE_URL, connect_args={"check_same_thread": False})

# 第2步：创建拨号器（每次调用开始一次新对话）
SessionLocal = sessionmaker(autocommit=False, autoflush=False, bind=engine)

# 第3步：创建表格模板
Base = declarative_base()

# 第4步：用模板定义表格（定义一张"用户表"）
class User(Base):
    __tablename__ = "users"
    id = Column(Integer, primary_key=True)
    name = Column(String)
    email = Column(String, unique=True)

# 第5步：根据模板自动建表
Base.metadata.create_all(bind=engine)
```

### 📝 完整示例：异步连接

```python
from sqlalchemy.ext.asyncio import create_async_engine, AsyncSession
from sqlalchemy.orm import sessionmaker

# 注意URL格式变了：sqlite+aiosqlite（需要额外安装 aiosqlite 包）
SQLALCHEMY_DATABASE_URL = "sqlite+aiosqlite:///./test.db"

# 创建异步连接器
engine = create_async_engine(SQLALCHEMY_DATABASE_URL)

# 创建异步"拨号器"
AsyncSessionLocal = sessionmaker(engine, class_=AsyncSession, expire_on_commit=False)
```

## 知识点 8.3：数据库操作

### 📦 CRUD：数据库的四种基本操作

CRUD 是四个英文单词的首字母缩写，是所有数据库操作的基础：

| 字母 | 英文 | 中文 | 生活类比 | 例子 |
|------|------|------|----------|------|
| **C** | Create | 创建 | 在通讯录里**新增**一个联系人 | 注册新用户 |
| **R** | Read | 读取 | **查看**通讯录里的某个联系人 | 查看用户信息 |
| **U** | Update | 更新 | **修改**通讯录里联系人的电话号码 | 修改用户昵称 |
| **D** | Delete | 删除 | **删掉**通讯录里的一个联系人 | 注销用户 |

---

### 🔑 三个关键动作：add、commit、refresh

在 ORM 里创建一条新数据，需要三步。用**网购**来类比：

```python
# 第1步：db.add(user)  →  把商品放进购物车
db.add(user)

# 第2步：db.commit()   →  点击"确认下单"
db.commit()

# 第3步：db.refresh(user)  →  刷新页面，看到订单号等系统生成的信息
db.refresh(user)
```

#### `db.add(user)` —— 放进购物车

你创建了一个 User 对象，但数据库还不知道它的存在。`add()` 就是告诉 Session："嘿，这个对象等会儿要存进数据库。"

此时只是"暂存"，还没有真正写入数据库。就像你把商品放进了购物车，但还没付款。

#### `db.commit()` —— 确认下单

**为什么需要 commit？**

想象银行转账：你给朋友转 1000 块。银行不会在你点"转账"的瞬间就把钱转走，而是先让你确认——输入密码、短信验证——最后点"确认"。

为什么这么麻烦？因为**一旦转错就收不回来了**。

数据库也一样。`commit()` 就是那个"确认"按钮：
- 在 `commit()` 之前，你随时可以反悔（撤销操作）
- 一旦 `commit()`，数据就**真正写入**数据库了
- 如果 `commit()` 过程中出错，所有操作都会**回滚**（就像从没操作过一样）

```python
# 没有commit：操作还在"暂存区"，可以随时反悔
# 有了commit：操作真正生效，数据写入数据库
db.commit()
```

> 💡 这就是数据库的**事务机制**：要么全部成功，要么全部回滚，不会出现"做了一半"的情况。

#### `db.refresh(user)` —— 刷新页面

你创建用户时没有填 `id`（因为 id 是数据库自动生成的）。`commit()` 之后，数据库已经给这个用户分配了 id，但你的 Python 对象还不知道。

`refresh()` 就像刷新网页——从数据库重新读取最新数据，填充到 Python 对象里。

```python
user = User(name="Alice", email="alice@qq.com")
# 此时 user.id 是 None

db.add(user)
db.commit()
# 此时数据库里 user.id 已经是 1 了，但 Python 对象里还是 None

db.refresh(user)
# 现在 user.id 变成了 1
```

### 🛠️ CRUD 完整代码示例

```python
from sqlalchemy.orm import Session

# ===== 依赖注入获取 Session（开始一次对话） =====
def get_db():
    db = SessionLocal()    # 拨通电话
    try:
        yield db           # 把对话交给请求处理函数使用
    finally:
        db.close()         # 不管发生什么，最后都要挂电话

# ===== C - Create（创建） =====
def create_user(db: Session, name: str, email: str):
    # 1. 创建Python对象（写好信封内容）
    user = User(name=name, email=email)
    # 2. 放进暂存区（放进购物车）
    db.add(user)
    # 3. 确认写入（点击下单）
    db.commit()
    # 4. 刷新获取数据库生成的id（刷新页面看订单号）
    db.refresh(user)
    return user

# ===== R - Read（读取） =====
def get_user(db: Session, user_id: int):
    # 从数据库查找id匹配的用户，返回第一个匹配结果
    return db.query(User).filter(User.id == user_id).first()

# ===== U - Update（更新） =====
def update_user(db: Session, user_id: int, new_name: str):
    # 1. 先查出来（找到要修改的联系人）
    user = db.query(User).filter(User.id == user_id).first()
    # 2. 修改属性（修改联系人名字）
    user.name = new_name
    # 3. 确认保存（点击保存）
    db.commit()
    return user

# ===== D - Delete（删除） =====
def delete_user(db: Session, user_id: int):
    # 1. 先查出来（找到要删除的联系人）
    user = db.query(User).filter(User.id == user_id).first()
    # 2. 删除（从通讯录里删掉）
    db.delete(user)
    # 3. 确认删除（确认移除）
    db.commit()
```

### 🔗 FastAPI 集成：把数据库操作接入 API

```python
from fastapi import FastAPI, Depends, HTTPException
from sqlalchemy.orm import Session

app = FastAPI()

@app.post("/api/v1/users")
async def create_user(name: str, email: str, db: Session = Depends(get_db)):
    # 先检查邮箱是否已被注册
    db_user = db.query(User).filter(User.email == email).first()
    if db_user:
        raise HTTPException(status_code=400, detail="邮箱已存在")
    # 调用前面写好的创建函数
    return create_user(db, name, email)
```

> 💡 `Depends(get_db)` 是 FastAPI 的依赖注入——每次请求进来时自动"拨通电话"（创建 Session），请求结束后自动"挂电话"（关闭 Session）。

## 知识点 8.4：Agent 场景应用

### 💬 对话历史存储

AI 助手需要记住用户之前说了什么。就像微信聊天记录一样，每条对话都需要保存下来。

```python
from sqlalchemy import Column, String, DateTime
from datetime import datetime

class Conversation(Base):
    __tablename__ = "conversations"
    
    id = Column(String, primary_key=True)               # 对话的唯一ID
    user_id = Column(String)                             # 哪个用户的对话
    messages = Column(String)                            # 对话内容（JSON格式）
    created_at = Column(DateTime, default=datetime.now)  # 创建时间
    updated_at = Column(DateTime, default=datetime.now, onupdate=datetime.now)  # 最后更新时间
```

> 💡 `messages` 字段用 JSON 格式存储，因为一次对话包含多条消息，结构类似：
> ```json
> [
>   {"role": "user", "content": "你好"},
>   {"role": "assistant", "content": "你好！有什么可以帮你的？"}
> ]
> ```

### ⚙️ Agent 配置存储

每个 Agent 都有自己的配置（用什么模型、温度参数是多少等），这些配置需要持久化保存。

```python
class AgentConfig(Base):
    __tablename__ = "agent_configs"
    
    id = Column(String, primary_key=True)       # 配置的唯一ID
    agent_name = Column(String)                  # Agent名称，如"客服助手"
    model_name = Column(String)                  # 使用的模型，如"gpt-4"
    parameters = Column(String)                  # 参数配置（JSON格式）
```

> 💡 `parameters` 用 JSON 存储，因为不同 Agent 的参数可能完全不同：
> ```json
> {"temperature": 0.7, "max_tokens": 2000, "top_p": 0.9}
> ```

## 知识点 8.5：Harness 架构视角分析

### ① 数据库在 Harness 中的作用

Harness（线束架构）的核心思想是：**用系统性的工程手段来保证软件质量，而不是靠事后打补丁**。数据库在其中扮演四个角色：

| 作用 | 解释 | 生活类比 |
|------|------|----------|
| **边界控制** | 数据库约束限制数据的合法范围 | 银行柜台：不填身份证号就办不了业务 |
| **错误恢复** | 事务回滚保证数据一致性 | 转账失败，钱自动退回，不会"扣了但没到" |
| **上下文管理** | 持久化存储对话上下文 | 笔记本：每次聊天内容都记下来，下次打开还能接着聊 |
| **反馈回路** | 数据分析和日志记录 | 行车记录仪：记录所有操作，出问题时可以回溯 |

### ② 补偿性代码 vs 系统性工程

| 方式 | 判断 | 说明 |
|------|------|------|
| 使用 ORM | ✅ 系统性工程 | ORM 自动处理 SQL 注入防护，不用手动转义特殊字符 |
| 使用依赖注入管理 Session | ✅ 系统性工程 | 统一管理"电话"的接通和挂断，不会忘记关闭连接 |
| 手写 SQL 字符串 | ❌ 补偿性代码 | 容易忘记过滤特殊字符导致 SQL 注入，出了事再打补丁 |
| 每次手动 `db.close()` | ❌ 补偿性代码 | 容易忘记关闭连接，导致数据库连接泄漏 |

> 💡 **核心思想**：好的架构让"正确的事"变得容易，让"错误的事"变得困难。ORM 和依赖注入就是让正确的事（安全操作数据库）变得容易的工具。

### 🔧 第二步：Engine 和 Session（database.py）

```python
# app/database.py
from sqlalchemy import create_engine
from sqlalchemy.orm import sessionmaker, declarative_base
from app.config import DATABASE_URL, POOL_SIZE, MAX_OVERFLOW, POOL_RECYCLE, POOL_PRE_PING

# 创建 Engine（带连接池）
engine = create_engine(
    DATABASE_URL,
    pool_size=POOL_SIZE,
    max_overflow=MAX_OVERFLOW,
    pool_recycle=POOL_RECYCLE,
    pool_pre_ping=POOL_PRE_PING,
    echo=False  # 生产环境关闭 SQL 日志，调试时设为 True
)

# Session 工厂
SessionLocal = sessionmaker(autocommit=False, autoflush=False, bind=engine)

# 表模板
Base = declarative_base()


# 依赖注入：每个请求自动获取和释放 Session
def get_db():
    db = SessionLocal()
    try:
        yield db
    finally:
        db.close()
```

```python

from sqlalchemy import Column, String, DateTime, ForeignKey, Text
from sqlalchemy.orm import relationship
from datetime import datetime
from app.database import Base

class Message(Base):
    __tablename__ = "messages"

    id = Column(String(36), primary_key=True)
    conversation_id = Column(String(36), ForeignKey("conversations.id"), nullable=False)

> 💡 **为什么拆成三张表而不是一张表存 JSON？**
> - 拆表后可以**单独查询某条消息**（如搜索历史消息）
> - 可以**统计对话数量**（`COUNT` 操作）
> - 可以**级联删除**（删对话时自动删所有消息，`cascade="all, delete-orphan"`）
> - JSON 方案虽然简单，但无法高效查询和统计

### 🔧 第四步：数据库操作层（Repository）

把 CRUD 操作封装到独立的层，业务逻辑不直接写 SQL：

```python
# app/repositories/conversation_repo.py
from sqlalchemy.orm import Session
from sqlalchemy import desc
from app.models.conversation import Conversation
from app.models.message import Message


class ConversationRepository:
    """对话数据的增删改查——只负责和数据库打交道"""

    def __init__(self, db: Session):
        self.db = db

    def create_conversation(self, user_id: str, title: str) -> Conversation:
        """创建一段新对话"""
        conversation = Conversation(user_id=user_id, title=title)
        self.db.add(conversation)
        self.db.commit()
        self.db.refresh(conversation)
        return conversation

    def get_conversation(self, conversation_id: str) -> Conversation | None:
        """根据ID获取对话"""
        return self.db.query(Conversation).filter(
            Conversation.id == conversation_id
        ).first()

    def list_conversations(self, user_id: str, page: int = 1, page_size: int = 20) -> list[Conversation]:
        """分页获取用户的对话列表，按时间倒序"""
        offset = (page - 1) * page_size
        return (
            self.db.query(Conversation)
            .filter(Conversation.user_id == user_id)
            .order_by(desc(Conversation.created_at))
            .offset(offset)
            .limit(page_size)
            .all()
        )

    def add_message(self, conversation_id: str, role: str, content: str) -> Message:
        """往对话中添加一条消息"""
        message = Message(conversation_id=conversation_id, role=role, content=content)
        self.db.add(message)
        self.db.commit()
        self.db.refresh(message)
        return message

    def get_messages(self, conversation_id: str, limit: int = 50) -> list[Message]:
        """获取对话的最近N条消息，按时间正序（从旧到新）"""
        return (
            self.db.query(Message)
            .filter(Message.conversation_id == conversation_id)
            .order_by(Message.created_at)
            .limit(limit)
            .all()
        )
```

> 💡 **为什么要单独一个 Repository 层？** 业务逻辑（如"发消息前检查对话是否存在"）和数据操作（如"INSERT INTO messages"）混在一起会很乱。分层后：Repository 只管数据库，Service 只管业务规则，各司其职。

###  第五步：业务逻辑层（Service）

```python
# app/services/conversation_service.py
from fastapi import HTTPException
from app.repositories.conversation_repo import ConversationRepository


class ConversationService:
    """对话业务逻辑——处理规则判断，调用 Repository 操作数据"""

    def __init__(self, repo: ConversationRepository):
        self.repo = repo

    def start_conversation(self, user_id: str, title: str):
        """开启新对话"""
        if not title.strip():
            raise HTTPException(status_code=400, detail="对话标题不能为空")
        return self.repo.create_conversation(user_id, title)

    def send_message(self, conversation_id: str, role: str, content: str):
        """发送消息（带业务校验）"""
        # 1. 检查对话是否存在
        conversation = self.repo.get_conversation(conversation_id)
        if not conversation:
            raise HTTPException(status_code=404, detail="对话不存在")

        # 2. 检查角色是否合法
        if role not in ("user", "assistant"):
            raise HTTPException(status_code=400, detail="角色只能是 user 或 assistant")

        # 3. 检查内容是否为空
        if not content.strip():
            raise HTTPException(status_code=400, detail="消息内容不能为空")

        # 4. 写入数据库
        return self.repo.add_message(conversation_id, role, content)

    def get_history(self, conversation_id: str, page: int = 1, page_size: int = 20):
        """获取对话历史（分页）"""
        conversation = self.repo.get_conversation(conversation_id)
        if not conversation:
            raise HTTPException(status_code=404, detail="对话不存在")
        return self.repo.get_messages(conversation_id, limit=page_size)
```

> 💡 **Service 层做了什么？** 它不直接操作数据库，而是做**业务规则判断**：标题不能为空、角色必须合法、对话必须存在。这些判断和数据库操作分开，以后改规则不用动数据库代码。

一个真实的请求进来，数据是怎么流转的：

```

    ↓

```

###  事务在真实业务中的使用

前面的 CRUD 示例中，每个操作单独 `commit()`。但有些业务需要**多个操作要么全成功，要么全失败**：

```python
# 场景：用户发消息的同时，扣减用户的积分余额
def send_message_and_deduct_points(
    db: Session,
    conversation_id: str,
    user_id: str,
    content: str,
    points_cost: int
):
    try:
        # 操作1：添加消息
        message = Message(conversation_id=conversation_id, role="user", content=content)
        db.add(message)

        # 操作2：扣减积分
        user = db.query(User).filter(User.id == user_id).first()
        if user.points < points_cost:
            raise HTTPException(status_code=400, detail="积分不足")
        user.points -= points_cost

        # 两个操作一起提交——要么都成功，要么都回滚
        db.commit()
        db.refresh(message)
        return message

    except Exception:
        db.rollback()  # 回滚：消息不会写入，积分也不会扣
        raise
```

> 💡 **为什么需要事务？** 假设消息写入了但积分扣减失败（比如数据库断了），就会出现"消息发了但没扣积分"的bug。事务保证这两个操作是**原子性**的——绑在一起，同生共死。
