## 知识点 12.1：什么是流式输出

### ① 先搞清楚：传统方式有什么问题？

在学流式输出之前，我们先想想普通的 HTTP 请求是怎么工作的：

```
用户发送请求 → 服务器处理（可能需要10秒）→ 服务器一次性返回全部结果 → 用户看到完整响应
```

**问题在哪？** 如果服务器需要 10 秒才能生成完整的结果，用户就得盯着空白屏幕干等 10 秒，然后突然看到一大坨文字。

这在普通接口里还好——比如查个数据库，1 秒就返回了。但如果你的 Agent 要调用大模型生成一段几百字的回复呢？大模型生成内容是很慢的，可能要 5~30 秒。让用户干等 30 秒再看到结果，体验极差。

### ② 流式输出是什么？

**流式输出 = 服务器边生成数据边返回，用户边接收边显示。**

```
用户发送请求 → 服务器开始生成第1个字 → 立刻返回给用户 → 用户看到第1个字
                  服务器生成第2个字 → 立刻返回给用户 → 用户看到第2个字
                  服务器生成第3个字 → 立刻返回给用户 → 用户看到第3个字
                  ...
```

用户不需要等全部内容生成完，马上就能看到内容在"跳动"，体验非常好。

### ③ 生活化类比：看视频

| 传统方式 | 流式方式 |
|----------|----------|
| 必须把整个视频文件下载完，才能点开看 | 边下载边播放，几秒钟就能开始看 |
| 等全部数据到齐 | 来一点数据就看一点 |
| 视频越大，等得越久 | 视频再大也能马上开始 |

你想想，如果看个视频要先等 10 分钟下载完，谁受得了？流式输出就是这个道理——**不要等，来一点用一点**。

### ④ 最直观的例子：ChatGPT

你用过 ChatGPT 或者类似的大模型对话产品吗？当你发送一个问题后，你会看到回答**一个字一个字地"蹦"出来**，就像有人在实时打字一样。

**这就是流式输出！**

背后的原理就是：大模型每生成几个字，就立刻通过网络推送给前端，前端收到后马上显示出来。所以你才看到文字"蹦出来"的效果。

如果不流式输出，你就会看到：发完问题 → 等 15 秒空白 → 突然刷出一大段文字。体验天差地别。

### ⑤ 应用场景

| 场景 | 说明 |
|------|------|
| **大模型对话** | LLM 逐字返回，用户实时看到回复（最典型） |
| **Agent 任务执行** | Agent 边思考边输出推理过程 |
| **实时日志推送** | 服务器日志实时推送到前端 |
| **大文件下载** | 文件分段传输，不用等整个文件准备好 |

## 知识点 12.2：FastAPI 流式响应

### ① 前置概念：什么是生成器（Generator）？

在写流式输出代码之前，你必须先理解一个 Python 概念——**生成器**。

**生成器是什么？** 简单说，就是一个用了 `yield` 关键字的函数。它和普通函数最大的区别是：

- **普通函数**：用 `return` 返回结果，一旦 return，函数就结束了
- **生成器函数**：用 `yield` 产出值，每次产出一个值后**暂停**，下次调用**从暂停的地方继续**

### ② 类比：生成器 = 流水线

想象一个工厂流水线：

| 普通函数（return） | 生成器（yield） |
|---------------------|-----------------|
| 工厂把所有产品全部做好，堆在一起，一次性发货 | 流水线每做好一个产品，就发一个 |
| 你要等所有产品做完才能拿到 | 每做好一个你就能拿到一个 |
| 产品多的话，等很久 | 马上就能拿到第一个 |

### ③ yield vs return 的区别

```python
# 普通函数：return 一次性返回全部
def normal_function():
    return [1, 2, 3, 4, 5]  # 一次性返回整个列表

result = normal_function()
print(result)  # [1, 2, 3, 4, 5] —— 全部拿到了


# 生成器函数：yield 一个一个产出
def generator_function():
    yield 1  # 产出1，暂停
    yield 2  # 产出2，暂停
    yield 3  # 产出3，暂停
    yield 4  # 产出4，暂停
    yield 5  # 产出5，暂停

gen = generator_function()
print(next(gen))  # 1 —— 拿到第一个
print(next(gen))  # 2 —— 拿到第二个
print(next(gen))  # 3 —— 拿到第三个
# 每次调用 next()，生成器从上次暂停的地方继续，产出下一个值
```

**关键区别总结：**
- `return` = 结束函数，一次性返回所有结果
- `yield` = 暂停函数，返回一个值，下次调用继续从这走

### ④ StreamingResponse 的作用

理解了生成器之后，`StreamingResponse` 就很好懂了：

**StreamingResponse = 把生成器产出的值，一个一个发送给客户端。**

它的工作流程：
```
生成器产出第1块数据 → StreamingResponse 发给客户端
生成器产出第2块数据 → StreamingResponse 发给客户端
生成器产出第3块数据 → StreamingResponse 发给客户端
...直到生成器耗尽
```

### ⑤ 代码示例：模拟 Agent 的流式思考过程

```python
from fastapi import FastAPI
from fastapi.responses import StreamingResponse
import asyncio

app = FastAPI()

async def agent_thinking_stream(question: str):
    """模拟 Agent 边思考边输出的过程"""
    # 模拟 Agent 的推理步骤
    steps = [
        f"收到问题：{question}\n",
        "正在分析问题...\n",
        "正在检索知识库...\n",
        "正在组织答案...\n",
        "答案是：这是一个很好的问题！\n",
    ]
    
    for step in steps:
        yield step          # 每产出一个步骤，就返回给客户端
        await asyncio.sleep(1)  # 模拟处理耗时

@app.get("/api/v1/agent/think")
async def think(question: str = "什么是AI Agent？"):
    # StreamingResponse 会把生成器的每个 yield 值逐个发给客户端
    return StreamingResponse(agent_thinking_stream(question))
```

**代码解读：**
1. `agent_thinking_stream` 是一个生成器函数（用了 `yield`）
2. 每次 `yield` 产出一段文字，然后暂停
3. `StreamingResponse` 接收这个生成器，每产出一个值就发给客户端
4. 客户端会每隔 1 秒收到一段文字，而不是等 5 秒后一次性收到全部

### ⑥ 同步生成器也行

FastAPI 的 `StreamingResponse` 既支持异步生成器（`async def` + `yield`），也支持同步生成器（`def` + `yield`）：

```python
# 同步生成器 —— 一样能用
def sync_agent_stream(question: str):
    """同步版本的 Agent 流式输出"""
    thoughts = ["分析问题...", "检索知识...", "生成回答..."]
    for thought in thoughts:
        yield f"{thought}\n"

@app.get("/api/v1/agent/think-sync")
async def think_sync(question: str = "什么是AI？"):
    return StreamingResponse(sync_agent_stream(question))
```

> **什么时候用同步，什么时候用异步？**
> - 如果生成过程中需要 `await`（比如调用外部 API、数据库），用 `async def` + `yield`
> - 如果只是简单的数据生成，用 `def` + `yield` 就够了

## 知识点 12.3：大模型流式输出（SSE 协议）

### ① 前置概念：什么是 SSE？

**SSE = Server-Sent Events = 服务器推送事件**

普通的 HTTP 请求是"一问一答"：客户端问，服务器答，然后连接就结束了。

但有些场景需要**服务器主动、持续地给客户端推送数据**，比如：
- 大模型一个字一个字地生成回复
- 股票行情实时更新
- 新闻推送

SSE 就是一种让**服务器能持续推送数据给客户端**的技术。它基于 HTTP 协议，但建立连接后会保持打开，服务器可以不断地往客户端发数据。

### ② SSE 的数据格式：`data: xxx\n\n`

SSE 协议规定了一个简单的数据格式：

```
data: {"content": "你"}\n\n
data: {"content": "好"}\n\n
data: {"content": "，"}\n\n
data: {"content": "我是AI"}\n\n
```

每一段数据都以 `data: ` 开头，以 `\n\n`（两个换行符）结尾。这就是 SSE 的"规矩"，客户端（浏览器）看到这个格式就知道"哦，这是 SSE 数据"。

**各部分含义：**
- `data: ` —— 固定前缀，告诉客户端"后面是数据内容"
- `{"content": "你"}` —— 实际的数据，通常用 JSON 格式
- `\n\n` —— 固定后缀，两个换行符表示"这条消息结束了"

### ③ `media_type="text/event-stream"` 的作用

```python
return StreamingResponse(
    llm_stream(prompt),
    media_type="text/event-stream"  # 这一行很关键！
)
```

`media_type="text/event-stream"` 是告诉客户端（浏览器）：

> "这不是一次普通的 HTTP 响应，这是一个 SSE 流式数据流，请用 SSE 的方式来处理。"

如果不设置这个，客户端会把它当成普通的文本响应，等所有内容都到齐了才处理，那就失去流式的意义了。

**类比：** 就像快递包裹上贴的标签。贴了"易碎品"标签，快递员就会小心 handling；贴了"text/event-stream"，浏览器就知道要用 SSE 方式逐条处理数据。

### ④ `[DONE]` 标记的作用

```python
yield "data: [DONE]\n\n"
```

`[DONE]` 是一个**约定俗成的结束标记**，告诉客户端：

> "所有数据都发完了，流式响应结束了。"

为什么需要它？因为在 SSE 中，连接是一直保持打开的。客户端怎么知道服务器已经发完了？就是靠这个 `[DONE]` 标记。客户端收到 `[DONE]` 就知道"可以关闭连接了"。

这个不是 HTTP 标准规定的，而是 OpenAI 等大厂约定俗成的做法，现在已经成为行业惯例。

### ⑤ 完整代码：模拟大模型流式输出

```python
from fastapi import FastAPI, Request
from fastapi.responses import StreamingResponse
import asyncio
import json

app = FastAPI()

async def llm_stream(prompt: str):
    """模拟大模型流式返回 —— 模拟 ChatGPT 那种一个字一个字蹦出来的效果"""
    
    # 模拟大模型生成的回复内容
    full_response = "你好！我是一个AI助手，很高兴为你服务。有什么可以帮助你的吗？"
    
    # 逐字输出，模拟大模型的生成过程
    for char in full_response:
        # 把每个字包装成 JSON 格式
        chunk = json.dumps({"content": char})
        # 按照 SSE 格式发送：data: + JSON数据 + 两个换行
        yield f"data: {chunk}\n\n"
        await asyncio.sleep(0.1)  # 模拟大模型生成每个字的耗时
    
    # 所有内容发完了，发送结束标记
    yield "data: [DONE]\n\n"

@app.post("/api/v1/chat/stream")
async def chat_stream(request: Request):
    body = await request.json()
    prompt = body.get("message", "")
    
    # media_type 告诉客户端这是 SSE 流
    return StreamingResponse(
        llm_stream(prompt),
        media_type="text/event-stream"
    )
```

**代码逐行解读：**
1. `llm_stream` 是生成器函数，逐字产出内容
2. 每个字被包装成 `{"content": "字"}` 的 JSON
3. 按照 SSE 格式 `data: {json}\n\n` 输出
4. `await asyncio.sleep(0.1)` 模拟大模型生成耗时
5. 最后输出 `data: [DONE]\n\n` 告诉客户端"发完了"
6. `media_type="text/event-stream"` 让浏览器知道这是 SSE

### ⑥ 使用 sse-starlette 库（更优雅的方式）

手动拼 `data: xxx\n\n` 格式有点麻烦，可以用 `sse-starlette` 库来简化：

```bash
pip install sse-starlette
```

```python
from fastapi import FastAPI, Request
from sse_starlette.sse import EventSourceResponse
import asyncio

app = FastAPI()

async def chat_generator(prompt: str):
    """用 EventSourceResponse 的方式，不需要手动拼 SSE 格式"""
    messages = ["你好", "，", "我是", "AI", "助手", "，", "有什么", "可以", "帮助", "你的", "？"]
    for msg in messages:
        # 直接 yield 字典，库会自动帮你转成 SSE 格式
        yield {"event": "message", "data": msg}
        await asyncio.sleep(0.3)

@app.post("/api/v1/chat/sse")
async def chat_sse(request: Request):
    body = await request.json()
    prompt = body.get("message", "")
    # EventSourceResponse 自动处理 SSE 格式和 media_type
    return EventSourceResponse(chat_generator(prompt))
```

**对比两种方式：**

| 方式 | 优点 | 缺点 |
|------|------|------|
| 手动拼 `data: xxx\n\n` | 不依赖第三方库，灵活 | 格式容易写错 |
| `sse-starlette` | 自动处理格式，代码更简洁 | 需要额外安装依赖 |

## 知识点 12.4：流式输出的错误处理

### ① 流式输出中错误处理的特殊性

普通的 HTTP 接口，如果出错了，直接返回一个错误状态码就行：

```python
# 普通接口 —— 出错了直接返回 500
@app.get("/api/v1/data")
async def get_data():
    try:
        result = do_something()
        return {"data": result}
    except Exception as e:
        return {"error": str(e)}  # 直接返回错误信息，客户端收到完整的错误响应
```

**但流式输出不一样！** 流式输出是边生成边发送的。可能你已经发了 5 条数据给客户端了，第 6 条的时候突然出错了。这时候你不能"撤回"已经发出去的数据，也不能像普通接口那样返回一个错误状态码——因为响应头早就发出去了。

**类比：** 就像你在直播，已经播了 5 分钟了，突然设备出故障了。你没法"撤回"前 5 分钟的直播，只能在直播里告诉观众"设备出问题了"。

### ② 解决方案：在流中发送错误信息

```python
import json
import asyncio

async def safe_llm_stream(prompt: str):
    """带错误处理的流式输出"""
    try:
        full_response = "这是AI的回复内容..."
        for char in full_response:
            chunk = json.dumps({"content": char})
            yield f"data: {chunk}\n\n"
            await asyncio.sleep(0.1)
    except Exception as e:
        # 出错了！但不能 return 错误，只能在流里发一个错误消息
        error_msg = json.dumps({"error": f"生成过程中出错: {str(e)}"})
        yield f"data: {error_msg}\n\n"
    finally:
        # 无论成功还是失败，都发送结束标记
        yield "data: [DONE]\n\n"
```

**关键点：**
- 错误信息也通过 `yield` 发送，而不是 `return`
- 用 `finally` 确保 `[DONE]` 一定会被发送，客户端不会一直傻等
- 客户端需要能识别错误消息（检查 JSON 里有没有 `error` 字段）

### ③ 客户端断开检测：request.is_disconnected()

流式输出还有一个特殊问题：**客户端可能中途断开连接**。

比如用户正在看 Agent 的流式回复，突然关了浏览器标签页。这时候服务器还在傻傻地生成数据、发送数据，但这些数据已经没人收了，白白浪费服务器资源。

**类比：打电话**

想象你在打电话跟朋友聊天：
- 你正在说话（服务器在生成数据）
- 朋友突然挂了电话（客户端断开连接）
- 你还在对着空气说话（服务器继续生成和发送）—— 这没有意义！

`request.is_disconnected()` 就是用来检测"对方是不是已经挂了电话"：

```python
from fastapi import FastAPI, Request
from fastapi.responses import StreamingResponse
import asyncio
import json

app = FastAPI()

async def chat_with_disconnect_check(request: Request, prompt: str):
    """带客户端断开检测的流式输出"""
    
    full_response = "这是一段很长的AI回复内容，需要一段时间才能生成完毕..."
    
    for char in full_response:
        # 检查客户端是否已经断开（对方是不是挂了电话）
        if await request.is_disconnected():
            print("客户端已断开，停止生成")
            break  # 对方都挂了，就别说了
        
        chunk = json.dumps({"content": char})
        yield f"data: {chunk}\n\n"
        await asyncio.sleep(0.1)
    
    yield "data: [DONE]\n\n"

@app.post("/api/v1/chat/safe-stream")
async def safe_chat_stream(request: Request):
    body = await request.json()
    prompt = body.get("message", "")
    return StreamingResponse(
        chat_with_disconnect_check(request, prompt),
        media_type="text/event-stream"
    )
```

**为什么这很重要？** 在 Agent 场景中，大模型调用是很贵的（按 token 计费）。如果用户已经关了页面，你还继续调用大模型生成内容，那就是白白烧钱。`is_disconnected()` 帮你及时止损。

## 知识点 12.5：Harness 架构视角分析

### ① 流式输出在 Harness 架构中的作用

从 Harness 架构的角度来看，流式输出解决了几个关键问题：

| 架构关注点 | 流式输出的作用 | 说明 |
|------------|----------------|------|
| **边界控制** | 速率控制 + 超时控制 | 防止服务器被大量流式请求压垮 |
| **错误恢复** | 优雅关闭流式连接 | 出错时能正确通知客户端并释放资源 |
| **上下文管理** | 流式会话的状态维护 | 多轮流式对话中保持上下文一致性 |
| **反馈回路** | 实时响应提升用户体验 | 用户能即时看到 Agent 的思考过程 |

### ② 补偿性代码 vs 系统性工程

| 方式 | 判断 | 说明 |
|------|------|------|
| 使用 `StreamingResponse` | ✅ 系统性工程 | FastAPI 框架提供的标准流式响应方式 |
| 使用 SSE 协议 | ✅ 系统性工程 | 行业标准实时通信协议，浏览器原生支持 |
| 使用 `sse-starlette` | ✅ 系统性工程 | 成熟的第三方 SSE 库，自动处理格式细节 |
| 检测客户端断开 | ✅ 系统性工程 | 框架提供的标准能力，保障资源合理利用 |
| 手动分块发送 | ❌ 补偿性代码 | 自己拼凑分块逻辑，容易出错，不可靠 |
| 忽略客户端断开 | ❌ 补偿性代码 | 不检测断开会导致资源浪费和潜在内存泄漏 |

| **文件传输** | Agent 生成的大文件分段下载 |

### 学习重心

| 内容 | 深度 | 理由 |
|------|------|------|
| 生成器（yield） | ✅ 必须掌握 | 流式输出的基础，不懂生成器就写不了流式 |
| StreamingResponse | ✅ 必须掌握 | FastAPI 流式输出的核心组件 |
| SSE 协议格式 | ✅ 必须掌握 | 大模型流式返回的行业标准 |
| `[DONE]` 结束标记 | ✅ 必须掌握 | 客户端判断流结束的关键 |
| 异常处理 | ✅ 必须掌握 | 保障流式会话稳定性 |
| 客户端断开检测 | ✅ 必须掌握 | 资源释放和成本控制的关键 |
| sse-starlette | ✅ 推荐使用 | 简化 SSE 开发，减少手动拼格式的错误 |

### 哪些内容浅尝，哪些必须深挖

- **浅尝**：WebSocket 流式传输，了解基本概念即可（大模型场景 SSE 更常用）
- **深挖**：SSE 实现和错误处理，这是大模型 Agent 应用的核心能力
- **深挖**：客户端断开检测和资源释放，这关系到你的钱包（API 调用费用）
