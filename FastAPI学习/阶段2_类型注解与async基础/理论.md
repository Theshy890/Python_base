## 知识点 2.1：Python类型注解

### ① 先搞懂"什么是类型"

在写代码之前，我们先聊一个最基础的问题：**数据也有"种类"之分。**

想象你家里有各种各样的**收纳盒**：

| 盒子 | 里面装的东西 | 对应编程中的"类型" |
|------|-------------|-------------------|
| 鞋盒 | 鞋子（一双一双的） | `int` 整数——像 `1`、`42`、`-7` 这样完整的数字 |
| 信封 | 信件（一段一段的文字） | `str` 字符串——像 `"你好"`、`"Agent"` 这样用引号包起来的文本 |
| 开关面板 | 只有"开"和"关"两种状态 | `bool` 布尔值——只有 `True`（真）和 `False`（假） |
| 秤 | 称出来的重量（带小数） | `float` 浮点数——像 `3.14`、`95.5` 这样带小数点的数字 |

**为什么要分种类？** 因为你不会把汤倒进纸信封里，也不会把信件塞进鞋盒。每种盒子只适合装特定的东西。编程也一样——**整数可以做加减法，字符串不能做加减法**。如果你把 `"123"`（字符串）和 `456`（整数）混在一起相加，Python 会报错，因为它不知道该做"文字拼接"还是"数学加法"。

```python
# 整数可以做数学运算
price = 100 + 50      # 结果是 150

# 字符串做的是"拼接"
greeting = "你好" + "世界"  # 结果是 "你好世界"

# 混在一起就会报错！
wrong = "价格：" + 100   # ❌ TypeError！Python 不知道该怎么办
```

### ② 那"类型注解"又是什么？

好，现在你知道了数据有不同类型。但 Python 有一个很"随性"的特点：**它不强制你声明类型。**

```python
# Python 允许你这样做——变量想装什么就装什么
x = 100        # 现在是整数
x = "hello"    # 下一秒变成字符串，Python 不反对
x = True       # 再变成布尔值，Python 也无所谓
```

这就像你家的收纳盒**没有贴标签**。你自己可能还记得鞋盒里装过什么，但过了一段时间、或者别人来翻你的盒子，就完全搞不清楚了。

**类型注解 = 给盒子贴上标签。**

```python
# 贴上标签后，一目了然
name: str = "张三"        # 这个盒子装的是字符串
age: int = 25             # 这个盒子装的是整数
score: float = 95.5       # 这个盒子装的是浮点数
is_active: bool = True    # 这个盒子装的是布尔值
```

> **注意**：Python 的类型注解**不会真的限制你往盒子里放什么**（它不会报错阻止你）。它更像是一个"约定"和"提示"——告诉看代码的人（以及 IDE 编辑器）："我这里打算放字符串哦"。

### ③ 那为什么 FastAPI 特别需要类型注解？

这是关键问题。在普通 Python 脚本里，类型注解只是"建议"，不写也能跑。但 **FastAPI 会把你的类型注解当真！**

打个比方：

> 你开了一家快递站，客户填快递单时，有些栏目标了"必填"，有些没标。
> - **普通 Python 脚本**：不管客户怎么填你都收，填错了等寄出去出了问题再说。
> - **FastAPI**：看到标签上写"整数"，如果客户填了"abc"，**当场就拒收**，自动返回错误提示。

FastAPI 靠类型注解来**自动校验**用户提交的数据。你写了 `age: int`，FastAPI 就会自动检查用户传来的 age 是不是整数，不是的话自动返回 422 错误。你什么都不用额外写！

```python
# 没有类型注解：FastAPI 不知道 message 应该是什么类型
def chat(message):
    pass

# 有类型注解：FastAPI 自动知道 message 必须是字符串，还会自动校验
def chat(message: str):
    pass
```

**这就是为什么在 FastAPI 里，类型注解不是"可选的装饰"，而是"必须掌握的基础"。**

### ④ 函数也要贴标签

函数就像一个"加工机器"：你扔进去原料，它吐出产品。类型注解可以同时标注"需要什么原料"和"产出什么产品"。

```python
# name: str 表示"需要字符串作为原料"
# -> str 表示"产出的是字符串"
def greet(name: str) -> str:
    return f"你好, {name}"

# 调用示例
result = greet("张三")  # result 是字符串 "你好, 张三"
```

### ⑤ 盒子里还能装盒子：list 和 dict

现实里，你的收纳盒里可能不止一样东西——可能一个盒子里装了好几双鞋。编程也一样，有时候一个变量要装**一组数据**。

**`list[str]` —— 一个盒子里装了一堆字符串**

方括号 `[]` 里的内容表示"这个列表里装的是什么类型"：

```python
# list[str] = "一个列表，里面每个元素都是字符串"
users: list[str] = ["张三", "李四", "王五"]
#         ↑
#    方括号里写 str，意思是"里面装的全是字符串"

# list[int] = "一个列表，里面每个元素都是整数"
ages: list[int] = [25, 30, 28]
#       ↑
#    方括号里写 int，意思是"里面装的全是整数"
```

**`dict[str, int]` —— 一个"对照表"，左边是字符串，右边是整数**

想象一本"成绩册"：左边写科目名（字符串），右边写分数（整数）。方括号里的两个类型，用逗号隔开，第一个是"键"的类型，第二个是"值"的类型：

```python
# dict[str, int] = "一个字典，键是字符串，值是整数"
scores: dict[str, int] = {"数学": 90, "语文": 85, "英语": 92}
#          ↑       ↑
#       键的类型  值的类型
#       (科目名)  (分数)

# dict[str, str] = "键和值都是字符串"
translations: dict[str, str] = {"hello": "你好", "world": "世界"}
```

**记忆口诀：方括号里写的永远是"里面装什么"。**

### ⑥ Python 3.9+ 的新写法

在老版本 Python 中，写 `list[str]` 和 `dict[str, int]` 需要从 `typing` 模块导入 `List` 和 `Dict`（大写开头）：

```python
# 老写法（Python 3.8 及以下）
from typing import List, Dict
users: List[str] = ["张三", "李四"]
scores: Dict[str, int] = {"数学": 90}
```

Python 3.9+ 之后，直接用**小写**的 `list` 和 `dict` 就行，不用再导入了：

```python
# 新写法（Python 3.9+，推荐）
users: list[str] = ["张三", "李四"]
scores: dict[str, int] = {"数学": 90, "语文": 85}
```

> 本教程统一使用新写法。如果你的 Python 版本低于 3.9，请用老写法。

### ⑦ 面向 Agent 场景的完整示例

```python
# 一个典型的 Agent 函数，类型注解让一切清晰可见
def call_llm(prompt: str, max_tokens: int = 1024) -> dict[str, str]:
    """
    调用大模型 API
    
    看函数签名就知道：
    - prompt：必须传一个字符串（你问的问题）
    - max_tokens：可选，传一个整数（最多生成多少字），默认 1024
    - 返回值：一个字典，键是字符串，值也是字符串
      比如 {"status": "success", "reply": "你好！"}
    """
    # 这里是模拟实现
    return {"status": "success", "reply": f"AI回复: {prompt}"}


def build_conversation_history(messages: list[dict[str, str]]) -> str:
    """
    把对话历史拼成一个字符串
    
    - messages：一个列表，里面每个元素都是字典
    - 每个字典的格式是 {"role": "user", "content": "你好"}
    """
    history = ""
    for msg in messages:
        history += f"{msg['role']}: {msg['content']}\n"
    return history


# 调用示例
conversation: list[dict[str, str]] = [
    {"role": "user", "content": "什么是AI Agent？"},
    {"role": "assistant", "content": "AI Agent 是能够自主决策的智能体。"},
    {"role": "user", "content": "能举个例子吗？"},
]

result: dict[str, str] = call_llm("请总结以下对话", max_tokens=512)
print(result["reply"])
```

## 知识点 2.2：类型注解的实际价值

### ① 对 Agent 开发的意义

| 价值 | 具体体现 | 打个比方 |
|------|----------|----------|
| **自动校验数据** | FastAPI 根据类型注解自动检查请求数据，不合法直接拒绝 | 快递站按快递单自动检查，不合格当场退回 |
| **代码自文档化** | 函数签名就是文档，不用看实现就知道参数和返回值 | 看盒子标签就知道里面装什么，不用打开看 |
| **IDE 智能提示** | 写代码时自动补全、类型错误实时标红 | 导航仪实时提醒你"前方违章拍照" |
| **早期发现错误** | 运行前就能发现类型不匹配的问题 | 出门前检查钥匙带了没，比到了公司才发现忘带好 |

### ② 对比示例：有注解 vs 没注解

```python
# ❌ 没有类型注解——看函数签名完全不知道该怎么传参
def call_llm(prompt, max_tokens):
    pass
# prompt 是什么类型？字符串？字典？
# max_tokens 是整数还是字符串？有默认值吗？
# 返回值是什么？完全不知道……

# ✅ 有类型注解——一目了然
def call_llm(prompt: str, max_tokens: int = 1024) -> dict[str, str]:
    pass
# prompt 是字符串（你问的问题）
# max_tokens 是整数，默认 1024（最多生成多少 token）
# 返回值是字典，键值都是字符串（比如 {"reply": "你好"}）
```

**在团队协作和 Agent 开发中，类型注解就是代码的"说明书"。**

## 知识点 2.3：异步编程基础

### ① 先理解"什么是同步"

想象你去银行办业务，只有一个柜台、一个工作人员：

> 1. 你排到号，开始办业务（比如存款，需要 5 分钟）
> 2. **你必须站在柜台前等着**，工作人员办完你的，才轮到下一个人
> 3. 后面的人**全部排队等着**，什么都不干

这就是**同步**——**一件事做完，再做下一件事，中间必须干等。**

```python
import time

def 取号():
    print("取号中...")
    time.sleep(1)       # 等 1 秒
    print("取号完成")

def 填单():
    print("填单中...")
    time.sleep(2)       # 等 2 秒
    print("填单完成")

def 办理():
    print("办理中...")
    time.sleep(5)       # 等 5 秒
    print("办理完成")

# 同步执行：一个接一个，总共需要 1+2+5 = 8 秒
取号()
填单()
办理()
```

在程序里，`time.sleep()` 代表任何需要"等待"的操作——比如等网络响应、等数据库查询、等文件读写。**同步代码在等待的时候，整个程序就卡在那里，什么都干不了。**

### ② 再理解"什么是异步"

还是去银行，但这次银行升级了：

> 1. 你取完号后，**不用站在柜台前傻等**——你可以去旁边刷手机、喝水
> 2. 柜员在后台同时处理多个人的业务
> 3. 轮到你的时候，广播叫号，你再去柜台

这就是**异步**——**等待的时候不闲着，去做别的事情。**

```python
import asyncio

async def 取号():
    print("取号中...")
    await asyncio.sleep(1)   # 等待的时候，去做别的事！
    print("取号完成")

async def 填单():
    print("填单中...")
    await asyncio.sleep(2)   # 等待的时候，去做别的事！
    print("填单完成")

async def 办理():
    print("办理中...")
    await asyncio.sleep(5)   # 等待的时候，去做别的事！
    print("办理完成")

# 异步执行：三个任务同时开始，总共只需要约 5 秒（最慢那个的时间）
async def main():
    await asyncio.gather(取号(), 填单(), 办理())

asyncio.run(main())
```

**对比一下：**

| | 同步 | 异步 |
|---|---|---|
| 做事方式 | 排队：做完一件再做下一件 | 同时开多个：等的时候去做别的 |
| 等待时 | 干等着，程序卡住 | 去做其他事，程序不卡 |
| 总耗时 | 所有任务时间**相加** | 取决于**最慢**的那个任务 |
| 上面的例子 | 8 秒 | 约 5 秒 |

### ③ 搞懂 async 和 await 这两个关键字

很多人被 `async` 和 `await` 吓到，其实它们的意思非常直白：

**`async` = 声明"这个函数会等待"**

在函数前面加上 `async`，就是告诉 Python："注意啦，这个函数里面有需要等待的操作，它可以被暂停。"

```python
# 加了 async，这个函数就变成了"异步函数"（也叫"协程"）
async def 煮咖啡():
    ...
```

> 类比：你在餐厅门口挂了个牌子"本餐厅需要预约"（`async`）。这个牌子本身不做什么，只是**声明**：来这里吃饭是需要等的，要提前预约。

**`await` = 真正"暂停"的那一刻**

在异步函数内部，遇到需要等待的操作时，用 `await` 来**真正暂停**。暂停的这段时间，程序会去做别的事情。

```python
async def 煮咖啡():
    print("开始煮咖啡...")
    await asyncio.sleep(3)   # ← 这一行是"暂停"：等 3 秒，期间去做别的事
    print("咖啡好了！")
```

> 类比：你进了餐厅，点了菜。`await` 就是你**坐下等菜**的那个动作——你不用一直盯着厨房，可以玩手机（程序去做别的事），菜好了服务员叫你（等待结束，继续执行）。

**总结一句话：**
- `async def` = 声明"我这个函数会等人"
- `await` = "现在我开始等了，你先去忙别的"

### ④ asyncio.gather —— 把多个任务打包一起执行

假设你要同时煮咖啡、烤面包、煎鸡蛋。你不需要一个一个来，可以把三个任务"打包"，让它们同时开始：

```python
# asyncio.gather 的作用：把多个异步任务打包，一起执行
await asyncio.gather(煮咖啡(), 烤面包(), 煎鸡蛋())
```

**类比：** 你是餐厅经理，`asyncio.gather` 就是你**同时给三个厨师下指令**："你们三个同时开工！" 然后你等他们全部做完。

```python
import asyncio

async def 煮咖啡():
    await asyncio.sleep(3)
    print("☕ 咖啡好了")
    return "咖啡"

async def 烤面包():
    await asyncio.sleep(2)
    print("🍞 面包好了")
    return "面包"

async def 煎鸡蛋():
    await asyncio.sleep(1)
    print("🍳 鸡蛋好了")
    return "鸡蛋"

async def main():
    # 三个任务同时开始！
    results = await asyncio.gather(煮咖啡(), 烤面包(), 煎鸡蛋())
    print(f"早餐齐了: {results}")
    # 总耗时约 3 秒（最慢的咖啡），而不是 3+2+1=6 秒

asyncio.run(main())
```

### ⑤ 面向 Agent 场景的完整示例：批量调用 LLM

```python
import asyncio

async def call_llm(prompt: str) -> str:
    """模拟调用大模型 API（需要等待网络响应）"""
    await asyncio.sleep(1)  # 模拟 1 秒的网络延迟
    return f"AI回复: {prompt}"

async def batch_call_llm(prompts: list[str]) -> list[str]:
    """
    批量调用大模型——用 gather 并发执行
    
    如果串行调用 3 个 prompt，需要 3 秒
    用 gather 并发调用，只需要约 1 秒！
    """
    # 创建多个任务（但还没开始执行）
    tasks = [call_llm(prompt) for prompt in prompts]
    
    # gather 把它们打包一起执行
    results = await asyncio.gather(*tasks)
    
    return list(results)

# 使用示例
prompts = ["什么是AI Agent？", "Python有什么优点？", "如何学习FastAPI？"]
results = asyncio.run(batch_call_llm(prompts))

for prompt, reply in zip(prompts, results):
    print(f"问: {prompt}")
    print(f"答: {reply}")
    print()
```

## 知识点 2.4：async 关键字详解

### ① 核心语法速查表

| 关键字/函数 | 作用 | 类比 |
|------------|------|------|
| `async def` | 定义一个异步函数（协程） | 在餐厅门口挂牌子："本店需要预约" |
| `await` | 暂停当前函数，等待异步操作完成 | 坐下等菜，期间玩手机 |
| `asyncio.run()` | 启动异步程序（程序入口） | 开门营业！ |
| `asyncio.gather()` | 把多个异步任务打包并发执行 | 同时给多个厨师下指令 |

### ② 关键概念

| 概念 | 解释 | 类比 |
|------|------|------|
| **协程（Coroutine）** | 用 `async def` 定义的函数，可以暂停和恢复 | 可以"暂停等待"的特殊函数 |
| **事件循环（Event Loop）** | 协程的"调度员"，决定哪个协程先执行、哪个后执行 | 餐厅经理：安排谁先做菜、谁后做菜 |
| **awaitable** | 可以被 `await` 的对象 | "需要等待才能拿到的东西"——比如等快递送到 |

### ③ 常见错误提醒

```python
# ❌ 错误1：在普通函数里用 await
def normal_func():
    await asyncio.sleep(1)  # 报错！await 只能在 async 函数里用

# ✅ 正确：必须用 async def
async def correct_func():
    await asyncio.sleep(1)

# ❌ 错误2：直接调用异步函数，不加 await
async def main():
    call_llm("你好")  # 不会执行！只会创建一个协程对象，被丢弃

# ✅ 正确：用 await 或 gather
async def main():
    result = await call_llm("你好")           # 单个任务
    results = await asyncio.gather(            # 多个任务
        call_llm("你好"),
        call_llm("再见")
    )
```

## 知识点 2.5：FastAPI 中的异步路由

### ① 先搞清楚：为什么 FastAPI 路由要用 `async def` 而不是 `def`？

回忆一下知识点 2.3 的内容：异步的核心优势是**在等待的时候去做别的事**。

在 Agent 服务中，最常见的操作是什么？**调用外部 API**（比如调用大模型、查向量数据库、调工具接口）。这些操作都需要**等待网络响应**——属于"IO 密集型"操作。

| 用 `def`（同步） | 用 `async def`（异步） |
|---|---|
| 调用 LLM 时，整个服务卡住，其他用户的请求排队等着 | 调用 LLM 时，服务去处理其他用户的请求 |
| 10 个用户同时请求 = 排队等 10 轮 | 10 个用户同时请求 = 几乎同时处理 |

**所以：如果你的路由函数里有"等待"操作（网络请求、数据库查询、文件读写），就用 `async def`。**

### ② IO 密集型 vs CPU 密集型

这两个词听起来很专业，其实很好理解：

**IO 密集型 = 大部分时间在"等"**

> 类比：你在网上下单，大部分时间在等快递送到。你本人没干什么重活，就是在等。
> 
> 典型场景：调用 API、读写数据库、读写文件、网络爬虫。
> 
> **→ 适合用异步（`async def`）**，因为等待的时间可以去做别的事。

**CPU 密集型 = 大部分时间在"算"**

> 类比：你在做数学考试，一直在埋头计算，没有时间干别的。
> 
> 典型场景：图像处理、视频编码、大规模数据计算、模型训练。
> 
> **→ 不适合用异步**，因为你根本没在"等"，CPU 一直在满负荷运转，没法"暂停去做别的事"。

```python
# IO 密集型 ✅ 适合 async def
@app.get("/api/chat")
async def chat(message: str):
    # 调用大模型 API——需要等网络响应
    response = await call_llm_api(message)  # 等待时可以去处理其他请求
    return {"reply": response}

# CPU 密集型 ❌ 不适合 async def，用普通 def
@app.post("/api/process-image")
def process_image(image_url: str):
    # 图像处理——CPU 一直在满负荷计算
    result = heavy_image_processing(image_url)  # 这里没有"等待"，全是计算
    return {"result": result}
```

### ③ 异步路由代码示例

```python
from fastapi import FastAPI
import asyncio

app = FastAPI()

@app.get("/")
async def root():
    await asyncio.sleep(1)  # 模拟耗时操作
    return {"message": "异步响应"}

@app.post("/api/v1/chat")
async def chat(message: str):
    """异步对话接口——调用 LLM 属于 IO 密集型操作"""
    await asyncio.sleep(0.5)  # 模拟调用 LLM 的网络延迟
    return {"response": f"AI收到: {message}"}

@app.get("/api/v1/batch-chat")
async def batch_chat(messages: list[str]):
    """
    批量对话接口——用 gather 并发调用多次 LLM
    
    这是异步编程在 Agent 服务中最典型的应用场景
    """
    async def single_call(msg: str) -> str:
        await asyncio.sleep(0.5)  # 模拟每次调用 LLM 的延迟
        return f"AI回复: {msg}"
    
    # 并发调用，总耗时约 0.5 秒，而不是 0.5 * N 秒
    results = await asyncio.gather(*[single_call(m) for m in messages])
    return {"responses": list(results)}
```

### ④ 同步 vs 异步路由对比总结

| 特性 | 同步路由 `def` | 异步路由 `async def` |
|------|----------------|----------------------|
| 并发能力 | 低（一个请求卡住，后面的排队） | 高（等待时处理其他请求） |
| 适用场景 | CPU 密集型（图像处理、大计算） | IO 密集型（API 调用、数据库查询） |
| 性能特点 | 需要多线程才能提高并发 | 单线程就能实现高并发 |
| Agent 场景 | 本地模型推理、文本后处理 | 调用远程 LLM API、查向量数据库 |

## 知识点 2.6：Harness 架构视角分析

### ① 类型注解在 Harness 中的作用

- **边界控制**：类型注解定义了数据的合法范围，是第一道防线——FastAPI 自动拒绝不合法的数据，就像快递站按标签自动检查包裹
- **错误恢复**：类型错误在开发期就被发现（IDE 标红），而不是上线后才发现崩溃
- **上下文管理**：清晰的类型定义让数据在模块之间传递时更加安全，不会出现"我以为你传的是字典，结果是字符串"的尴尬
- **反馈回路**：IDE 实时提示类型错误，写代码的同时就在做质量检查

### ② 异步编程在 Harness 中的作用

- **边界控制**：异步并发控制可以限制同时执行的任务数量（比如最多并发 10 个 LLM 调用），防止资源耗尽
- **错误恢复**：异步任务可以独立失败和重试，一个 LLM 调用失败不影响其他调用
- **上下文管理**：asyncio 提供了任务取消和超时机制——比如 LLM 超过 30 秒没响应，自动取消
- **反馈回路**：并发执行提高了响应速度，用户体验更好；同时可以快速发现哪个环节是瓶颈

### ③ 补偿性代码 vs 系统性工程

| 方式 | 判断 | 说明 |
|------|------|------|
| 使用类型注解 | ✅ 系统性工程 | 长期保值，FastAPI 自动利用注解做校验，一劳永逸 |
| 使用异步编程 | ✅ 系统性工程 | 提高并发能力，天然适合 AI 服务的 IO 密集场景 |
| 手动写 if 检查类型 | ❌ 补偿性代码 | 容易遗漏，重复劳动，不如让 FastAPI 自动校验 |
| 同步调用外部 API | ❌ 补偿性代码 | 阻塞线程，并发能力差，用户多了就崩 |

## 📌 章节总结

### 知识点在 Agent 项目中的落地位置

- **数据定义**：所有输入输出数据都需要类型注解——FastAPI 靠它自动校验
- **API 接口**：IO 密集型路由用 `async def`，让服务能同时处理多个请求
- **批量调用**：用 `asyncio.gather` 并发调用多个 LLM API，把等待时间压缩到最短

### 学习重心

| 内容 | 深度 | 理由 |
|------|------|------|
| 基础类型注解（int/str/bool/float） | ✅ 必须掌握 | 所有代码的基础 |
| 容器类型注解（list/dict） | ✅ 必须掌握 | FastAPI 自动校验的核心 |
| async/await 语法 | ✅ 必须掌握 | 并发调用 LLM 的关键 |
| asyncio.gather | ✅ 必须掌握 | 批量任务并发执行的标配 |
| 复杂类型注解（泛型、Protocol 等） | ⚠️ 适度了解 | 后续 Pydantic 章节会深入 |

### 哪些内容浅尝，哪些必须深挖

- **浅尝**：类型注解的高级特性（泛型、Protocol 等），当前阶段了解基础即可
- **深挖**：async/await 的使用场景和限制，这是构建高并发 Agent 服务的关键
- **核心心法**：**有"等待"就用 async，有"数据"就加类型注解**——这两条原则贯穿整个 FastAPI 开发
