# 阶段11：异步与并发

> 在构建 Agent 系统时，你经常需要同时调用多个 LLM API、同时处理多个用户请求、同时执行多个工具。如果一个个排队等着来，效率会非常低。本阶段我们就来搞懂：如何让程序"同时做多件事"。

---

## 知识点 11.1：异步编程回顾

> 这是阶段2内容的进阶。我们先快速回顾基础概念，然后重点理解一个很多人搞混的问题：并发和并行到底有什么区别？

### ① 先回顾 async/await  basics

在阶段2你学过这几个概念，我们用一张表快速过一遍：

| 概念 | 一句话解释 | 生活类比 |
|------|-----------|---------|
| **协程（Coroutine）** | 可以"暂停"和"恢复"的函数 | 你可以做到一半先放一放，回头继续做 |
| **async def** | 定义一个异步函数（协程函数） | 声明"这个任务中间可以暂停" |
| **await** | 等待一个异步操作完成 | "等外卖到了我再继续下一步" |
| **事件循环（Event Loop）** | 负责调度所有协程的"总指挥" | 餐厅里的调度员，决定先处理哪桌 |

一个简单的异步函数长这样：

```python
async def call_llm(prompt: str) -> str:
    # await 表示：这里要等一会儿（比如等网络请求返回）
    # 在等待的期间，程序可以去做别的事
    result = await some_api_call(prompt)
    return result
```

核心思想就一句话：**遇到要等的事情时，不要傻等，先去做别的事**。

### ② 重点：并发 vs 并行 —— 不是一回事！

这两个词经常被混着用，但它们有本质区别：

| | 并发（Concurrency） | 并行（Parallelism） |
|--|-------------------|-------------------|
| **含义** | 同时**管理**多件事 | 同时**执行**多件事 |
| **关键** | 交替着做，看起来像同时 | 真正的同一时刻在做 |
| **需要** | 单核 CPU 就够了 | 需要多核 CPU |

#### 🍽️ 餐厅类比（请记住这个类比，贯穿整个阶段）

**并发 = 一个服务员同时服务多桌**

想象一个服务员负责 3 桌客人：
- A桌点完菜，等厨房做菜的时候 → 服务员去 B桌点菜
- B桌点完菜，等厨房做菜的时候 → 服务员去 C桌点菜
- 厨房做好 A桌的菜 → 服务员端给 A桌
- 然后继续服务 B桌、C桌……

**关键点：服务员只有一个人，他是在"切换着来"，但因为每桌都有"等待"的时间（等厨房做菜），所以他可以同时照顾多桌。**

**并行 = 多个服务员各服务一桌**

如果有 3 个服务员：
- 服务员1 专门服务 A桌
- 服务员2 专门服务 B桌
- 服务员3 专门服务 C桌

**关键点：真正的"同一时刻"在做事，因为人手够。**

#### 对应到程序

| 餐厅场景 | 程序对应 |
|---------|---------|
| 一个服务员切换服务多桌 | **异步（async）**：一个线程，遇到等待就切换做别的 |
| 多个服务员各服务一桌 | **多线程/多进程（并行）**：多个线程/进程真正同时执行 |
| 等厨房做菜 | 等网络请求、等数据库查询（**IO 操作**） |
| 切菜、炒菜（需要动手） | CPU 计算（**CPU 密集型任务**） |

**结论：async（异步）是并发，不是并行。它适合"有很多等待"的场景（比如调 API），不适合"需要大量计算"的场景。**

### ③ 同步 vs 异步：用代码感受区别

```python
# ========== 同步：一个服务员服务完一桌再服务下一桌 ==========
def sync_call_llm():
    # 第1个请求：发出去，傻等3秒，拿到结果
    result1 = call_api("你好")       # 等3秒...
    # 第2个请求：发出去，傻等3秒，拿到结果
    result2 = call_api("天气如何")    # 又等3秒...
    # 总共花了6秒！
    return [result1, result2]

# ========== 异步：一个服务员同时服务多桌 ==========
async def async_call_llm():
    # 第1个请求：发出去，等的时候去做别的
    result1 = await call_api("你好")       # 等3秒（但中间可以做别的事）
    # 第2个请求：发出去，等的时候去做别的
    result2 = await call_api("天气如何")    # 又等3秒（但中间可以做别的事）
    # 如果配合并发（下面会讲），两个请求可以同时发出，总共只花3秒！
    return [result1, result2]
```

> 💡 **注意**：上面这个 async 例子还是串行等待的（一个 await 接一个 await）。后面 11.2 节会讲如何让它们真正"同时发出"。

## 知识点 11.2：并发执行

> 上一节我们知道了异步可以"在等待时做别的事"。但问题来了：如果我有多个互不依赖的任务，怎么让它们**同时开始**，而不是排着队来？

### ① asyncio.gather —— "一起下单，一起等菜，好了全端上来"

#### 🍽️ 餐厅类比

想象你带3个朋友去餐厅，你们同时点了3道菜：
- 你跟服务员说："3道菜一起下给厨房"
- 厨房同时做这3道菜
- 全部做好了，服务员一次性把3道菜都端上来

**这就是 `asyncio.gather` 的工作方式：把多个任务打包，一起执行，等全部完成后，按顺序把结果返回给你。**

#### 代码示例：批量调用 LLM

```python
import asyncio

async def call_llm(prompt: str) -> str:
    """模拟调用 LLM API（耗时1秒）"""
    await asyncio.sleep(1)  # 模拟网络等待
    return f"AI回复: {prompt}"

async def batch_call(prompts: list[str]) -> list[str]:
    """批量调用 LLM"""
    # 把多个调用打包成任务列表
    tasks = [call_llm(prompt) for prompt in prompts]
    
    # gather = "一起发出去，等全部回来"
    results = await asyncio.gather(*tasks)
    
    return results

# 运行
prompts = ["你好", "什么是AI", "今天天气", "写首诗", "再见"]
results = asyncio.run(batch_call(prompts))

# 5个请求，每个1秒，并发执行后总共只花约1秒！
# results = ["AI回复: 你好", "AI回复: 什么是AI", ...]
```

#### 关键点

- `gather(*tasks)` 把任务列表"拆开"传进去（`*` 是解包操作符）
- 所有任务**同时开始**，不是排队
- 返回的结果**按传入顺序排列**（第1个结果对应第1个任务）
- **全部完成才返回**，如果有一个失败，默认会抛异常

### ② asyncio.create_task —— "提前下单，先逛会儿，回头再来取"

#### 🍽️ 餐厅类比

这次你一个人去餐厅：
- 你先跟服务员说："帮我点一份牛排"（**注册任务**）
- 然后你去上厕所、刷手机、喝水（**做别的事**）
- 等你想起来了，回座位看看牛排好了没（**取结果**）

**这就是 `create_task` 的工作方式：提前把任务"注册"到事件循环里让它开始跑，你可以先去做别的事，等需要结果的时候再来取。**

#### 代码示例

```python
async def main():
    # create_task = "提前下单"，任务立刻开始执行
    task1 = asyncio.create_task(call_llm("帮我写代码"))
    task2 = asyncio.create_task(call_llm("帮我写文档"))
    
    # ===== 任务已经在后台跑了，你可以先做别的事 =====
    print("先做点别的事情...")
    await asyncio.sleep(0.5)  # 模拟做一些其他工作
    print("别的事做完了，来取结果")
    
    # 需要结果了，来取
    result1 = await task1  # 如果已经完成了，立刻返回；没完成就等
    result2 = await task2
    
    return result1, result2
```

#### 关键点

- `create_task` 会**立刻**把任务交给事件循环开始执行
- 它返回一个 `Task` 对象，你可以稍后再 `await` 它取结果
- 在 `create_task` 和 `await task` 之间，你可以做其他事
- 如果你 `await task` 时任务已经跑完了，会**立刻**拿到结果，不用等

### ③ gather vs create_task —— 到底用哪个？

| | asyncio.gather | asyncio.create_task |
|--|---------------|-------------------|
| **类比** | 同时点3道菜，坐着等全上来 | 先下单，去逛街，回头来取 |
| **使用场景** | 多个任务互不依赖，想一次拿到所有结果 | 想提前启动任务，中间做别的事再取结果 |
| **结果返回** | 一次性返回所有结果（列表） | 一个一个取，想取哪个取哪个 |
| **灵活度** | 较低（打包等待） | 较高（可以控制每个任务的取结果时机） |

#### 什么时候用哪个？

```python
# 场景1：Agent 需要同时查询3个知识库，全部拿到后再汇总回答
# → 用 gather（需要所有结果才能继续）
async def search_all_knowledge_bases(query: str):
    results = await asyncio.gather(
        search_knowledge_base("知识库A", query),
        search_knowledge_base("知识库B", query),
        search_knowledge_base("知识库C", query),
    )
    return summarize(results)

# 场景2：Agent 提前启动一个耗时的后台任务，同时处理用户交互
# → 用 create_task（先启动，回头再取）
async def handle_user_request(user_input: str):
    # 提前启动 LLM 生成
    llm_task = asyncio.create_task(generate_long_response(user_input))
    
    # 先做一些快速的事情（比如记录日志、更新状态）
    await log_request(user_input)
    await update_user_stats()
    
    # 现在才需要 LLM 的结果
    response = await llm_task
    return response
```

## 知识点 11.3：FastAPI 异步路由

> 现在把异步知识用到 FastAPI 里。FastAPI 天然支持异步，但用错了反而会拖慢程序。这一节我们搞清楚：什么时候该用 async，什么时候不该。

### ① 异步视图函数 —— 最基本的用法

在 FastAPI 里，只要把路由函数声明为 `async def`，它就能在等待 IO 时服务其他请求：

```python
from fastapi import FastAPI
import asyncio

app = FastAPI()

@app.get("/api/v1/chat")
async def chat(message: str):
    # 调用 LLM API 需要等待网络响应
    # 在等待期间，FastAPI 可以处理其他用户的请求
    response = await call_llm_api(message)
    return {"response": response}
```

**这就像餐厅里的服务员：A桌在等菜的时候，服务员去服务B桌，而不是站在A桌旁边傻等。**

### ② 为什么 CPU 密集型任务不能用 async？

这是一个很多人搞混的点。我们先搞清楚 async 的本质：

**async 的超能力 = 在"等待"的时候做别的事**

那问题来了：如果任务本身**不需要等待**，而是一直在**拼命计算**呢？

#### 🍽️ 餐厅类比

- **async 适合的场景**：服务员等厨房做菜（等 IO） → 等的时候去服务别的桌
- **async 不适合的场景**：服务员自己需要切菜炒菜（CPU 计算） → 他两只手都在忙，根本没法去服务别的桌

**CPU 密集型任务（比如大量数学计算、数据处理）会一直占着 CPU，不给事件循环切换的机会。结果就是：其他请求全被卡住了。**

```python
# ❌ 错误示范：在 async 函数里做大量计算
@app.get("/api/v1/process")
async def process(data: str):
    # 这个循环会一直占着 CPU，事件循环无法切换
    # 其他用户的请求全被卡住！
    result = ""
    for i in range(10_000_000):
        result += data
    return {"result": result}
```

### ③ 线程池 —— "把重活交给后厨"

#### 🍽️ 餐厅类比

服务员（主线程/事件循环）不适合干重活（CPU 计算），怎么办？

**交给后厨（线程池）！**

- 服务员接到任务 → 把需要重活的单子递给后厨
- 后厨有多个厨师（多个线程）同时干活
- 服务员继续服务其他桌（处理其他请求）
- 后厨做完了，把结果递给服务员

**这就是线程池的作用：把 CPU 密集型任务交给其他线程去执行，不阻塞主线程（事件循环）。**

#### 代码示例

```python
from fastapi import FastAPI
from concurrent.futures import ThreadPoolExecutor
import asyncio

app = FastAPI()

# 创建一个线程池（4个"厨师"）
executor = ThreadPoolExecutor(max_workers=4)

def heavy_computation(data: str) -> str:
    """CPU 密集型任务（这是普通同步函数，不是 async）"""
    result = ""
    for i in range(10_000_000):
        result += data
    return result

@app.get("/api/v1/compute")
async def compute(data: str):
    # run_in_executor = "把重活交给后厨"
    # 主线程（事件循环）不会被阻塞，可以继续服务其他请求
    loop = asyncio.get_event_loop()
    result = await loop.run_in_executor(executor, heavy_computation, data)
    return {"result": result}
```

#### 总结：什么时候用什么

| 任务类型 | 特点 | 用什么 | 类比 |
|---------|------|--------|------|
| **IO 密集型** | 大部分时间在"等"（网络请求、文件读写、数据库查询） | `async def` + `await` | 服务员等厨房做菜 |
| **CPU 密集型** | 大部分时间在"算"（数学计算、数据处理、字符串拼接） | 线程池 `run_in_executor` | 把重活交给后厨 |

### ④ Agent 场景中的实际应用

```python
from fastapi import FastAPI
from concurrent.futures import ThreadPoolExecutor
import asyncio

app = FastAPI()
executor = ThreadPoolExecutor(max_workers=4)

def preprocess_documents(documents: list[str]) -> list[str]:
    """CPU 密集型：预处理文档（分词、清洗等）"""
    # 这里做大量文本处理计算...
    return [doc.strip().lower() for doc in documents]

async def embed_documents(documents: list[str]) -> list[list[float]]:
    """IO 密集型：调用 Embedding API"""
    # 这里是网络请求，需要等待...
    return await call_embedding_api(documents)

@app.post("/api/v1/index")
async def index_documents(documents: list[str]):
    # 第1步：预处理（CPU 密集型）→ 交给线程池
    loop = asyncio.get_event_loop()
    cleaned = await loop.run_in_executor(executor, preprocess_documents, documents)
    
    # 第2步：生成向量（IO 密集型）→ 用 async
    embeddings = await embed_documents(cleaned)
    
    return {"status": "indexed", "count": len(embeddings)}
```

## 知识点 11.4：异步数据库操作

> 数据库查询是典型的 IO 密集型操作（发请求 → 等数据库返回）。使用异步数据库驱动，可以在等待查询结果时处理其他请求，显著提升吞吐量。

### ① SQLAlchemy 异步模式

```python
from sqlalchemy.ext.asyncio import AsyncSession, create_async_engine
from sqlalchemy.orm import sessionmaker
from sqlalchemy import select

# 注意连接字符串用的是 "sqlite+aiosqlite"（异步驱动）
engine = create_async_engine("sqlite+aiosqlite:///./agent.db")
AsyncSessionLocal = sessionmaker(engine, class_=AsyncSession)

async def get_db():
    """异步数据库会话依赖"""
    async with AsyncSessionLocal() as session:
        yield session

@app.get("/api/v1/conversations")
async def get_conversations(db: AsyncSession = Depends(get_db)):
    # await 等待数据库返回结果，期间可以服务其他请求
    result = await db.execute(select(Conversation))
    return result.scalars().all()
```

> 💡 异步数据库的关键：把同步驱动（如 `sqlite`）换成异步驱动（如 `sqlite+aiosqlite`），把 `Session` 换成 `AsyncSession`，查询时加 `await`。其他写法几乎不变。

## 知识点 11.5：并发控制

> 并发很强大，但不加控制就会出问题。想象一下：如果1000个请求同时打到 LLM API，API 会直接崩溃。所以我们需要"限流"和"超时"。

### ① 信号量 Semaphore —— "餐厅只有5张桌子"

#### 🍽️ 餐厅类比

想象餐厅只有 5 张桌子：
- 前 5 拨客人来了，直接进去坐
- 第 6 拨客人来了，**门口等着**，里面有人走了才能进
- 第 7 拨、第 8 拨……全部排队等

**信号量（Semaphore）就是"桌子数量"。它限制同时执行的任务数量，超出的任务只能排队等待。**

#### 为什么需要限制并发？

在 Agent 场景中：
- LLM API 通常有**速率限制**（比如每秒最多10个请求）
- 同时发太多请求会导致 API 拒绝服务（429 错误）
- 同时跑太多任务会**耗尽系统资源**（内存、网络连接）

#### 代码示例

```python
import asyncio

# 最多同时执行 5 个 LLM 调用（就像餐厅只有5张桌子）
semaphore = asyncio.Semaphore(5)

async def call_llm(prompt: str) -> str:
    """模拟调用 LLM API"""
    await asyncio.sleep(1)
    return f"AI回复: {prompt}"

async def limited_call(prompt: str) -> str:
    """带并发限制的 LLM 调用"""
    async with semaphore:
        # 进入 async with 时"占一张桌子"
        # 如果5张桌子都满了，就在这里等着
        result = await call_llm(prompt)
        # 离开 async with 时"腾出桌子"，下一个排队的人可以进来了
        return result

async def main():
    # 同时发起20个请求，但最多5个同时执行
    prompts = [f"问题{i}" for i in range(20)]
    tasks = [limited_call(prompt) for prompt in prompts]
    results = await asyncio.gather(*tasks)
    # 20个请求，每批5个，大约4批完成，总共约4秒
```

#### 信号量大小怎么定？

| 大小 | 效果 | 风险 |
|------|------|------|
| **太小**（如2） | 并发度低，速度慢 | 资源没充分利用 |
| **太大**（如1000） | 并发度高 | 可能压垮 API 或耗尽资源 |
| **合适**（如 API 限制的一半） | 既快又安全 | 需要根据实际情况调整 |

### ② 超时控制 —— "等外卖超过30分钟就取消"

#### 🍽️ 餐厅类比

你点了一份外卖：
- 正常情况下 20 分钟送到
- 但如果骑手迷路了、商家忘了做……你可能等1小时都等不到
- 所以你会设一个底线："超过30分钟没到就取消订单，换一家"

**超时控制就是给任务设一个"最长等待时间"。防止某个任务无限期卡住，导致整个系统挂起。**

#### 为什么需要超时？

在 Agent 场景中：
- LLM API 偶尔会**响应很慢**（网络问题、服务器繁忙）
- 如果某个请求一直不返回，整个流程就**卡住了**
- 用户不可能无限等待，必须有个兜底

#### 代码示例

```python
import asyncio

async def call_llm(prompt: str) -> str:
    """模拟调用 LLM API"""
    await asyncio.sleep(5)  # 假设这次 API 响应很慢
    return f"AI回复: {prompt}"

async def call_with_timeout(prompt: str, timeout: float = 3.0) -> str:
    """带超时的 LLM 调用"""
    try:
        # wait_for = "最多等 timeout 秒"
        # 如果超时了，会抛出 asyncio.TimeoutError
        result = await asyncio.wait_for(call_llm(prompt), timeout=timeout)
        return result
    except asyncio.TimeoutError:
        # 超时后的处理：返回错误信息、重试、用默认回复等
        return "抱歉，AI 响应超时，请稍后重试"

# 使用
result = await call_with_timeout("你好", timeout=3.0)
# 如果3秒内没返回 → result = "抱歉，AI 响应超时，请稍后重试"
```

### ③ 组合使用：信号量 + 超时 = 健壮的并发调用

在实际 Agent 项目中，通常把两者组合使用：

```python
import asyncio

semaphore = asyncio.Semaphore(5)  # 最多5个并发

async def robust_llm_call(prompt: str, timeout: float = 10.0) -> str:
    """健壮的 LLM 调用：既限并发，又限超时"""
    async with semaphore:  # 限制并发数
        try:
            result = await asyncio.wait_for(  # 限制等待时间
                call_llm(prompt),
                timeout=timeout
            )
            return result
        except asyncio.TimeoutError:
            return f"[超时] 问题: {prompt}"
        except Exception as e:
            return f"[错误] 问题: {prompt} - {str(e)}"

async def batch_call(prompts: list[str]) -> list[str]:
    """批量调用：并发 + 限流 + 超时，一个不少"""
    tasks = [robust_llm_call(prompt) for prompt in prompts]
    results = await asyncio.gather(*tasks)
    return results
```

**这就像一家管理良好的餐厅：**
- **信号量** = 桌子数量有限，不会挤爆
- **超时** = 每桌有用餐时间上限，不会无限占座
- **gather** = 所有菜上齐了再一起端走

## 知识点 11.6：Harness 架构视角分析

### ① 异步并发在 Harness 中的作用

在 Harness 架构中，异步并发不是"锦上添花"，而是"必须有的基础设施"：

| Harness 概念 | 异步并发的作用 | 类比 |
|-------------|--------------|------|
| **边界控制** | 信号量限制并发数量，防止系统过载 | 餐厅桌子数量有上限 |
| **错误恢复** | 超时控制防止长时间阻塞，快速失败并恢复 | 等太久就取消换一家 |
| **上下文管理** | 异步任务的取消和状态追踪 | 记住每桌点了什么菜 |
| **反馈回路** | 并发执行提高响应速度，加速反馈循环 | 多个菜同时做，更快上齐 |

### ② 补偿性代码 vs 系统性工程

| 方式 | 判断 | 说明 |
|------|------|------|
| 使用 `asyncio.gather` 批量并发 | ✅ 系统性工程 | 标准并发执行方式，清晰可控 |
| 使用 `Semaphore` 限制并发 | ✅ 系统性工程 | 优雅的并发控制，不硬编码 |
| 使用 `wait_for` 超时控制 | ✅ 系统性工程 | 防止无限等待，保障系统韧性 |
| 手动创建和管理线程 | ❌ 补偿性代码 | 容易出错，线程泄漏、竞态条件 |
| 在 async 函数中调用同步阻塞代码 | ❌ 补偿性代码 | 阻塞事件循环，拖慢整个系统 |
| 不设超时、不设限流 | ❌ 补偿性代码 | 迟早会出生产事故 |

### ③ 设计思考

当你设计一个 Agent 系统的并发策略时，问自己：

1. **哪些任务是 IO 密集型？** → 用 async/await
2. **哪些任务是 CPU 密集型？** → 用线程池
3. **并发数有上限吗？** → 用 Semaphore
4. **如果某个任务卡住了怎么办？** → 用 timeout
5. **部分失败了怎么处理？** → gather 的 `return_exceptions=True` 参数

## 🤔 启发式思考题

1. **在 Agent 场景中，什么时候应该使用并发执行？什么时候应该串行执行？**
   > 提示：如果多个调用之间没有依赖关系（比如同时查3个知识库），用并发；如果后一步依赖前一步的结果（比如先查知识库再根据结果调 LLM），必须串行。

2. **如何处理批量请求中的部分失败？**
   > 提示：`asyncio.gather(return_exceptions=True)` 可以让失败的任务返回异常对象而不是中断所有任务。想想在 Agent 场景中，部分失败时应该怎么降级处理？

3. **信号量的大小如何确定？过大或过小会有什么问题？**
   > 提示：参考 API 的速率限制、服务器资源、响应时间。过小有点浪费性能，过大会压垮下游服务。

4. **如果一个异步任务无限期阻塞，会对整个系统造成什么影响？如何防范？**
   > 提示：事件循环被卡住，所有请求都无法处理。防范措施：超时、信号量、监控告警。

5. **如何设计一个支持超时和重试的异步调用封装？**
   > 提示：结合 `wait_for`（超时）+ 循环（重试）+ 指数退避（避免连续重试压垮服务）。

## 📌 章节总结

### 知识点在 Agent 项目中的落地位置

| 场景 | 用到的技术 | 为什么 |
|------|-----------|--------|
| 批量调用 LLM API | `asyncio.gather` | 多个独立请求同时发出，大幅缩短等待时间 |
| 并发查询多个知识库 | `asyncio.gather` | 同时搜索，汇总结果 |
| 限制 API 调用频率 | `Semaphore` | 防止超过 API 速率限制 |
| 防止 LLM 调用卡死 | `wait_for` 超时 | 保证用户体验和系统稳定性 |
| 文档预处理（分词、清洗） | 线程池 | CPU 密集型任务，不能阻塞事件循环 |
| 异步数据库读写 | 异步数据库驱动 | IO 密集型，异步可提升吞吐量 |

### 学习重心

| 内容 | 深度 | 理由 |
|------|------|------|
| `asyncio.gather` | ✅ 必须掌握 | 批量并发执行的核心，Agent 几乎必用 |
| `Semaphore` | ✅ 必须掌握 | 并发控制的关键，保护下游服务 |
| 超时控制（`wait_for`） | ✅ 必须掌握 | 防止系统卡死，保障稳定性 |
| `create_task` | ✅ 必须掌握 | 灵活的任务管理，后台任务必备 |
| 线程池（`run_in_executor`） | ⚠️ 适度了解 | 偶尔处理 CPU 密集型任务时需要 |
| 异步数据库 | ⚠️ 适度了解 | 了解概念，用的时候查文档即可 |

### 哪些内容浅尝，哪些必须深挖

- **浅尝**：高级异步模式（如 `asyncio.TaskGroup`、异步生成器），了解基本概念即可
- **深挖**：并发控制策略（信号量、锁、事件）和超时重试处理，这是保障 Agent 系统稳定运行的关键
- **核心心法**：**IO 等待用 async，CPU 计算用线程池，并发数量要限制，等待时间要有上限**
