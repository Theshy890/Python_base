## 知识点 14.1：什么是OpenAPI

### ① 先搞清楚：什么是API文档？

想象你开了一家餐厅，每道菜怎么做、用什么食材、多少钱——你需要写一份**菜单**告诉顾客。

API文档就是**接口的"菜单"**。它告诉调用你的人：

- 这个接口是干什么的？（菜名）
- 需要传什么参数？（食材）
- 返回什么结果？（菜品）
- 怎么调用？（点菜方式）

没有文档的接口，就像一道没写菜名的菜——别人根本不知道它是干嘛的，更不知道怎么用。

### ② 手动写文档的痛点

你可能想：那我手动写个Word文档不就行了？

问题在于：

| 痛点 | 场景 |
|------|------|
| **代码改了，文档忘了改** | 你把参数 `name` 改成了 `username`，文档里还是 `name`，调用方一脸懵 |
| **文档和代码不一致** | 代码里新增了 `temperature` 参数，文档里没写，别人根本不知道 |
| **维护成本极高** | 50个接口，每次改代码都要同步改文档，迟早漏掉 |
| **格式不统一** | 张三写Word，李四写Excel，王五写在代码注释里，乱七八糟 |

一句话：**手动文档永远跟不上代码的变化速度。**

### ③ OpenAPI：让文档"活"起来

OpenAPI 是一种**标准化的API描述格式**。它用JSON或YAML格式，把接口的所有信息都描述清楚——而且是**机器可读**的。

什么意思？就是说程序能自动读懂这份文档，不需要人去翻译。

> **类比：OpenAPI = 接口的"身份证"**
>
> 就像身份证包含了你的姓名、生日、地址、照片一样，OpenAPI包含了接口的：
> - 接口路径（`/api/v1/chat`）
> - 请求方法（GET、POST）
> - 参数信息（名称、类型、是否必填）
> - 返回格式（返回什么字段、什么类型）
> - 其他信息（接口描述、版本、作者）

有了这份"身份证"，各种工具就能自动生成漂亮的网页文档、测试界面、甚至客户端代码。

### ④ 核心价值

| 价值 | 说明 |
|------|------|
| **自动文档** | 代码就是文档，改了代码文档自动更新，永远不会不一致 |
| **交互式测试** | 在文档网页上直接点按钮测试接口，不需要额外工具 |
| **客户端生成** | 根据OpenAPI规范，自动生成Python、JavaScript等语言的客户端代码 |
| **标准化** | 业界通用标准，团队协作、对外提供API都有统一格式 |

## 知识点 14.2：FastAPI自动文档

### ① Swagger UI是什么？

Swagger UI 是一个**可以在线测试API的网页界面**。

> **类比：餐厅的"试吃台"**
>
> 你去餐厅，看到菜单上每道菜都有图片介绍。旁边还有个"试吃台"，你可以直接尝一口，看看味道怎么样。
>
> Swagger UI 就是这个试吃台：
> - 每道菜 = 每个API接口
> - 菜品介绍 = 接口文档（参数、返回值）
> - 试吃 = 在网页上直接填参数、点按钮、看返回结果

你不需要写任何测试代码，打开浏览器就能测试接口。

### ② FastAPI为什么能自动生成文档？

因为 FastAPI 充分利用了 Python 的**类型注解**和 **Pydantic 模型**。

你写代码时已经声明了：
- 参数类型是 `str`、`int`、`float`
- 参数是否必填（有没有默认值）
- 返回值用什么模型

这些信息已经**足够**生成一份完整的API文档了！FastAPI 只是把你已经写好的信息"翻译"成 OpenAPI 格式，再渲染成漂亮的网页。

**你不需要额外写任何文档代码——代码本身就是文档。**

### ③ 访问文档

```python
from fastapi import FastAPI

app = FastAPI(title="Agent服务", version="1.0", description="LLM Agent后端服务")

@app.get("/api/v1/chat")
async def chat(message: str):
    """对话接口"""
    return {"response": f"AI收到: {message}"}
```

启动服务后，访问以下地址：

| 地址 | 说明 |
|------|------|
| `http://localhost:8000/docs` | **Swagger UI**：交互式文档，可以直接测试接口 |
| `http://localhost:8000/redoc` | **ReDoc**：只读文档，适合查看和打印 |

打开 `/docs`，你会看到一个网页，里面列出了所有接口，点开就能填参数、点"Execute"测试——这就是 Swagger UI 的威力。

### ④ 文档元信息

你可以在创建 FastAPI 应用时设置文档的"封面信息"：

```python
app = FastAPI(
    title="Agent后端服务",          # 文档标题
    version="1.0.0",                # 版本号
    description="基于FastAPI构建的LLM Agent后端服务",  # 详细描述
    terms_of_service="https://example.com/terms",
    contact={
        "name": "API Support",
        "email": "support@example.com"
    },
    license_info={
        "name": "MIT License",
        "url": "https://opensource.org/licenses/MIT"
    }
)
```

这些信息会显示在文档页面的顶部，就像书的封面——告诉别人这是谁的服务、什么版本、怎么联系你。

## 知识点 14.3：自定义接口文档

### ① summary 和 description 的区别

你可能注意到，接口描述有两个参数：`summary` 和 `description`。它们有什么区别？

> **类比：summary = 菜名，description = 菜品介绍**
>
> - `summary`：一句话标题，像菜单上的"宫保鸡丁"——**短，让人一眼看懂**
> - `description`：详细说明，像菜单下面的"精选鸡腿肉，搭配花生、干辣椒爆炒，口感鲜嫩微辣"——**长，让人了解细节**

```python
from fastapi import FastAPI

app = FastAPI()

@app.post(
    "/api/v1/chat",
    summary="大模型对话",                                    # 菜名：一句话
    description="与大模型进行多轮对话，支持上下文记忆和流式输出。可配置温度和token上限。",  # 菜品介绍：详细说明
    response_description="AI回复内容"                        # 告诉用户返回什么
)
async def chat(message: str):
    return {"response": f"AI收到: {message}"}
```

### ② response_description 的作用

`response_description` 是告诉文档阅读者：**这个接口成功时返回什么？**

- `summary` 描述接口做什么
- `description` 描述接口怎么做
- `response_description` 描述接口返回什么

三者配合，调用方看文档时就能完整了解一个接口。

### ③ 参数描述

除了接口级别的描述，你还可以给**每个参数**加描述：

```python
from fastapi import FastAPI, Query, Body

app = FastAPI()

@app.post("/api/v1/chat")
async def chat(
    message: str = Body(..., description="用户消息，不能为空"),
    max_tokens: int = Body(1024, description="最大返回token数", ge=1, le=4096),
    temperature: float = Body(0.7, description="温度参数，控制随机性", ge=0.0, le=2.0)
):
    return {"message": message}
```

在 Swagger UI 中，每个参数旁边都会显示你写的 `description`，调用方一看就知道该传什么值。

> **类比：参数描述 = 菜单上标注的"辣度、份量、过敏原"**
>
> 好的菜单不仅告诉你菜名，还告诉你细节——参数描述也是同理。

## 知识点 14.4：响应模型文档

当你用 Pydantic 模型定义返回值时，FastAPI 会自动把模型的字段信息写进文档：

```python
from fastapi import FastAPI
from pydantic import BaseModel, Field

app = FastAPI()

class ChatResponse(BaseModel):
    response: str = Field(..., description="AI回复内容")
    status: str = Field("success", description="请求状态")
    token_usage: int | None = Field(None, description="使用的token数量")

@app.post("/api/v1/chat", response_model=ChatResponse)
async def chat(message: str):
    return ChatResponse(response=f"AI收到: {message}")
```

在 Swagger UI 中，会自动显示返回值的结构：

```json
{
    "response": "AI收到: 你好",
    "status": "success",
    "token_usage": 42
}
```

每个字段旁边的 `description` 也会显示在文档中，调用方一看就知道返回值的含义。

## 知识点 14.5：API分组

### ① 为什么要分组？

> **类比：超市分区**
>
> 想象你走进一家超市，所有商品都堆在一起——生鲜、饮料、零食、日用品混成一堆。你想买瓶水，得翻遍整个超市。
>
> 所以超市都有分区：生鲜区、饮料区、零食区、日用品区。每个区域放相关的商品，你一眼就能找到想去的地方。

API分组也是同理。当你的项目有几十个接口时：

- 对话相关的接口放一组
- Agent管理相关的接口放一组
- 知识库相关的接口放一组

这样在文档中，接口就会按组分类显示，而不是乱成一团。

### ② APIRouter：把相关接口打包在一起

`APIRouter` 就是一个"打包工具"——把相关的接口打包成一个模块：

```python
from fastapi import FastAPI, APIRouter

app = FastAPI()

# 对话模块：所有对话相关的接口
chat_router = APIRouter(prefix="/api/v1/chat", tags=["对话"])

# Agent管理模块：所有Agent相关的接口
agent_router = APIRouter(prefix="/api/v1/agents", tags=["Agent管理"])

@chat_router.post("/")
async def chat(message: str):
    return {"response": f"AI收到: {message}"}

@chat_router.get("/history")
async def get_history():
    return {"history": []}

@agent_router.get("/")
async def get_agents():
    return {"agents": []}

@agent_router.post("/")
async def create_agent(name: str):
    return {"agent": name}

# 把路由模块注册到主应用
app.include_router(chat_router)
app.include_router(agent_router)
```

`prefix` 给这组接口统一加路径前缀，`tags` 给这组接口打上标签。

### ③ tags：给接口打标签

`tags` 决定了接口在文档中**属于哪个分组**。相同 `tags` 的接口会显示在一起：

```python
@app.get("/api/v1/conversations", tags=["对话管理"])
async def get_conversations():
    """获取对话列表"""
    pass

@app.post("/api/v1/conversations", tags=["对话管理"])
async def create_conversation():
    """创建新对话"""
    pass

@app.delete("/api/v1/conversations/{id}", tags=["对话管理"])
async def delete_conversation(id: int):
    """删除对话"""
    pass
```

在 Swagger UI 中，这三个接口都会归到"对话管理"这个分组下，一目了然。

> **小结：**
> - `APIRouter` = 把接口打包（适合按模块拆分代码文件）
> - `tags` = 给接口打标签（决定文档中怎么分组显示）
> - 两者配合使用效果最好：用 `APIRouter` 组织代码，用 `tags` 组织文档

## 知识点 14.6：Harness架构视角分析

### ① 文档在Harness中的作用

- **边界控制**：文档定义了API的使用边界——哪些接口可用、参数有什么限制、返回什么格式。Agent调用API时，文档就是它的"操作手册"。
- **错误恢复**：交互式文档（Swagger UI）便于快速调试和测试。Agent出错时，开发者可以直接在文档页面复现问题，不需要写测试脚本。
- **上下文管理**：文档是API的"活文档"，始终和代码保持同步。Agent的上下文窗口有限，清晰的文档能帮助Agent快速理解接口用途，减少试错。
- **反馈回路**：文档便于团队协作——前端开发者、Agent开发者、测试人员都通过文档了解接口，形成高效的反馈回路。

### ② 文档质量对Agent的影响

在Agent/LLM场景下，API文档的质量直接影响Agent的表现：

| 文档质量 | Agent表现 |
|----------|-----------|
| 参数描述清晰 | Agent能正确构造请求 |
| 返回值描述完整 | Agent能正确解析响应 |
| 接口分组合理 | Agent能快速找到需要的接口 |
| 缺少描述或描述模糊 | Agent可能传错参数、误解返回值 |

**好的API文档 = Agent的"使用说明书"，文档越清晰，Agent越可靠。**

## 📌 章节总结

### 知识点在Agent项目中的落地位置

- **API文档**：自动生成和定制接口文档，让Agent能"读懂"你的接口
- **接口测试**：在Swagger UI中直接测试API，快速验证Agent的调用是否正确
- **团队协作**：前端和后端通过文档协作，Agent开发者也能快速了解后端能力

### 学习重心

| 内容 | 深度 | 理由 |
|------|------|------|
| 自动文档 | ⚠️ 适度了解 | 开发效率工具，FastAPI默认就能用 |
| 自定义描述 | ⭐ 建议掌握 | 描述质量直接影响Agent的调用准确率 |
| API分组 | ⚠️ 适度了解 | 接口多了之后才需要，但要知道怎么分 |

### 哪些内容浅尝，哪些必须深挖

- **浅尝**：高级文档定制（如自定义OpenAPI schema、自定义Swagger UI主题），了解即可
- **深挖**：参数描述和响应模型描述——这些直接影响Agent能不能正确理解和调用你的接口
