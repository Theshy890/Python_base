## 知识点 3.1：HTTP方法与路由

### ① 先搞懂"什么是路由"

在写代码之前，我们先来理解一个核心概念：**路由**。

想象你走进一家大餐厅。餐厅里有不同的区域：

- 🥗 **凉菜区** → 你想吃凉菜，就去这个区域
- 🔥 **热菜区** → 你想吃热菜，就去这个区域
- 🥤 **饮料区** → 你想喝东西，就去这个区域

每个区域就像一个"入口"，你走到对应的区域，就能得到对应的服务。

**API中的路由就是这些"区域入口"。**

当你在手机上点"查看我的对话列表"，手机需要知道去服务器的哪个"入口"拿数据——这个入口就是路由。路由本质上就是一个**URL地址**，比如 `/api/v1/conversations` 就是"对话列表"这个功能的入口。

再进一步：光找到入口还不够，你还得告诉服务员你要**做什么**。同样是去"对话区"，你可能是想：
- **看看**有哪些对话（查）
- **新建**一个对话（增）
- **修改**某个对话的标题（改）
- **删除**某个对话（删）

这四种操作，在HTTP协议中对应四种不同的**方法（Method）**。

### ② 四种HTTP方法——生活化类比

| HTTP方法 | 作用 | 生活类比 | 详细说明 |
|----------|------|----------|----------|
| **GET** | 获取/查看 | 🏫 **去图书馆查书**：你走到书架前，找到一本书翻看，书还是原样，你只是"看看" | GET只读取数据，不修改任何东西。就像你去图书馆查资料，看完放回去，不会影响书本身 |
| **POST** | 创建/提交 | 🏦 **去银行开户**：你带着身份证去银行，填写表格，银行给你开一个新账户——从无到有，"创建"了一个新东西 | POST用来提交新数据，在服务器上创建一个新的资源。就像开户一样，之前不存在，提交后就有了 |
| **PUT** | 修改/更新 | 🔑 **改银行卡密码**：你的账户已经存在了，你去银行把旧密码改成新密码——东西还在，只是"更新"了部分内容 | PUT用来修改已有的资源。就像改密码，账户不变，但里面的信息被更新了 |
| **DELETE** | 删除 | 🚪 **注销手机号**：你打电话给运营商，把不用的手机号注销掉——这个东西从此"消失"了 | DELETE用来删除服务器上的资源。就像注销账户，一旦删除就没了 |

### ③ 为什么不同操作要用不同方法？

你可能会问：反正都是发请求，为什么非要分GET、POST、PUT、DELETE？全用GET不行吗？

**三个原因：**

**1. 安全性**
想象一下：如果所有操作都用GET，那浏览器预加载页面时可能不小心触发了"删除"操作！分开方法后，服务器可以设置"GET请求只允许查看，不允许修改"，这就安全多了。

**2. 语义清晰**
看到 `GET /conversations`，任何程序员都知道这是"获取对话列表"；看到 `DELETE /conversations/123`，就知道这是"删除123号对话"。不用看代码，光看URL就知道在干什么。

**3. 工具友好**
浏览器的缓存机制会缓存GET请求（因为GET不会改数据），但不会缓存POST请求。分清楚方法，能让系统自动帮你做很多优化。

### ④ 代码示例：Agent对话服务的路由

理解了上面的概念，再来看代码就很自然了：

```python
from fastapi import FastAPI

app = FastAPI()

# GET = "查看"对话列表（去图书馆查书）
@app.get("/api/v1/conversations")
async def get_conversations():
    """获取所有对话列表"""
    return {"conversations": []}

# POST = "创建"一个新对话（去银行开户）
@app.post("/api/v1/conversations")
async def create_conversation():
    """创建新对话"""
    return {"conversation_id": "conv_001"}

# GET + 路径参数 = 查看某个具体对话的详情
@app.get("/api/v1/conversations/{conv_id}")
async def get_conversation(conv_id: str):
    """获取单个对话详情"""
    return {"conversation_id": conv_id}

# PUT = "修改"某个对话（改密码）
@app.put("/api/v1/conversations/{conv_id}")
async def update_conversation(conv_id: str):
    """更新对话"""
    return {"conversation_id": conv_id, "updated": True}

# DELETE = "删除"某个对话（注销账户）
@app.delete("/api/v1/conversations/{conv_id}")
async def delete_conversation(conv_id: str):
    """删除对话"""
    return {"conversation_id": conv_id, "deleted": True}
```

> 💡 **注意看规律**：同一个URL地址 `/api/v1/conversations`，搭配不同的HTTP方法（GET vs POST），就是完全不同的功能。就像同一个窗口，你可以去"存款"也可以去"取款"——关键看你做什么操作。

### ⑤ Harness架构视角

| 架构原则 | 在路由中的体现 |
|----------|----------------|
| **边界控制** | 路由定义了外部能访问哪些功能，没定义的路由就无法访问，这就是"边界" |
| **错误恢复** | 如果请求了一个不存在的路由，FastAPI自动返回404错误，不会让系统崩溃 |
| **反馈回路** | 每个路由都可以单独记录日志、监控性能，方便追踪问题 |

## 知识点 3.2：路径参数

### ① 先搞懂"什么是路径参数"

上一节我们知道了路由就是URL地址。但有时候，我们不想为每个资源单独写一个路由。

比如你有100个对话，难道要写100个路由吗？

```
/conversations/conv_001
/conversations/conv_002
/conversations/conv_003
...（还有97个）
```

当然不用！**路径参数**就是解决这个问题的——它在URL中挖一个"坑"，让这个位置可以填入不同的值。

### ② 生活化类比：快递单号

想象你去快递驿站取快递：

- 快递驿站有一个统一的地址：**XX路XX号快递驿站**（这就是路由）
- 但你的快递不是随便拿的，你需要报出你的**快递单号**（这就是路径参数）
- 每个人的快递单号不同，但取件流程是一样的

```
快递驿站地址：XX路XX号          →  路由：/api/v1/conversations/
你的快递单号：SF1234567890      →  路径参数：conv_001
完整取件请求：去XX路XX号，报单号SF1234567890
完整API请求：GET /api/v1/conversations/conv_001
```

### ③ 语法：{花括号}标记"坑位"

在FastAPI中，用**花括号 `{}`** 来标记URL中的"坑位"：

```python
@app.get("/api/v1/conversations/{conv_id}")
async def get_conversation(conv_id: str):
    return {"conversation_id": conv_id}
```

**这里有两个 `conv_id`，它们是什么关系？**

| 位置 | 写法 | 作用 |
|------|------|------|
| URL里的 `{conv_id}` | 花括号包裹 | 告诉FastAPI："这个位置是一个变量，可以接受任何值" |
| 函数参数 `conv_id: str` | 函数定义里 | 告诉Python："把URL里那个位置拿到的值，传给我这个变量" |

**FastAPI会自动把两者关联起来**——名字相同就会自动匹配。

举个例子：
```
用户访问：GET /api/v1/conversations/conv_001
                                    ↑
                            这个值被提取出来
                                    ↓
FastAPI自动执行：get_conversation(conv_id="conv_001")
                                    ↓
函数返回：{"conversation_id": "conv_001"}
```

### ④ 路径参数支持的类型

路径参数不只是字符串，FastAPI会自动根据你声明的类型进行转换和校验：

| 类型 | 示例路由 | 能匹配的URL | 不能匹配的URL |
|------|----------|-------------|---------------|
| `str` | `/users/{name}` | `/users/小明` ✅ | 都能匹配（str是万能型） |
| `int` | `/tasks/{task_id}` | `/tasks/123` ✅ | `/tasks/abc` ❌（不是数字） |
| `float` | `/config/{rate}` | `/config/0.75` ✅ | `/config/abc` ❌（不是小数） |

```python
# int类型：自动把URL中的数字转成整数
@app.get("/api/v1/tasks/{task_id}")
async def get_task(task_id: int):
    # 如果用户访问 /tasks/abc，FastAPI自动报错，不会进入这个函数
    return {"task_id": task_id, "type": type(task_id).__name__}
```

### ⑤ 多个路径参数 & Agent场景

一条URL里可以有多个"坑位"，就像快递单号可以包含"区域+编号"：

```python
@app.get("/api/v1/agents/{agent_id}/tasks/{task_id}")
async def get_agent_task(agent_id: str, task_id: str):
    """获取某个Agent的特定任务"""
    return {"agent_id": agent_id, "task_id": task_id}

# 访问：GET /api/v1/agents/agent_001/tasks/task_042
# 返回：{"agent_id": "agent_001", "task_id": "task_042"}
```

> 💡 **理解要点**：路径参数的本质是——**"我在找谁"**。它用来唯一标识一个资源，就像快递单号唯一标识一个包裹。

## 知识点 3.3：查询参数

### ① 先搞懂"什么是查询参数"

如果说路径参数是"找谁"，那查询参数就是"**怎么找**"。

想象你在网上买衣服：

- 你打开了"女装"页面（这相当于**路径参数**——确定了你要看哪类商品）
- 然后你开始筛选：价格100-200、颜色红色、按销量排序（这些就是**查询参数**——进一步缩小范围）

查询参数长什么样？你一定见过：

```
https://www.taobao.com/search?q=连衣裙&color=红色&sort=sales
                                    ↑
                              这个?后面的部分就是查询参数
```

格式是：`?键=值&键=值&键=值`，用 `?` 和URL主体隔开，多个参数之间用 `&` 连接。

### ② 路径参数 vs 查询参数：一张图说清楚

```
GET /api/v1/conversations/conv_001/messages?page=2&limit=20
    └─────────── URL主体 ──────────┘  └── 查询参数 ──┘
         │                    │              │
      固定部分           路径参数         筛选条件
     "/api/v1/"     "conv_001"      "page=2, limit=20"
    （路由前缀）   （找哪个对话）    （怎么筛选消息）
```

| 对比维度 | 路径参数 | 查询参数 |
|----------|----------|----------|
| 位置 | 嵌在URL路径中间 | 挂在URL末尾，`?` 后面 |
| 作用 | **找谁**——确定具体是哪个资源 | **怎么找**——筛选、排序、分页 |
| 是否必须 | 必须提供 | 可以有默认值，不填也行 |
| 类比 | 快递单号（确定取哪个包裹） | 网购筛选条件（缩小范围） |

### ③ 代码示例

```python
# 查询参数：函数中有默认值的参数
@app.get("/api/v1/conversations")
async def get_conversations(page: int = 1, page_size: int = 10):
    """获取对话列表，支持分页"""
    return {"page": page, "page_size": page_size}
```

**这里的关键**：`page` 和 `page_size` **没有**出现在URL的 `{}` 里，但出现在了函数参数中——FastAPI就会自动把它们识别为**查询参数**。

```
访问：GET /api/v1/conversations?page=2&page_size=20
                                    ↑
                        FastAPI自动提取：page=2, page_size=20
函数执行：get_conversations(page=2, page_size=20)
返回：{"page": 2, "page_size": 20}

如果没传查询参数：GET /api/v1/conversations
函数执行：get_conversations(page=1, page_size=10)  ← 使用默认值
```

### ④ 必填 vs 可选

```python
@app.get("/api/v1/search")
async def search(
    query: str,                    # 没有默认值 → 必填！不传就报错
    max_results: int = 10,         # 有默认值 → 可选，不传就用10
    filter_type: str | None = None # 可以是None → 可选，不传就是None
):
    return {"query": query, "max_results": max_results, "filter_type": filter_type}
```

> 💡 **简单规则**：函数参数有默认值 = 可选查询参数；没有默认值 = 必填查询参数。

### ⑤ Agent场景示例

```python
@app.get("/api/v1/chat/completions")
async def chat_completions(
    prompt: str,                       # 必填：用户的问题
    model: str = "gpt-3.5-turbo",      # 可选：默认用这个模型
    max_tokens: int = 1024,            # 可选：默认最多生成1024个token
    temperature: float = 0.7           # 可选：默认创造性适中
):
    """模拟大模型对话接口"""
    return {
        "prompt": prompt,
        "model": model,
        "max_tokens": max_tokens,
        "temperature": temperature
    }

# 最简单的调用：GET /api/v1/chat/completions?prompt=你好
# 完整调用：GET /api/v1/chat/completions?prompt=写首诗&model=gpt-4&max_tokens=2048&temperature=0.9
```

## 知识点 3.4：请求体（Body）

### ① 先搞懂"什么是请求体"

我们已经学了两种传参方式：
- **路径参数**：嵌在URL里（"找谁"）
- **查询参数**：挂在URL末尾（"怎么找"）

这两种方式有个共同点：**都写在URL里，肉眼可见**。

但有些数据不适合放在URL里——比如一大段聊天消息、一份JSON配置、一张图片的数据。这时候就需要**请求体（Body）**。

### ② 生活化类比：寄信

想象你要寄一封信：

```
┌─────────────────────────────────────┐
│  信封（外面能看到的）                  │
│                                     │
│  收件地址：北京市海淀区XX路XX号        │  ← 这就是 URL（路由）
│  收件人：张三                         │  ← 这就是 路径参数
│  挂号信/平信：挂号                     │  ← 这就是 HTTP方法
│                                     │
│  ─ ─ ─ ─ ─ 信封内 ─ ─ ─ ─ ─ ─ ─ ─  │
│                                     │
│  信的内容：                            │
│  "张三你好，我想跟你讨论一下           │  ← 这就是 请求体（Body）
│   项目的事情……"（可能写了好几页）      │     信封外面看不到，
│                                     │     要拆开才能看到
└─────────────────────────────────────┘
```

| 寄信 | API请求 |
|------|---------|
| 信封上的地址 | URL（路由 + 路径参数） |
| 寄信方式（挂号/平信） | HTTP方法（GET/POST/PUT/DELETE） |
| 信里面的内容 | 请求体（Body） |

### ③ 为什么复杂数据要用Body？

你可能会问：查询参数也能传数据，为什么还要搞个Body？

| 对比维度 | 查询参数 | 请求体（Body） |
|----------|----------|----------------|
| 可见性 | 写在URL里，所有人都能看到 | 藏在请求内部，URL里看不到 |
| 数据量 | 有长度限制（浏览器一般限制2000字符左右） | 理论上没有上限，可以传很大的数据 |
| 数据格式 | 只能是简单的键值对（`key=value`） | 支持JSON等复杂格式，可以嵌套、可以传数组 |
| 适用场景 | 简单的筛选条件、分页参数 | 复杂的结构化数据、大量内容 |

**在Agent/LLM场景中**，用户发的一条消息可能很长，对话历史是一个嵌套的JSON数组——这些都必须用Body来传。

### ④ 代码示例

```python
from fastapi import FastAPI, Body

app = FastAPI()

@app.post("/api/v1/chat")
async def chat(
    message: str = Body(..., description="用户消息"),
    history: list = Body([], description="对话历史")
):
    return {"message": message, "history_length": len(history)}
```

客户端发送请求时，数据放在Body里（JSON格式）：

```json
{
    "message": "你好，请帮我分析一下这段代码",
    "history": [
        {"role": "user", "content": "之前的消息"},
        {"role": "assistant", "content": "之前的回复"}
    ]
}
```

> 💡 **注意**：Body数据不出现在URL里，所以你看不到它。它藏在HTTP请求的"信封内部"。

### ⑤ Body的高级用法：数据校验

```python
@app.post("/api/v1/chat")
async def chat(
    message: str = Body(..., embed=True),
    max_tokens: int = Body(1024, ge=1, le=4096)
):
    """
    embed=True: 即使只有一个参数，也要求用JSON格式包装
    ge=1, le=4096: 限制max_tokens必须在1到4096之间
    """
    return {"message": message}
```

如果用户传了 `max_tokens: 9999`，FastAPI会自动拒绝并返回错误提示——不用你手动写校验代码。

## 知识点 3.5：多种参数组合

### ① 综合运用

实际项目中，一个接口往往同时用到多种参数。来看一个完整的Agent执行接口：

```python
from fastapi import Query, Body

@app.post("/api/v1/agents/{agent_id}/execute")
async def execute_agent(
    agent_id: str,                      # 路径参数：执行哪个Agent
    task_type: str = Query(..., description="任务类型"),  # 查询参数：什么类型的任务
    config: dict = Body(..., description="任务配置")       # 请求体：详细的配置数据
):
    """执行Agent任务"""
    return {
        "agent_id": agent_id,
        "task_type": task_type,
        "config": config
    }
```

调用这个接口时，三种参数各就各位：

```
POST /api/v1/agents/agent_001/execute?task_type=analysis
     └────── 路径参数 ──────┘ └─查询参数─┘
     agent_id = "agent_001"    task_type = "analysis"

请求体（Body）：
{
    "param1": "value1",
    "param2": "value2"
}
     └── config = {"param1": "value1", "param2": "value2"}
```

### ② 三种参数对比总结

| 参数类型 | 位置 | 作用 | 类比 | 适用场景 |
|----------|------|------|------|----------|
| **路径参数** | URL路径中 `{xxx}` | **找谁**——标识具体资源 | 快递单号 | 资源ID、名称 |
| **查询参数** | URL末尾 `?xxx=yyy` | **怎么找**——筛选、分页 | 网购筛选条件 | 过滤、排序、配置选项 |
| **请求体** | 请求内部（不可见） | **做什么**——传递完整数据 | 信的内容 | 复杂数据、大量信息 |

## 知识点 3.6：路由组织与版本控制

### ① 为什么需要版本控制？

想象你的Agent服务上线后，有100个用户在使用。现在你想升级接口，但新版本不兼容旧版——怎么办？直接把旧接口改掉，100个用户全崩了。

解决办法：**版本控制**——同时保留多个版本的接口。

```python
# 方式一：路径版本（推荐，最直观）
@app.get("/api/v1/chat")
async def chat_v1():
    return {"version": "v1"}

@app.get("/api/v2/chat")
async def chat_v2():
    return {"version": "v2"}

# 方式二：查询参数版本
@app.get("/api/chat")
async def chat(version: str = "v1"):
    if version == "v1":
        return {"version": "v1"}
    return {"version": "v2"}
```

### ② Agent服务路由规划

一个典型的Agent服务，路由可以这样组织：

```
/api/v1/
├── chat                    # 对话接口（用户发消息的地方）
├── conversations           # 对话管理（增删改查对话列表）
│   └── {conv_id}          # 单个对话（对某个对话进行操作）
├── agents                 # Agent管理（管理你的Agent们）
│   ├── {agent_id}         # 单个Agent（查看/修改某个Agent）
│   └── {agent_id}/execute # 执行Agent（让某个Agent干活）
├── tools                  # 工具管理（Agent可以调用的工具）
└── config                 # 配置管理（系统设置）
```

> 💡 这种层级结构就像公司的组织架构：先找到部门（agents），再找到具体的人（agent_id），然后让他做事（execute）。

## 知识点 3.7：Harness架构视角分析

### ① 路由在Harness中的作用

| 架构原则 | 在路由中的体现 | 通俗解释 |
|----------|----------------|----------|
| **边界控制** | 路由定义了API的访问边界 | 就像大楼的门禁卡——只能去你被授权的楼层，没定义的路由就无法访问 |
| **错误恢复** | 路由级别的异常处理可以统一捕获错误 | 就像消防通道——某个房间出问题了，有统一的疏散路线，不会整栋楼塌掉 |
| **上下文管理** | 通过路径参数传递资源标识 | 就像病历号——医生通过病历号知道在治哪个病人，不会搞混 |
| **反馈回路** | 清晰的路由结构便于监控和日志记录 | 就像门牌号——出了问题能快速定位是哪个房间，而不是"某处某处" |

### ② 参数校验在Harness中的作用

| 架构原则 | 在参数校验中的体现 | 通俗解释 |
|----------|---------------------|----------|
| **边界控制** | 参数类型和范围约束限制了合法值 | 就像电梯的载重限制——超过1000kg就不走，防止出事 |
| **错误恢复** | 提前拒绝非法输入，避免后续处理出错 | 就像门口的安检——危险品在门口就拦下来，不让带进大楼 |
| **上下文管理** | 结构化的参数便于上下文传递和验证 | 就像表格的必填项——每个字段都有明确含义，不会传错信息 |

### ③ 补偿性代码 vs 系统性工程

| 方式 | 判断 | 说明 |
|------|------|------|
| 使用FastAPI路由装饰器 | ✅ 系统性工程 | 框架提供标准化路由机制，不用自己解析URL |
| 使用参数类型注解 | ✅ 系统性工程 | 自动校验类型，不用手动写 `if type(x) != int` |
| 手动解析URL参数 | ❌ 补偿性代码 | 自己用字符串切割来提取参数，容易出错，重复劳动 |
| 使用单一POST接口 | ❌ 补偿性代码 | 所有操作都走同一个接口，违反RESTful设计，难以维护 |

## 📌 章节总结

### 一句话回顾

- **路由** = 餐厅的区域划分，告诉客户端"去哪个入口"
- **HTTP方法** = 你要做什么操作（查/增/改/删）
- **路径参数** = 快递单号，确定"找谁"
- **查询参数** = 网购筛选条件，确定"怎么找"
- **请求体** = 信的内容，传递"完整数据"

### 知识点在Agent项目中的落地位置

- **对话接口**：`POST /api/v1/chat` 处理用户消息（Body传消息内容）
- **对话管理**：`GET/POST/PUT/DELETE /api/v1/conversations` 管理对话生命周期
- **Agent执行**：`POST /api/v1/agents/{agent_id}/execute` 执行Agent任务（路径参数确定哪个Agent）

### 学习重心

| 内容 | 深度 | 理由 |
|------|------|------|
| 路径参数 | ✅ 必须掌握 | 资源标识的核心方式，每个项目都用 |
| 查询参数 | ✅ 必须掌握 | 过滤和分页的常用方式，几乎每个GET接口都有 |
| 请求体 | ✅ 必须掌握 | 传递复杂数据的标准方式，Agent场景必备 |
| 参数组合 | ✅ 必须掌握 | 实际项目中经常遇到，要分清什么参数放哪里 |
| 版本控制 | ⚡ 了解即可 | 项目初期不急，用户量上来后再考虑 |

### 哪些内容浅尝，哪些必须深挖

- **浅尝**：不常用的HTTP方法（HEAD、OPTIONS），了解即可
- **深挖**：参数校验和约束（后续Pydantic章节会深入），这是保障API安全的关键
