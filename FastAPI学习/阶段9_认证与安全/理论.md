# 阶段9：认证与安全

> 在之前的阶段中，我们写的 API 是"谁都能访问"的——就像一扇没有锁的门。
> 但在真实项目中，你必须搞清楚"谁在调用"、"他能做什么"。
> 这就是**认证与安全**要解决的问题。

## 知识点 9.1：认证基础

### ① 什么是认证？——先用生活场景理解

想象你住在一个小区里：

- **进小区大门**时，保安让你刷卡 → 门禁系统确认"你是这个小区的住户" → 这就是**认证（Authentication）**
- **进不同楼栋**时，有些楼栋需要额外刷楼层权限 → 系统确认"你能进几楼" → 这是**授权（Authorization）**

用一句话区分它们：

| 概念 | 英文 | 一句话解释 | 生活类比 |
|------|------|-----------|----------|
| **认证** | Authentication | 证明"你是谁" | 进小区刷卡，保安认你的脸 |
| **授权** | Authorization | 确定"你能做什么" | 进了小区后，你只能进自己那栋楼 |

> 🧠 **记住这个区别**：认证是第一步（你是谁），授权是第二步（你能干嘛）。
> 先认证，后授权。就像先验身份，再给权限。

### ② 常见的认证方式——逐个击破

别被这些名词吓到，我们一个一个来，每个都用生活中的东西类比：

#### 🔑 API Key —— "门禁卡"

**是什么**：一串固定的密钥字符串，类似于小区发给你的门禁卡。

**怎么用**：每次调用 API 时，把这串密钥带上，服务器一看"哦，这个密钥我认识，放行"。

**适合场景**：服务与服务之间的调用。比如你的 Agent 后端去调用大模型 API（OpenAI、百度文心等），每次请求都带上 API Key。

**特点**：
- ✅ 简单粗暴，容易理解
- ❌ 没有过期时间（除非你手动管理）
- ❌ 不区分"是谁在用"，只认卡不认人

#### 🎫 Bearer Token —— "一次性访客证"

**是什么**：一种令牌格式。"Bearer"的意思是"持有者"——谁持有这个 Token，谁就被认为是合法用户。

**怎么用**：请求时在 Header 里写上 `Authorization: Bearer <你的Token>`，就像访客进门时出示访客证。

**适合场景**：用户登录后，服务器发一个 Token 给前端，前端后续每次请求都带着这个 Token。

**特点**：
- ✅ 可以设置过期时间
- ✅ 比 API Key 更灵活
- ❌ Token 被偷了就麻烦了

#### 🏢 OAuth2 —— "第三方授权协议"

**是什么**：一个授权框架，最典型的场景就是"用微信登录"、"用 GitHub 登录"。

**怎么用**：你不需要自己实现完整的用户系统，而是让用户通过第三方平台（微信、GitHub、Google）授权登录。

**适合场景**：需要第三方登录的应用。

**特点**：
- ✅ 用户不需要注册新账号
- ❌ 流程复杂，初学者先了解概念即可

> 💡 在 FastAPI 中，OAuth2 更多是作为一个**框架骨架**被使用——即使你不用微信登录，FastAPI 也内置了 OAuth2 的工具类来帮你实现用户名+密码的登录流程。

#### 📦 JWT（JSON Web Token）—— "带有效期的通行证"

**是什么**：一种特殊格式的 Token，它本身就是一个加密的小数据包，里面包含了用户信息。

**生活类比**：想象一张"有效期30分钟的游乐园通行证"——上面写着你的名字、能玩的项目、有效期。工作人员不需要打电话给总部查你的信息，看一眼通行证就知道了。

**适合场景**：用户登录后，服务器生成一个 JWT 发给前端。前端后续请求都带着这个 JWT，服务器不需要查数据库就能验证用户身份。

**特点**：
- ✅ 无状态——服务器不需要存 Session，适合分布式部署
- ✅ 自带过期时间
- ❌ 一旦签发，中途无法撤销（除非额外做黑名单）

### ③ 总结对比表

| 方式 | 类比 | 核心特点 | 典型场景 |
|------|------|---------|---------|
| **API Key** | 门禁卡 | 固定密钥，简单 | 服务间调用（Agent 调大模型 API） |
| **Bearer Token** | 访客证 | 持有即有效 | 用户登录后携带令牌 |
| **OAuth2** | 第三方授权 | 框架，支持多种流程 | 微信/GitHub 第三方登录 |
| **JWT** | 有效期通行证 | 无状态，自带用户信息 | 用户登录（最常用） |

## 知识点 9.2：API Key 认证

### ① 先理解一个前置概念：什么是 Header？

在前面阶段我们学过，一个 HTTP 请求由三部分组成，就像一个信封：

```
┌─────────────────────────────────────┐
│  请求行：POST /api/v1/chat HTTP/1.1 │  ← 信封封面（我要寄到哪里、用什么方式）
├─────────────────────────────────────┤
│  Header（请求头）：                   │  ← 信封里面的备注信息
│    Content-Type: application/json   │     （认证信息就放在这里！）
│    X-API-Key: secret-key            │
├─────────────────────────────────────┤
│  Body（请求体）：                     │  ← 信封里的信纸（真正要传的数据）
│    {"message": "你好"}               │
└─────────────────────────────────────┘
```

**Header（请求头）**就是请求的"附加信息区域"，里面可以放各种键值对。认证信息（如 API Key）就放在这里。

### ② 为什么 API Key 要放在 Header 里，而不是放在 URL 里？

你可能见过这种写法：`/api/chat?api_key=secret-key`——把密钥直接写在 URL 参数里。

**这非常不安全！** 原因如下：

| 放在 URL 里 ❌ | 放在 Header 里 ✅ |
|----------------|-------------------|
| URL 会被浏览器历史记录 | Header 不会出现在历史记录中 |
| URL 会出现在服务器访问日志中 | Header 相对更隐蔽 |
| URL 容易被分享、截图时泄露 | Header 对用户不可见 |
| 像把钥匙挂在脖子上 | 像把钥匙放在口袋里 |

> 🧠 **原则**：任何敏感信息（密钥、Token）都应该放在 Header 里，永远不要放在 URL 中。

### ③ 代码实现——给 Agent API 加上 API Key 认证

```python
import os
from fastapi import FastAPI, Header, HTTPException, Depends

app = FastAPI()

# ⚠️ 不要硬编码密钥！从环境变量读取
# 在终端设置：set API_KEY=my-secret-key-12345
# 如果没设置环境变量，则使用默认值（仅开发时用）
API_KEY = os.getenv("API_KEY", "dev-default-key")


async def verify_api_key(x_api_key: str = Header(None)):
    """
    认证依赖函数：检查请求头中的 X-API-Key 是否匹配
    Header(None) 表示从请求头中读取 X-API-Key 字段
    如果请求头里没有这个字段，默认为 None
    """
    if x_api_key != API_KEY:
        raise HTTPException(status_code=401, detail="无效的API Key，拒绝访问")


@app.get("/api/v1/chat", dependencies=[Depends(verify_api_key)])
async def chat():
    """只有携带正确 API Key 的请求才能访问这个接口"""
    return {"message": "你好，我是Agent助手，已通过API Key认证！"}
```

### ④ os.getenv 是什么？为什么要用它？

```python
API_KEY = os.getenv("API_KEY", "dev-default-key")
```

这行代码的意思是：**从系统的环境变量中读取名为 `API_KEY` 的值**。

| 参数 | 含义 |
|------|------|
| `"API_KEY"` | 要读取的环境变量名称 |
| `"dev-default-key"` | 如果环境变量不存在，使用的默认值 |

**为什么不直接写死密钥？**

```python
# ❌ 错误示范：硬编码密钥
API_KEY = "my-super-secret-key-12345"

# ✅ 正确做法：从环境变量读取
API_KEY = os.getenv("API_KEY", "dev-default-key")
```

想象一下：如果你把密钥写死在代码里，然后上传到 GitHub——全世界都能看到你的密钥了！
而环境变量是存在服务器系统里的，不会出现在代码中，也不会被提交到 Git 仓库。

> 🧠 **安全原则**：代码可以公开，密钥不能公开。环境变量就是实现这个原则的最简单方式。

### ⑤ 如何测试？

```bash
# 先在终端设置环境变量
set API_KEY=my-secret-key-12345

# 启动服务后，用 curl 测试

# ✅ 携带正确的 API Key → 200 成功
curl -H "X-API-Key: my-secret-key-12345" http://localhost:8000/api/v1/chat

# ❌ 不携带 API Key → 422 参数缺失
curl http://localhost:8000/api/v1/chat

# ❌ 携带错误的 API Key → 401 认证失败
curl -H "X-API-Key: wrong-key" http://localhost:8000/api/v1/chat
```

## 知识点 9.3：JWT 认证

API Key 适合"服务对服务"的简单场景，但如果你的 Agent 系统有**用户注册、登录**功能，就需要更强大的认证方案——JWT。

### ① JWT 的完整工作流程

先看全局流程，再看代码：

```
┌──────────┐                              ┌──────────┐
│  客户端   │                              │  服务器   │
│ (前端/App)│                              │ (FastAPI) │
└────┬─────┘                              └────┬─────┘
     │                                         │
     │  第1步：用户提交用户名+密码              │
     │  ─────────────────────────────────────> │
     │                                         │
     │                          第2步：服务器验证密码
     │                          密码正确 → 生成JWT Token
     │                                         │
     │  第3步：返回JWT Token给客户端            │
     │  <───────────────────────────────────── │
     │                                         │
     │  第4步：后续请求，携带Token              │
     │  Header: Authorization: Bearer xxx.yyy  │
     │  ─────────────────────────────────────> │
     │                                         │
     │                          第5步：服务器验证Token
     │                          解密Token → 提取用户信息
     │                          （不需要查数据库！）
     │                                         │
     │  第6步：验证通过，返回数据               │
     │  <───────────────────────────────────── │
     │                                         │
```

> 🧠 **核心理解**：JWT 的精髓在于——Token 本身就包含了用户信息，服务器不需要查数据库就能验证。
> 就像那张"游乐园通行证"，工作人员看一眼就知道你是谁、能玩什么，不用打电话给总部确认。

### ② JWT 的结构——"三明治"三层结构

一个 JWT 长这样：`eyJhbGciOi.eyJzdWIiOi.SflKxwRJSMe`

它由三段组成，用 `.` 分隔，就像一个三明治：

```
┌──────────────────────────────────────────────────────┐
│  第一层：Header（面包）                                │
│  告诉服务器"我用什么算法加密的"                         │
│  例如：{"alg": "HS256", "typ": "JWT"}                │
├──────────────────────────────────────────────────────┤
│  第二层：Payload（肉饼）—— 最重要的部分                │
│  存放实际数据（叫"声明/claims"）                       │
│  例如：{"sub": "admin", "exp": 1700000000}            │
│  sub = 用户标识，exp = 过期时间                        │
├──────────────────────────────────────────────────────┤
│  第三层：Signature（面包）                             │
│  签名 = 用密钥对前两层做签名，防篡改                    │
│  如果有人偷偷改了 Payload，签名就对不上了               │
└──────────────────────────────────────────────────────┘
```

> 💡 这三层分别经过 Base64 编码后用 `.` 连接，就是你看到的 JWT 字符串。
> 注意：Base64 只是编码，不是加密！任何人都能解码看到内容。
> JWT 的安全性在于**签名**——你能看到内容，但改不了内容。

### ③ 密码哈希——为什么不能存明文密码？

在写登录代码之前，必须先理解"密码哈希"这个概念。

**问题**：如果用户的密码直接存在数据库里，一旦数据库被黑客攻破，所有用户的密码就全泄露了。

**解决**：不存密码本身，而是存密码的"哈希值"。

```
用户输入密码 "password123"
        │
        ▼
  ┌───────────┐
  │ 哈希函数   │  → bcrypt / sha256 等
  └─────┬─────┘
        │
        ▼
  "$2b$12$LJ3m4ys...（一长串乱码）"   ← 存入数据库
```

**哈希的特点**：
- ✅ **不可逆**：从哈希值无法反推出原始密码（就像把鸡蛋做成蛋糕后，无法变回鸡蛋）
- ✅ **固定长度**：不管密码多长，哈希值的长度都一样
- ✅ **唯一性**：不同的密码几乎不可能产生相同的哈希值
- ✅ **验证方式**：用户登录时，把输入的密码做同样的哈希，然后和数据库里的哈希值比对

```python
# 注册时：把密码变成哈希后存储
hashed = pwd_context.hash("password123")
# 存储到数据库的是 hashed，不是 "password123"

# 登录时：验证密码
pwd_context.verify("password123", hashed)  # → True
pwd_context.verify("wrong_password", hashed)  # → False
```

|----|------|

### ⑤ 代码实现——完整的 JWT 认证流程

```python
from datetime import datetime, timedelta
from fastapi import FastAPI, Depends, HTTPException, status
from fastapi.security import OAuth2PasswordBearer, OAuth2PasswordRequestForm
from jose import JWTError, jwt
from passlib.context import CryptContext

app = FastAPI()

# ============ 配置区 ============
# ⚠️ 生产环境必须用环境变量，这里为了演示直接写出来
SECRET_KEY = os.getenv("SECRET_KEY", "dev-secret-key-do-not-use-in-production")
ALGORITHM = "HS256"           # JWT 签名算法
ACCESS_TOKEN_EXPIRE_MINUTES = 30  # Token 有效期：30分钟

# ============ 初始化工具 ============
# 密码哈希工具：用来把密码变成哈希值
pwd_context = CryptContext(schemes=["bcrypt"], deprecated="auto")

# OAuth2PasswordBearer 的作用：
# 告诉 FastAPI "登录接口是 /token"
# 并且"从请求头 Authorization: Bearer xxx 中提取 Token"
# 后续任何用了 oauth2_scheme 的依赖，都会自动去请求头里找 Token
oauth2_scheme = OAuth2PasswordBearer(tokenUrl="token")

# ============ 模拟数据库 ============
# 真实项目中这些数据在数据库里
fake_users_db = {
    "admin": {
        "username": "admin",
        # 这是 "admin123" 的 bcrypt 哈希值
        "hashed_password": pwd_context.hash("admin123"),
    }
}


# ============ 工具函数 ============

def verify_password(plain_password: str, hashed_password: str) -> bool:
    """验证密码：把用户输入的明文密码做哈希，和数据库里的哈希值比对"""
    return pwd_context.verify(plain_password, hashed_password)


def create_access_token(data: dict, expires_delta: timedelta | None = None) -> str:
    """
    生成 JWT Token
    data: 要放进 Token 里的数据，比如 {"sub": "admin"}
    expires_delta: Token 的有效期
    """
    to_encode = data.copy()
    if expires_delta:
        expire = datetime.utcnow() + expires_delta
    else:
        expire = datetime.utcnow() + timedelta(minutes=15)
    # 把过期时间加进去
    to_encode.update({"exp": expire})
    # 用密钥签名，生成 JWT 字符串
    encoded_jwt = jwt.encode(to_encode, SECRET_KEY, algorithm=ALGORITHM)
    return encoded_jwt


async def get_current_user(token: str = Depends(oauth2_scheme)) -> str:
    """
    核心依赖函数：从请求头提取 Token → 解码 → 返回用户名
    这个函数会被很多接口复用，是 JWT 认证的"中枢"
    """
    # 定义一个"认证失败"的异常，后面反复用到
    credentials_exception = HTTPException(
        status_code=status.HTTP_401_UNAUTHORIZED,
        detail="无法验证凭证",
        headers={"WWW-Authenticate": "Bearer"},
    )
    try:
        # 解码 Token：用密钥验证签名，提取数据
        payload = jwt.decode(token, SECRET_KEY, algorithms=[ALGORITHM])
        # sub 字段存放的是用户名
        username: str = payload.get("sub")
        if username is None:
            raise credentials_exception
    except JWTError:
        # Token 过期、被篡改、签名不对 —— 都会走到这里
        raise credentials_exception
    return username


# ============ 接口 ============

@app.post("/token")
async def login_for_access_token(
    form_data: OAuth2PasswordRequestForm = Depends()
):
    """
    登录接口：接收用户名+密码，验证后返回 JWT Token
    OAuth2PasswordRequestForm 会自动解析表单中的 username 和 password
    """
    # 第1步：从"数据库"中查找用户
    user = fake_users_db.get(form_data.username)
    if not user:
        raise HTTPException(status_code=400, detail="用户名或密码错误")

    # 第2步：验证密码（把用户输入的密码和数据库里的哈希值比对）
    if not verify_password(form_data.password, user["hashed_password"]):
        raise HTTPException(status_code=400, detail="用户名或密码错误")

    # 第3步：生成 JWT Token
    access_token_expires = timedelta(minutes=ACCESS_TOKEN_EXPIRE_MINUTES)
    access_token = create_access_token(
        data={"sub": user["username"]},   # sub 是 JWT 标准字段，放用户标识
        expires_delta=access_token_expires
    )
    return {"access_token": access_token, "token_type": "bearer"}


@app.get("/api/v1/agent/status")
async def agent_status(current_user: str = Depends(get_current_user)):
    """
    需要登录才能访问的接口
    get_current_user 会自动从请求头提取 Token 并验证
    如果 Token 无效或过期，直接返回 401，根本不会执行到函数体
    """
    return {
        "message": f"你好 {current_user}，你已通过JWT认证",
        "agent_status": "running",
    }
```

### ⑥ 如何测试？

```bash
# 第1步：登录，获取 Token
curl -X POST http://localhost:8000/token \
  -d "username=admin&password=admin123"
# 返回：{"access_token": "eyJhbGci...", "token_type": "bearer"}

# 第2步：携带 Token 访问受保护的接口
curl -H "Authorization: Bearer eyJhbGci..." \
  http://localhost:8000/api/v1/agent/status
# 返回：{"message": "你好 admin，你已通过JWT认证", ...}

# 第3步：不携带 Token → 401 未认证
curl http://localhost:8000/api/v1/agent/status
# 返回：401 Unauthorized
```

## 知识点 9.4：权限控制

### ① 什么是权限控制？——用公司类比理解

认证解决了"你是谁"的问题，接下来要解决"你能做什么"的问题。

想象一家公司：

| 角色 | 能做什么 | 类比到 Agent 系统 |
|------|---------|------------------|
| **CEO（管理员）** | 看所有文件、管理所有员工、修改公司配置 | 管理员：管理所有 Agent、查看所有用户数据、修改系统配置 |
| **普通员工** | 只能看自己的文件、提交自己的工作 | 普通用户：只能调用自己的 Agent、查看自己的对话记录 |
| **访客** | 只能看公开资料，不能进入办公区 | 游客：只能访问公开接口，不能调用任何 Agent |

> 🧠 **权限控制的核心思想**：不同角色，不同权限。就像公司的门禁系统——CEO 的卡能进所有房间，普通员工的卡只能进自己的工位。

### ② 代码实现——角色权限控制

```python
from fastapi import FastAPI, Depends, HTTPException

app = FastAPI()

# 假设这是从 JWT Token 中解析出来的用户信息
# 真实项目中，get_current_user 会从数据库查询用户及其角色
async def get_current_user(token: str = Depends(oauth2_scheme)):
    """从 Token 中解析用户信息（包含角色）"""
    # 这里简化处理，真实项目会从数据库查
    return {"username": "admin", "role": "admin"}


async def require_admin(user=Depends(get_current_user)):
    """
    管理员权限检查：只有 role 为 admin 的用户才能通过
    这就像一个"门卫"，站在管理员专属接口前面检查身份
    """
    if user["role"] != "admin":
        raise HTTPException(status_code=403, detail="需要管理员权限，你无权访问")


@app.get("/api/v1/admin/agents")
async def list_all_agents(user=Depends(require_admin)):
    """管理员专属接口：查看所有 Agent 列表"""
    return {
        "agents": ["翻译Agent", "代码Agent", "数据分析Agent"],
        "message": "管理员查看所有Agent",
    }


@app.get("/api/v1/admin/users")
async def list_all_users(user=Depends(require_admin)):
    """管理员专属接口：查看所有用户"""
    return {
        "users": ["admin", "user1", "user2"],
        "message": "管理员查看所有用户",
    }


@app.get("/api/v1/my/agent")
async def my_agent(user=Depends(get_current_user)):
    """
    普通用户接口：只需要登录就能访问
    注意这里依赖的是 get_current_user（只要登录就行）
    而不是 require_admin（需要管理员）
    """
    return {
        "message": f"你好 {user['username']}，这是你的Agent",
        "my_agent": "我的翻译Agent",
    }
```

### ③ 更细粒度的权限控制

有时候不只是"管理员 vs 普通用户"，还需要更细的控制：

```python
# 权限表：定义每个角色能做什么
PERMISSIONS = {
    "admin": {"agent:create", "agent:delete", "agent:read", "user:manage"},
    "user":  {"agent:create", "agent:read"},
    "guest": {"agent:read"},
}


def check_permission(user: dict, required_permission: str) -> bool:
    """检查用户是否拥有某个权限"""
    user_role = user.get("role", "guest")
    return required_permission in PERMISSIONS.get(user_role, set())


async def require_permission(permission: str, user=Depends(get_current_user)):
    """
    通用权限检查依赖
    用法：Depends(require_permission("agent:delete"))
    """
    if not check_permission(user, permission):
        raise HTTPException(
            status_code=403,
            detail=f"权限不足：你需要 {permission} 权限才能执行此操作"
        )


@app.delete("/api/v1/agents/{agent_id}")
async def delete_agent(
    agent_id: str,
    user=Depends(require_permission("agent:delete"))
):
    """只有拥有 agent:delete 权限的角色才能删除 Agent"""
    return {"message": f"Agent {agent_id} 已删除"}
```

## 知识点 9.5：安全最佳实践

### ① 密码安全

```python
from passlib.context import CryptContext

pwd_context = CryptContext(schemes=["bcrypt"], deprecated="auto")

# ✅ 注册时：永远存储哈希值，不存明文
hashed_password = pwd_context.hash("password123")

# ✅ 登录时：用 verify 比对，不用 == 比对
is_valid = pwd_context.verify("password123", hashed_password)

# ❌ 绝对不要这样做：
# password = "password123"  # 明文存储
# if input_password == stored_password:  # 明文比对
```

## 知识点 9.6：Harness 架构视角分析

### ① 认证安全在 Harness 中的作用

- **边界控制**：认证是系统的第一道防线，就像小区大门的保安——所有请求必须先"亮身份"，才能进入系统内部
- **错误恢复**：统一的认证失败处理（401/403），避免每个接口各自处理认证逻辑，减少遗漏
- **上下文管理**：认证信息（当前用户是谁、什么角色）作为上下文在系统中传递，后续所有逻辑都依赖这个上下文
- **反馈回路**：认证日志便于安全审计——谁在什么时间访问了什么接口，一目了然

### ② 补偿性代码 vs 系统性工程

| 方式 | 判断 | 说明 |
|------|------|------|
| 使用 OAuth2 + JWT | ✅ 系统性工程 | 标准认证框架，经过大量验证 |
| 使用 bcrypt 哈希密码 | ✅ 系统性工程 | 工业级密码保护方案 |
| 密钥从环境变量读取 | ✅ 系统性工程 | 安全的密钥管理方式 |
| 硬编码密钥 | ❌ 补偿性代码 | 安全隐患，代码泄露 = 密钥泄露 |
| 明文存储密码 | ❌ 补偿性代码 | 数据库泄露 = 所有用户密码泄露 |
| 每个接口手动检查认证 | ❌ 补偿性代码 | 容易遗漏，应该用 Depends 统一处理 |
| 把 Token 放在 URL 里 | ❌ 补偿性代码 | URL 会被记录在日志中，Token 泄露 |

## 🤔 启发式思考题

1. **在 Agent 服务中，为什么认证安全是刚需？**
   提示：如果你的 Agent API 不认证，任何人都能调用你的 Agent，意味着——别人可以用你的 Agent 去调大模型，花的是你的钱！

2. **如何设计 API Key 的生成和管理策略？**
   提示：API Key 应该能生成、能撤销、能设置过期时间、能限制调用频率。想想怎么实现？

3. **JWT 的优点和缺点是什么？在什么场景下适合使用 JWT？**
   提示：JWT 无状态、不需要查数据库，但一旦签发就无法中途撤销。如果你的系统需要"踢人下线"功能，JWT 够用吗？

4. **如何实现多租户的权限控制？**
   提示：在多租户 Agent 系统中，租户 A 不能看到租户 B 的 Agent 和数据。如何在 JWT 中携带租户信息？

5. **API 的限流和熔断是否属于安全范畴？如何实现？**
   提示：即使认证通过了，如果一个用户疯狂调用你的 API，你的服务器可能被打垮。限流（Rate Limiting）也是安全的一部分。
